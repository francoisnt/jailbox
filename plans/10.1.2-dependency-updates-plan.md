# 10.1.2. Automatic dependency updates

## Intent

Implement this plan before the other active plans. It stands alone; its
number only places it first.

### Goal

Keep dependencies current, keep one authoritative place for each pinned
version, and flag compatibility problems that affect users early.

- A daily run updates outdated dependencies one at a time, tests each, and
  lands it on `master` when the tests pass.
- Each release first runs that same update step, then is refused while a
  known update failure is unresolved.
- The daily run also tests the newest release against new editor versions,
  because that is what users run, and records the result.

Decision logic lives in repository scripts that also run locally; workflows
only call them and pass results along.

### Updates

An update is one dependency moving to its newest version:

| Update | Pinned in | Newest means |
| --- | --- | --- |
| `CODE_VERSION`, `REMOTE_SSH_VERSION`, `OPEN_REMOTE_SSH_VERSION` | `versions.env` | newest stable release (one update each) |
| `CODIUM_VERSION` with `CODIUM_COMMIT` | `versions.env` | newest stable release and its build commit (one update) |
| `BASE_IMAGE_DEBIAN`, `BASE_IMAGE_ALPINE`, `BASE_IMAGE_FEDORA` | `versions.env` | newest stable series, by today's Docker Official Images rule (one update each) |
| `GO_SERIES` | `src/go.mod` `go` directive, mirrored in the root `Containerfile` | newest stable Go series |

An update is written as space-separated `KEY=VALUE` pairs: one pair for most
updates (`BASE_IMAGE_DEBIAN=debian:13`, `GO_SERIES=1.28`), both pairs for
VSCodium (`CODIUM_VERSION=1.143.17232 CODIUM_COMMIT=c072…`). A list of
updates concatenates them, each key at most once. This text is the editor
gate script's input, the `update` value in `compatibility/master.csv`, and
the issue title's identifier, so it stays stable across releases. Each key
accepts only its own strict value format, the same formats enforced today;
values are data and are never evaluated as shell.

One repository script applies a list of updates to a checkout: it writes the
pins, regenerates the files built from them, and leaves the tree unchanged on
any failure. The daily run, the editor gate script, and maintainers working
locally all use it.

Releases keep building and testing with the newest patch of the Go series,
and gate reuse keeps requiring that exact Go release.

### Tested commits

A test result always belongs to a commit. Gate runs take the commit to test
as an input, replacing today's per-editor override inputs. A release reuses
a passing five-gate result only for the exact commit it ships: push CI under
today's conditions, or the update step in the same release run. A scheduled
daily run's result is never reused later: its tested commit always has the
results commit on top, so a release starting there runs fresh gates.

### Daily run

One scheduled workflow looks up the newest versions once and runs two jobs.

**Update `master`:**

- The step works from a base commit: `master`'s head for a scheduled run,
  the release's starting commit for a release.
- It tests one update: the eligible pending update attempted least recently
  (by its rows in `compatibility/master.csv`), so an update that keeps
  erroring cannot hold up the others. Only while the pinned Go series is
  unsupported does a pending `GO_SERIES` update go first, since nothing else
  can be tested then.
- An update whose latest row is `fail` is not eligible until that row is
  deleted (for example in the fix PR) or a newer version appears.
- The update becomes one commit on the base, pushed to a temporary branch
  named for the run, and the five gates test that commit. The branch is
  removed when the run ends.
- **Pass:** the tested update commit and a results commit on top of it are
  pushed to `master` in one push that succeeds only if `master` is exactly
  the base. Otherwise only the result rows are recorded, and a later run
  retests the update. Any other push rejection fails the run.
- The step reports the landed update commit, if any, and the pending updates
  blocked by a `fail` row.
- Update and results commits use the automation identity
  `github-actions[bot]` (the name and email the release and compatibility
  scripts use today); `10.1.3-release-notes-plan.md` relies on it to leave
  them out of release notes.

**Check the newest release:**

- Tests the newest published release (the highest version with a row in
  `compatibility/releases.csv`, which a release writes only after
  publishing) with the newest editor and extension versions. Only the editor
  gate runs: editor versions affect nothing else, and the other gates passed
  for that tag at release.
- The gate's steps come from the tag: one repository script installs the
  editors (with the requested updates applied) and runs `tests/run editor`.
  Every editor gate run uses it; this check runs the tag's copy in its own
  job, with its own log names. The script's path, arguments, and updates
  input are the interface `master`'s workflow calls on older tags, so they
  stay stable; its internals may change freely. The check starts with the
  first release that contains the script.
- Skips a tag and editor version set that already has a `pass` or `fail`
  row; `error` rows do not suppress retries.
- A tag that cannot be built because its Go series is unsupported records
  `fail`, and its issue says the newest release needs a new release for
  that reason, not that an editor failed.

### Results

- The two compatibility files are the only memory of what was tested. Both
  gain a `result` column (`pass`, `fail`, or `error`; existing rows become
  `pass`); `compatibility/master.csv` gains an `update` column (empty for
  existing rows). Bash and Podman versions are empty when the run did not
  observe them. The run's rows for both jobs go in one results commit, also
  when an update could not land.
- `fail`: a gate's tests ran and failed, a confirmed incompatibility. It
  files an issue, makes the update ineligible, and blocks releases while
  that version is still the newest.
- `error`: a selected update or release check stopped before its tests
  (resolving Go, downloading or installing dependencies). It files no issue,
  blocks nothing, and leaves it eligible; the red run is the notice.
- A failing newest-version lookup or failing reporting fails the run
  without a row.
- For a new `fail`, the issue is filed before the row is recorded; a rerun
  after a failed recording may file a duplicate issue, which is accepted.
  Issues are only created, never searched or closed by automation; each
  names the row to delete to retry.
- Reporting runs from `master`'s scripts, so the CSV format and issue rules
  stay current. Documentation that links the files explains `result`.

### Release

The same rules apply regardless of the version bump.

1. The release runs the update step with its starting commit as the base,
   so the update state is fresh even if the schedule stopped. The
   newest-release check is skipped.
2. It ships the tested update commit when the step landed one (not the
   results commit on top), otherwise its starting commit; commits others
   push meanwhile are never shipped. A selected update ending in `error`
   lands nothing. If the step cannot look up versions or report, the release
   fails and can be rerun.
3. It is refused while the step reports a pending update blocked by a
   `fail` row, naming that row. A failed version that is no longer the
   newest blocks nothing.
4. Otherwise it proceeds as today on that commit: it reuses the update
   step's result after a landed update, or push CI, or runs the gates, then
   packages, tags, and records its row in `compatibility/releases.csv` after
   publishing. A failed recording fails the run; rerunning its recording job
   writes the row.

The release itself never applies updates or commits pins.

### Removed behavior

- The separate Go-support and base-image jobs in
  `.github/workflows/canary.yml`.
- Issue filing in `scripts/canary-base-images.sh`; its stable-series lookup
  moves to `scripts/lib/`.
- `scripts/bump-base-image.sh`, replaced by the general update script.
- The editor-only pin advance in `scripts/canary-report.sh`, generalized to
  any update, and its issue lookup and closing (`gh issue list`,
  `gh issue close`).
- The `code_version`, `codium_version`, `remote_ssh_version`, and
  `open_remote_ssh_version` inputs of `.github/workflows/test-gates.yml`, and
  the `JAILBOX_*` editor overrides read by `tests/ci/setup-linux.sh` and
  `scripts/record-compatibility.sh`.
- `PINS_LAST_VERIFIED` in `versions.env` and the generated tested-matrix
  block; Git history dates each update.

### Non-goals

- Maintenance branches for hotfixes; they get their own plan when needed.
- Release notes, which `10.1.3-release-notes-plan.md` covers.

### Acceptance

Unit tests with fixture repositories cover:

- the update script for each key, invalid keys and values, and an unchanged
  tree on failure;
- update selection: least recently attempted first, `GO_SERIES` first only
  while the pinned series is unsupported, `fail` rows excluded until deleted
  or superseded;
- landing: the landed commit is the tested commit, and update and results
  commits carry the automation identity; a pass lands with its
  results in one push, or records only results when `master` is not exactly
  the base (including a rewound `master`); another rejection fails;
- results: `fail` files one issue and blocks, `error` files none and blocks
  nothing, a lookup failure records nothing; empty Bash and Podman fields
  are accepted;
- the newest-release check: target selection from `releases.csv`, the skip
  rule, retry after `error`, and the Go-support `fail`;
- the release: shipping the landed or starting commit, continuing after an
  update `error`, failing on a lookup failure, refusing while a pending
  update is blocked, and not refusing for a superseded failure;
- no automation searching or closing issues.

`tests/unit/release-workflow.sh` asserts the new workflow wiring. CI gates
this depends on: lint and portable; the first real daily run and release are
the end-to-end check.

## Implementation detail

Guidance only; the implementer chooses the mechanisms.

- Newest-version lookups exist: `scripts/resolve-latest-versions.sh` and the
  `codium-commit` job in `canary.yml` (editors), `stable_image_version` in
  `scripts/canary-base-images.sh` (images), and `go.dev/dl/?mode=json` as
  read by `scripts/go-version.sh` (Go).
- `GO_SERIES` changes the `go` directive in `src/go.mod` (for example with
  `go mod edit -go`) and the `golang:X.Y-trixie` image in the root
  `Containerfile`, which `tests/unit/release-workflow.sh` already checks.
- The update script can grow out of `scripts/bump-base-image.sh` (strict
  validation, regeneration, restore on failure).
- Each `test-gates.yml` job checks out the commit input. Each daily run
  calls it at most once, so artifact names and outputs need no per-update
  variants. `verified-result` records evidence for that commit; its guard
  against editor overrides goes away with them.
- `scripts/lib/release-gates.py select` keeps accepting only push CI; the
  release reads its own update step's outcome directly. Pushes with the
  workflow token start no workflows, so the temporary branch triggers no CI.
- The landing push must require `master` to equal the base exactly; a plain
  push also succeeds when `master` was rewound to an ancestor.
  `scripts/canary-report.sh` uses
  `--force-with-lease=refs/heads/master:<base>`, and its uncommitted
  worktree fix uses `git ls-remote` to tell a moved `master` apart from
  other rejections.
- The release can call the daily workflow as a reusable workflow, with a
  base-commit input, an input that skips the newest-release check, and
  outputs for the landed commit and blocked updates. Gate, package, install,
  and tag steps in `release.yml` use `GITHUB_SHA` today and must use the
  shipped commit.
- Result rows can reuse the retrying append in
  `scripts/record-compatibility.sh` and the schema in
  `scripts/lib/record-compatibility.py`; `tests/lib/compatibility-tests.py`
  reads `releases.csv` too. `record-compatibility.sh` requires `HEAD` to
  equal `GITHUB_SHA` and takes Bash and Podman from the runtime gate; daily
  rows need the tested commit and versions passed explicitly.
