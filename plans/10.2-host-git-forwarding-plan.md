# 10.2. Host Git through command forwarding (draft)

## Intent

Status: draft, pending the decisions below. This document does not authorize
implementation. Settle and implement it after 10.1 and before
`11.1-go-frontend-plan.md`. Forwarded Git uses the service from
`10.1-host-command-forwarding-plan.md`. This plan owns bundled policy presets,
the Git integration, and their verification.

### Goal

Let supported Git commands typed inside the container run on the host against
the existing project checkout. Pushes can use the host user's SSH key, SSH
agent, or credential helper while credentials and agent access stay on the
host.

### Presets

- jailbox ships policy presets: policy files in the 10.1 language, installed
  with the runtime bundle. This plan ships one preset, `git`.
- Each preset has its own activation key, off by default. For Git that is
  `HOST_COMMAND_GIT` (`true` or `false`, default `false`; machine callers use
  `JAILBOX_CONFIG_HOST_COMMAND_GIT`). Later presets add their own keys; a preset
  without a declared key fails explicitly. An active preset enables forwarding
  even without `HOST_COMMAND_POLICY`. Without any of these keys, nothing is
  forwarded. As with `HOST_COMMAND_POLICY`, the frontend only passes the keys;
  core resolves presets from the installed bundle and enforces them.
- The effective policy is all active presets plus the `HOST_COMMAND_POLICY`
  file. The 10.1 rule that exactly one definition must match applies across all
  sources: a custom policy can add definitions but cannot override a preset's.
- Presets contain only policy rules. Protections specific to a program are
  jailbox code tied to that program; they apply to every definition running it,
  whether it comes from a preset or a custom policy.
- Preset contents are part of the policy snapshot and compatibility checks, so
  an upgrade that changes a preset requires stop/start before reuse. Release
  notes identify preset changes, and widening a preset follows the release
  version policy for public changes.
- The documentation lists each preset's exact rules.

### Why forwarding Git needs more than 10.1

Today the container can access `.git` in the shared checkout and can write it
under the default writable project mount. Forwarding adds a way for container
processes to start host Git on demand with the host user's permissions and
credentials. A read-only `.git` mount protects direct writes through that
mount. Host Git can still read state planted during an earlier session and
consult files in the writable checkout. The Git design must account for these
routes:

- Writable `.git/config` or `.git/hooks` can select arbitrary host commands
  (hooks, `core.fsmonitor`, `core.sshCommand`, credential helpers, remote URLs).
- Hooks configured to live in the working tree (for example husky's
  `core.hooksPath=.husky`) or hook frameworks that run project-defined scripts.
- A nested `.git` directory or gitfile planted in a subdirectory, found by
  repository discovery when Git runs from that subdirectory.
- Submodule recursion, which runs Git inside working-tree directories whose
  gitfiles the sandbox controls.
- `.gitattributes`, which selects filter, diff, and merge drivers defined in
  the host user's Git configuration (for example git-lfs).
- Arguments that change Git's configuration, repository, or helper programs,
  such as `-c`, `--config-env`, `-C`, `--git-dir`, `--work-tree`,
  `--exec-path`, `--upload-pack`, and `--receive-pack`.
- State planted while `.git` was writable in earlier sessions.

A forwarded push can publish both container-authored commits and commits already
in the checkout. The host must control which remote and branch a forwarded push
can update, regardless of the arguments and repository settings available to the
container. Keeping credentials on the host still grants the container whatever
publishing authority the policy allows.

### Pending decisions

The protections that answer each route above, handling of Git invocations the
policy does not list (including editor Git integration), use of the host user's
Git configuration, submodule and linked-worktree support, and review of
pre-existing repository state still need decisions before this draft can become
an implementation plan.

## Implementation detail

Keep preset files under `src/` so packaging installs them, and cover both
checkout and installed layouts. Use the forwarding service for request delivery
and command lifetime. Keep
repository selection, Git-specific checks, and credential use in the Git
integration. Verify that requests sent directly to the service receive the same
checks as requests sent by the container wrapper.
