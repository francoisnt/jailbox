# 3.2. Machine boundary charter

## Goal

Establish jailbox's machine interface as a first-class product boundary and
layer the human editor workflow on top of it as a strict internal consumer,
within one repository and one installed command:

```text
orchestrators -----------> jailbox machine commands -> Podman
jailbox editor frontend -> jailbox machine commands -> Podman
```

The orchestrator lane is not speculative: a first-party orchestrator is
planned, and the machine surface — schema discovery, forward-compatible
connection records, and the version-range policy — is its contract.

The machine surface is environment-only configuration plus explicit commands:
`up`, `stop`, `status`, `config-schema`, `connection-info`, `doctor`,
`--clean`, and `--version`, plus the attach commands `exec` and `shell` that
03.2.09.1 and 03.2.09.2 add. `--help` and `--uninstall` sit outside both
layers: they consume no configuration and describe or remove the installation
itself.

The frontend owns the config file and its `--config` selection, `init`, editor
discovery, profiles, bootstrap hosts, and editor launch, and reaches the
machine surface only by invoking the public CLI as child processes. It also
owns `--no-editor`, which 03.2.11 adds so the file-driven headless workflow
survives `up` becoming environment-only. `ssh-config` does not survive the
series: 03.2.09 moves its editor-agnostic connection instructions into
`doctor`, and 03.2.11 then removes the command.

Splitting the frontend into an independent Go product is deferred, not
rejected. `repository-split-rationale.md` records the original split
rationale and the deferral addendum with its revival triggers; the archived
split-era stubs 03.1.1 and 03.2.11–03.2.15 point at the full text (in git
history at `9a04def`) that remains the starting point if it is revived. The
active 03.2.11 reuses that number deliberately: the in-repo frontend layer
replaces the whole archived 03.2.11–03.2.15 range.

## Sequence

Implement the indexed plans in filename order. Version precedes digest because
the release version is hashed; digest precedes ownership-label removal because
it becomes the reuse gate; the frontend refactor lands last, after every
machine interface it consumes exists and passes its gates.

No release will be made until every plan in this series is implemented and
all three test gates pass. Intermediate implementations need not provide the
completed series' full behavior. Work may depend on a later plan when that
dependency and the remaining integration are explicitly tracked and accounted
for; all test gates must continue to pass. Reviews and implementations should
assess those dependencies against the completed series rather than require
temporary compatibility behavior for an unreleased intermediate state.

Every load-bearing forward dependency must be recorded at both ends. The
receiving plan owns completion of the integration and its verification, with
explicit acceptance criteria; the originating plan's forward reference alone
does not assign that work to a later implementer.

## Normativity

External surfaces are normative in every indexed plan: command names and
semantics, configuration keys and their validation outcomes, machine schemas
and record formats, digest content, security invariants, and error classes.
Internal prescriptions — named functions, module placement, ordered
procedures, exact message wording — are guidance. They record one design that
was thought through and are worth reading as such, but they are not a
specification to transcribe. The implementor is expected to substitute a
better design wherever one serves the same intent, and to check this detail
against the tree rather than trust it: these plans were written ahead of the
code and their internal prescriptions go stale as the repository moves. Where
detail is stale or simply worse than what the work reveals, follow the intent
and report the divergence. Neither improving on a prescription nor discarding
a stale one requires a plan amendment. A departure that changes an external
surface still requires updating the owning plan first.

## Layer boundary

Core owns canonical environment configuration and validation, images, Podman
lifecycle, filesystem and egress policy, SSH generations and transport,
deterministic identity, machine status/connection data, and portable/runtime
gates. Editor-server runtime packages remain part of core's generic
attached-development wrapper contract; users customize images through their
Containerfile.

The frontend layer owns `jailbox.conf` parsing, `init`, `--config` selection,
editor discovery/validation, profiles, bootstrap destinations, and editor
launch. Editor diagnosis lives in that validation rather than in a diagnostic
command: the frontend checks the editor before any lifecycle mutation and its
refusals name every unmet requirement, while `doctor` stays core-owned,
configuration-independent, and free of editor state. It composes
`JAILBOX_CONFIG_*` values from the file, invokes `jailbox up` and `jailbox
connection-info` as child processes with that environment, and never sources
lifecycle modules, calls Podman, or reads core runtime state directly. A
boundary check enforces this, making the frontend the reference consumer of
the machine interface. The frontend also owns the editor gate, which doubles
as the machine interface's integration test precisely because the frontend
reaches core only through the CLI.

Neither layer owns worktrees, external credentials, agent selection,
scheduling, or Git integration.

## Security invariants

- Container roots remain read-only, with capabilities dropped and
  `no-new-privileges`.
- No container-engine socket is mounted.
- Project runtime state remains outside the project.
- Core validates and read-only mounts known launch inputs; the frontend
  protects the policy inputs only it knows about.
- Egress mode has no direct route and HTTP(S) uses the allowlisting proxy.
- SSH uses strict host-key checking and project-scoped pinned state.
- Each new container generation gets fresh client/server credentials; resume
  preserves and validates that generation.

Persistent home content is sandbox-controlled state trusted across policy and
version changes. Server material is read-only and client secrets stay
host-only. Digest and structure validation prevent weakened resume. Guarantees
cover one lifecycle command at a time; locking remains backlog work.

## Acceptance criteria

- Machine commands consume only environment configuration and expose the
  documented machine schemas.
- The frontend reaches core exclusively through the public CLI as child
  processes and passes the boundary check.
- Bare `jailbox` remains the human editor launch, `--no-editor` carries the
  file-driven headless launch, and `up` remains the explicit machine launch.
- All indexed plans and their gates pass in order.

## Non-goals

- A repository split, a second installed executable, a Go rewrite, a TOML
  config format, or the `WRAPPER_SETUP` caller mechanism — all deferred with
  the split; see the rationale addendum.
- Plugins, a private API, a separate protocol version, or an installed or
  dynamically downloaded shared runtime library.
- Automatic dependency installation.
- Moving SSH out of core.
- Automatic cleanup/replacement, persistent integrity monitoring, or lifecycle
  serialization.
