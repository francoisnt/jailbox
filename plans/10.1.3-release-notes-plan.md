# 10.1.3. Generated release notes

> Draft: points marked ⚑ are still to be settled and are collected under
> "Points to settle" at the end. They are removed once decided.

## Intent

Implement after `10.1.2-dependency-updates-plan.md` and before the other
active plans. It reads release test results from the `compatibility`
branch that 10.1.2 introduces.

### Goal

Releases have no notes today. Every release must publish notes that tell a
user what changed and what it was tested with, generated as far as possible
from facts the repository already holds, so writing them costs the
maintainer nothing.

### Inputs and preview

One repository script produces the notes. Its output depends only on:

- the range from the previous release to the shipped commit (⚑ S5 decides
  what counts as the previous release);
- the release decision: the new version and why it was chosen, including a
  requested minimum bump or first major;
- the verified test results, when they exist: the run link and the observed
  Bash and Podman versions.

The same inputs always produce the same notes, locally or in CI. A local
preview, before any test results exist, uses the decision `scripts/release.sh
--dry-run` makes with the same options and marks the tested-with section as
not yet tested.

### Notes content

Sections with nothing to report are left out.

1. **Summary:** the new and previous version, and why this bump was chosen
   (breaking interface change, additive change, requested minimum, first
   major, or none).
2. **Interface changes:** every change the release tool's comparison
   classifies as breaking or additive, with breaking changes marked. Today
   that is configuration keys, commands, and flags added or removed.
   Because the notes and the version come from the same comparison, they
   can never disagree.
3. **Dependency changes:** each pin that changed, old → new, with what it
   means for users: Alpine is the base of the egress proxy image jailbox
   builds; Debian is the default base in the `Containerfile` that
   `jailbox init` writes; Fedora is test coverage only; editor and extension
   versions are the tested versions; the Go series is the compiler of the
   shipped programs. A pin present at only one end is listed as added or
   removed; for example, the first release after `v0.5.2` shows the Go series
   as added, since that tag has no `src/go.mod`. ⚑ S4
4. **Changes:** the subjects of the commits in the range. ⚑ S3
5. **Tested with:** the editor and extension versions, base images, and the
   Bash and Podman versions the release's gates ran with, linking that run.
6. **Install or upgrade:** fixed instructions.

### Publication

- The notes are generated before the tag is created; a failure to generate
  them refuses the release, so no release ships without notes.
- ⚑ S1: where the notes are published.
- ⚑ S2: whether a maintainer can add hand-written text, and how.

### Dependencies

- Release test results are rows in `releases.csv` on the `compatibility`
  branch (10.1.2). Automation never commits to `master`, so every commit in
  the range comes from a reviewed PR.
- The interface section reads the release tool's comparison. Today that is
  `scripts/public-api-diff.sh`, which prints only `removed`, `added`, or
  `unchanged`; it must also report each change. `11.2.4-public-interface-
  plan.md` replaces that comparison and owns keeping this section complete:
  every change it classifies as breaking or additive, including changes
  that keep the name (a key's type or namespace, a command moving between
  programs, a reordered or changed output field), appears in the notes.

### Removed behavior

- `CONTRIBUTING.md` asks maintainers to mention new Debian and Alpine bases
  in the release notes by hand; the notes now do it.

### Non-goals

- GitHub's own generated notes, which depend on pull requests and the
  hosting service.
- Rewriting commit subjects; they are already written in plain language.

### Acceptance

- The interface section lists every change the comparison classifies as
  breaking or additive, and nothing else, even when a removal or a requested
  minimum alone determined the version.
- Every changed pin appears once with its old and new value and its user
  meaning; added and removed pins are labeled; unchanged pins do not appear.
- The tested-with section matches the release's `release` row in
  `releases.csv` on the `compatibility` branch; a local preview marks it as
  not yet tested.
- Identical inputs produce identical notes.
- A release whose notes cannot be generated is refused before tagging.
- Unit tests with fixture repositories cover each section, a repository with
  no previous release, a previous release without `src/go.mod`, a requested
  minimum bump, and a release with no changes in a section.

## Implementation detail

Guidance only; the implementer chooses the mechanisms.

- `scripts/release.sh` selects the version from the latest tag and
  `scripts/public-api-diff.sh`; the summary can reuse that selection.
- Pins live in `versions.env` and the `go` directive of `src/go.mod`; read
  both at the two refs with `git show`, treating a missing file as no pin.
- `softprops/action-gh-release` in `release.yml` accepts a notes file.
- The tested-with values are the `publish` job's outputs that
  `record-compatibility.sh` already receives.

## Points to settle

1. **S1 — Where notes are published.**
   - (a) The GitHub release text only (recommended to start).
   - (b) Also a `CHANGELOG.md` in the repository. Every change to `master`
     goes through a PR, so each release would need a changelog PR.
   - (c) Also a notes file inside the release package, so offline installs
     carry them.
2. **S2 — Hand-written text.**
   - (a) None; generated content only (recommended to start; commit subjects
     already explain changes).
   - (b) An optional highlights paragraph given when starting the release,
     for example as the message of the release-request tag.
   - (c) A notes file maintained in PRs and consumed at release; clearing it
     afterwards needs another PR.
3. **S3 — Which commits are listed.**
   - (a) Only commits that change what users receive: `src/`, `docs/`,
     `README.md`, `LICENSE`, and the scripts that build the package
     (`scripts/build-programs.sh`, `scripts/build-tarball.sh`), so test,
     plan, and CI work stays out (recommended). The cost is keeping that
     list in step with the package build.
   - (b) Every commit.
4. **S4 — Security-relevant changes.** Add a section listing commits that
   touch the security documentation (`docs/security.md`) or the README
   threat model, or leave security changes in the general list
   (recommended).
5. **S5 — A tag whose publication failed.** The release pushes its tag
   before publishing, so a failed publication leaves a tag users never
   received; the next version choice and notes would start from it.
   - (a) A release that fails after pushing its tag checks whether its
     GitHub release was published, and deletes the tag only if it was not.
     Publication can succeed before a later step fails, so the job's failure
     alone is not proof. Every remaining tag is then a published release,
     and both the version choice and the notes keep using the highest tag
     (recommended).
   - (b) Both use the highest release with a `release` row in
     `releases.csv` on the `compatibility` branch, and the next release must skip the
     stale tag's version number. A published release whose row failed to
     record stays invisible until that recording is rerun.
