# 3.2.11. Editor frontend layering

## Intent

### Goal

Restructure the human editor workflow into a frontend layer that consumes
jailbox's machine interface exclusively through the public CLI, making bare
`jailbox` the reference consumer of environment configuration, `up`, and
`connection-info`.

### Sequence

Implement after 03.2.09.2. Together with 03.2.16, this plan replaces the
archived split-era plans numbered 03.2.11 through 03.2.15; the deferral is
recorded in `repository-split-rationale.md`.

03.2.16 owns the remaining consumer-compatibility fixtures, durable architecture
document, caller-serialization documentation review, complete installer
dependency validation, and final cross-series documentation verification.
This plan completes frontend behavior and its
composition, attachment, and boundary tests; release still requires 03.2.16
and all four gates. The consumer-verification handoffs assigned to 03.2.11
by archived 03.2.08 and 03.2.09 transfer to 03.2.16; frontend connection
parsing and attachment tests remain here.

### Module ownership and boundary

Gather all frontend implementation files in `host/frontend/`, absorbing
`host/editor.sh` and the strict config-file parser retained by 03.1:

- `jailbox.conf` discovery, `--config` selection, strict parsing, and `init`;
- explicit file validation through `--config PATH validate`, composing policy
  and delegating local-input checks to the public machine `validate` command;
- editor binary and Remote SSH extension discovery and validation;
- isolated profile path/settings generation under
  `~/.local/state/jailbox/editor-profiles/`;
- deterministic environment composition and machine-command invocation; and
- connection-record parsing and editor launch.

Place machine implementation modules in `host/core/`. Any frontend entry
module and editor module belong together in `host/frontend/`; their filenames
and division of responsibilities remain implementation choices. Keep shared
public declarations in `host/public-api.sh`, usable by both layers without
core initialization. These directory ownership rules are required by
`AGENTS.md`.

Migrate the existing flat host modules as part of this implementation, using
`git mv` for tracked file moves. Update source paths in `jailbox`, modules,
tests, and tooling; update `install.sh`'s required-file inventory and verify
release packaging and installation include both directories and their required
modules. Lint, syntax, and boundary checks must discover files throughout the
new directories. Update active documentation and `AGENTS.md` module paths;
leave archived plans unchanged. Existing paths named below identify the
pre-migration code to change.

The frontend reaches core only by executing the public CLI as child
processes. It never calls lifecycle, network, SSH, image, or identity
functions in-process, never invokes Podman, and never reads SSH or runtime
state files directly; `connection-info` is its sole source of connection
data. Enforce this with a boundary check in `scripts/lint.sh` or a portable
test that fails when any frontend module references non-public core functions
or core state paths, or reads or writes private core configuration globals.
Parsed configuration and composed policy have frontend-owned state; shared
public declarations remain available without relying on core initialization.

Move editor resolution from `host/preflight.sh`'s `host_preflight` into
`host/frontend/`, including selection precedence, binary discovery, and
invalid-editor refusals. Move ownership of `EDITOR_BIN`, currently declared
in `host/preflight.sh`, into the frontend. Core preflight retains only machine
prerequisites and performs no editor discovery or validation. Remove core
reads of editor state through the image-hook removal and network-policy
migration specified below; editor selection follows the launch sequence's
precedence in its frontend owner.

With this plan, machine commands stop reading `jailbox.conf`: delete the 03.1
temporary adapter fallback from `up`. `exec`, `shell`, `connection-info`, and
`validate` already load environment configuration directly. Replace the shared
`load_effective_config` path in `prepare_launch` in `jailbox` as bare launch
moves to the frontend, and remove `command_requires_config` from
`host/common.sh`; the frontend owns the required default-file rule.
Core also stops anchoring config files, because it can no longer resolve
them: remove `DEFAULT_CONFIG_INPUT`, `SELECTED_CONFIG_INPUT`, and
`DEFAULT_CONFIG_PRESENT` from `host/common.sh` and their automatic-input
handling from `finalize_effective_readonly_paths` in
`host/container-runtime.sh`, leaving `SELECTED_DEV_CONTAINERFILE_INPUT` in
place because the Containerfile remains a core input. The frontend's
`READONLY_PATHS` anchor replaces the removed automatic protection, so the
protection itself is unchanged; only the layer that declares it moves.

The strict parser survives as frontend code and the file remains the
frontend's permanent human surface. Environment callers are unaffected. The
parser keeps both of its current value rules — no whitespace and no shell
metacharacters — and adds rejection of ASCII control characters (bytes
0x01–0x1F and 0x7F). The combined rule rejects a strict superset of what
03.1's environment contract rejects, so every value the file admits is
already a legal environment value and the file-to-environment mapping is
byte-clean by construction. Reject NUL bytes anywhere in the selected file
before parsing can silently discard them, naming the selected file and the
line where determinable; file input, unlike environment values, can contain
NUL. The existing whitespace rule already covers TAB and the newline family; retain
ordinary line delimiters and permitted formatting whitespace in the file.

### Command surface

Bare `jailbox` is the human editor launch. `jailbox --no-editor` performs the
same file-driven composition and `up` invocation but skips editor discovery,
bootstrap-host composition, and editor launch, preserving today's headless
`jailbox up` file workflow; the machine `up` command itself is environment-
only. `init` moves to frontend ownership as a local file-creation command;
`--config` selects files for frontend launches and the explicit file-validation
form.

Declare `--no-editor` as a non-lifecycle frontend command in
`host/public-api.sh`, with the required help and handler mappings. Frontend
commands compose and invoke public core commands; core lifecycle commands own
resource mutations and their failure handling. Keep named frontend commands in
`CLI_OTHER_COMMANDS`, outside `CLI_LIFECYCLE_COMMANDS`. Update the category
comment in `host/public-api.sh` to explain this distinction for both bare
launch and `--no-editor`, which delegate lifecycle operations to `up`. Verify
frontend composition, delegation, sequencing, and failure propagation
separately from `up`'s lifecycle matrix coverage. Frontend-only file keys
already live in their own `FRONTEND_SCALAR_KEYS` class there, separate from
`CONFIG_SCALAR_KEYS`/`CONFIG_ARRAY_KEYS`; preserve that separation so
`config-schema` never emits them while `scripts/public-api-diff.sh` still
covers them. The generated public-API comparison must classify declaration
changes, including `--no-editor`, under 03.2.01's bump policy. Review also
classifies the added `--config PATH validate` behavior, removal of the temporary
`up` file fallback, removal of init's resource-state gate, changed bare-launch
handling of inherited machine configuration, and tightening of the config-file value
grammar: semantic changes are not detected by a comparison of declaration
names alone.

### Launch sequence

Bare `jailbox` performs these ordered steps:

1. Canonicalize the project and default/selected configuration paths under
   the existing symlink rules; the default `jailbox.conf` anchor is required
   even when `--config` selects another file.
2. Parse the selected file with the strict parser. File `EDITOR` is
   frontend-only state and is never exported to core.
3. Resolve the editor by precedence `JAILBOX_EDITOR`, then file `EDITOR`,
   then `codium` when available, then `code`, and require the selected binary
   and its Remote SSH extension before any machine command. The inherited
   shell `EDITOR` variable must not influence selection. Require
   `jeanp413.open-remote-ssh` for Codium and `ms-vscode-remote.remote-ssh` for
   Code in the extension inventory used by the launched editor. A failed
   inventory query refuses even if it prints the expected extension. Editor
   and extension versions do not gate launch or produce version warnings;
   the documented tested versions remain CI evidence, not runtime limits.
   An extension-inventory query on every bare launch, including reopening a
   running sandbox, is an accepted cost of checking current prerequisites.
4. Compose the final machine environment: map file keys to bare
   `JAILBOX_CONFIG_<KEY>` scalars and contiguous indexed array members;
   append the selected editor's bootstrap destinations only when the parsed
   `EGRESS_ALLOW` is nonempty;
   append the default and any distinct selected in-project config file to
   `READONLY_PATHS`; retain first occurrences and drop later byte-identical
   duplicates. Remove every inherited `JAILBOX_CONFIG_*` entry from each
   child environment and export exactly the parsed and composed machine
   declarations. Preserve all unrelated environment entries, including
   `PATH`, `HOME`, XDG, Podman, and DBUS settings. When inherited machine
   configuration is ignored, emit a notice on stderr naming variables only,
   never their values, and direct environment-driven callers to `jailbox up`.
   Apply this behavior to bare launch, `--no-editor`, and explicit file
   validation. Bare launch therefore always uses file policy, replacing its
   current environment-precedence behavior.
5. Invoke `jailbox up` as a child process with exactly that environment.
6. If and only if `up` succeeds, invoke `jailbox connection-info` as a child
   process with the byte-identical environment.
7. Strictly parse the NUL-delimited records defined by 03.2.09: require one
   each of `ssh_config`, `ssh_host`, `remote_path`, `project_id`, and
   `proxy_url` in the documented order; reject duplicates, malformed or
   unterminated records, and missing fields; ignore valid trailing future
   fields.
8. Generate isolated editor settings — set editor `http.proxy` exactly when
   `proxy_url` is non-empty and omit it otherwise — and launch Remote SSH at
   the reported host and path.

Generated settings must be valid JSON and preserve each accepted connection
value exactly after JSON decoding, including quotes and backslashes in paths.
Settings inspection must recognize those same decoded values. Invalid input
must fail before editor launch rather than publish unusable settings.

Never infer success from diagnostics or continue after either child command
fails. The frontend never calls `stop` or `--clean` automatically; refusals
surface core's directional recovery guidance unchanged. Switching editors or
switching between bare `jailbox` and `--no-editor` refuses when bootstrap-host
composition changes the effective allowlist, with `jailbox stop` then a fresh
launch as recovery. An unchanged effective host set permits reuse, including
when the file already lists the relevant bootstrap hosts; unfiltered launches
compose no bootstrap hosts. Selecting another in-project file with `--config`
refuses when its anchor changes the ordered `READONLY_PATHS` value. If both
anchors are already present and composition leaves that value unchanged, the
selection alone does not change the digest. An out-of-project selection adds
no anchor. In every case, reuse still requires all other policy and health
checks to pass.

Each child invocation establishes its own required state and health evidence.
Successful `up` does not let `connection-info` skip validation, and the frontend
must not cache or pass private validation results between them. Batching remains
inside core invocations; the frontend adds no duplicate health implementation.

### File validation, `init`, and connection instructions

This plan owns 03.2.09's file-validation handoff. `jailbox --config PATH validate`
uses the frontend's existing strict parser, validates file-only keys, and
composes the same machine environment and protected config anchors as
`--no-editor`. It invokes `jailbox validate` as a child without `--config` in
the environment composed under step 4, including its notice and preservation
rules. Inherited `JAILBOX_CONFIG_*` values cannot affect this
explicit file-validation path. `jailbox validate` without `--config` remains
environment-only, even when a jailbox.conf exists. Document
`jailbox --config jailbox.conf validate` as the default-file check.

No editor discovery, bootstrap-host addition, profile generation, up, or
connection-info call occurs during file validation. Its success checks the
file's headless machine policy and local inputs, not editor readiness or
existing sandbox compatibility. Propagate core failures and emit no frontend
success after a failed child; syntax failures name the selected file and line.
Reuse the parser and composition helpers, not a second validation implementation.

`init` creates the minimal configuration independently of sandbox state. It
requires neither Podman nor any machine-command call, including `status`.
Preserve no-overwrite behavior, strict path checks, and safe file publication:
existing destinations, including symlinks and directories, must not be
overwritten, and failed preparation or publication must not leave partial
configuration or report success. Creating the file does not mutate existing
sandbox resources; later launches enforce policy compatibility through core.

Complete the init migration assigned here by archived 03.2.06 and 03.2.08
by removing the resource-state guard. Remove `run_init`'s
`require_sandbox_absent` call, Podman prerequisite, and core identity
initialization in `jailbox`, and remove the obsolete helper from
`host/container-runtime.sh`. Migrate `init_project_config` from
`host/common.sh` into the frontend while retaining its publication safeguards.
In `tests/unit/init-config.sh`, replace `test_init_needs_podman_only` and its
"init still requires podman" assertion with a regression proving successful
initialization without Podman. Remove the obsolete
`tests/fixtures/init-podman.sh` fixture and its setup references. Update both
README.md passages: remove the `status` section's "initialization requires
successful `absent` plus newline" contract and the troubleshooting row requiring
absent containers before `init`.

`init` also seeds advisory protection suggestions. The fixed candidate set,
in output order, is `.env`, `.git/hooks`, `AGENTS.md`, `CLAUDE.md`, and
`.github/workflows`. List each existing candidate as a commented path, without
an assignment, and explain that selected paths should be added comma-separated
to the single live `READONLY_PATHS=` assignment. Detection checks path existence
without reading candidate contents. Absent candidates are skipped without
stubs, nothing is enabled, and the effective created policy remains minimal.
Enabling suggestions must leave one assignment rather than require duplicate
keys or inline comments, neither of which the parser accepts. Document the
candidate set and order. Interactive and flag-driven initialization remains
backlog work.

Retain core's `ssh-config` command for human connection instructions as defined
by 03.2.09. The frontend never parses that output: `connection-info` remains its
only connection-data source. README supplies the editor setting name paired
with the path ssh-config reports.

Editor launch validation carries its own diagnostic obligation. A refusal must
name every requirement it found unmet and the resolved editor together with the
precedence step that selected it, so a user can correct the setup from one
refusal instead of discovering the next problem on the next launch. Because
validation precedes any lifecycle mutation, a refused launch leaves no
resources behind and is safe to repeat as a diagnostic.

Editor validation covers host-side binary and extension presence requirements;
it does not diagnose the selected image's compatibility with that editor.
Remove `warn_if_alpine_dev_image_with_vscode` from `host/dev-image.sh` and
its `run_launch` hook in `jailbox`, including `bring_up_sandbox`'s
`pre_build_hook` plumbing. Neither core nor the frontend emits an automatic
Alpine/VS Code compatibility warning. README retains the explicit requirement
to use VSCodium for Alpine images, the troubleshooting guidance, and the
supported editor/image matrix. The frontend's preflight success certifies the
host editor prerequisites only, not remote image compatibility.

### Editor packages

Editor-server runtime packages remain in core `container/setup.sh` as part of
the generic attached-development wrapper contract. No caller setup-script
mechanism exists; users customize images through their Containerfile.

### Security invariants

Development/proxy hardening, socket isolation, project-external runtime
state, proxy-only egress, and strict pinned SSH remain core-enforced and are
not reimplemented in the frontend. The frontend read-only anchors every
in-project policy input it consumes, matching the existing config-anchor
contract. It trusts project files at invocation start and does not monitor
later host edits; this limit stays in the threat model. Remote session
`HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` variables remain exclusively
jailbox-generated SSH session behavior; the egress allowlist is never copied
into editor settings.

### Acceptance criteria

- All frontend implementation files reside in `host/frontend/` and machine
  implementation files in `host/core/`, with shared public declarations in
  `host/public-api.sh`. Source loading, installer inventory, packaging, tests,
  lint, syntax, and boundary checks cover the migrated layout, including new
  frontend files; installed commands work with that layout.
- Bare `jailbox` follows the eight-step sequence and reaches core only
  through public CLI child processes; the boundary check rejects in-process
  use of core internals.
- The identical composed environment is used for `up` and `connection-info`,
  and unchanged inputs produce an unchanged digest.
  Tests also prove a successful `up` followed by a validation refusal from
  `connection-info` prevents editor launch, without using prior success as a
  substitute for current validation.
- 03.2.02's effective-policy composition contract is integrated and tested:
  hashed hosts match the rendered proxy filter, and in-project config anchors
  participate in both the digest and read-only protection. Editor attachment
  uses `connection-info`'s digest gate and never proceeds after its refusal.
- Shell attachment after filtered editor launch succeeds with identical
  composed environment policy and valid local TTYs; changed policy refuses
  without lifecycle mutation, completing 03.2.09.2's integration handoff.
- Machine commands no longer read any config file; the frontend owns the
  file, `init`, and `--config`, and `--no-editor` preserves the headless
  file workflow.
- The migration removes the superseded adapter and editor-specific core
  branches identified above; no unused parallel implementation or private-core
  forwarding wrapper remains solely to preserve the former organization.
- Initialization works regardless of sandbox state, without Podman, machine
  commands, or core resource inspection. It preserves no-overwrite behavior,
  strict path checks, and safe publication, and leaves sandbox resources
  unchanged, completing the init migration owned by this plan.
- `ssh-config` remains a human command and `connection-info` is the frontend's
  only connection-data source; editor `http.proxy` follows `proxy_url` exactly.
- Equivalent effective allowlists permit healthy sandbox reuse regardless of
  member order or repetition, and generated editor JSON preserves accepted
  connection values exactly.
- No editor launches after any child-command failure. Frontend connection
  tests enforce required-field meanings and order, framing and uniqueness,
  reject malformed/truncated streams, and accept valid opaque trailing fields.
- File input rejects NUL before byte loss. All file-driven child environments
  exclude inherited machine policy, preserve unrelated entries, and emit the
  specified notice without values when inherited policy was ignored.
- Editor and headless switches, and config-file selections, permit reuse when
  composition leaves effective policy unchanged; actual changes still refuse.
- Init suggestions preserve one live assignment and the documented ordering.
  All four gates pass for this implementation.
- Editor launch validation refuses before any machine command runs and names
  every unmet requirement in one refusal. File validation performs no editor
  discovery and delegates machine-policy checks to core validate.
- The explicit file-validation form uses shared parsing/headless composition,
  ignores inherited machine policy, preserves core failure status, and creates
  no resources. Environment-only validate never implicitly reads a config file.
- Image/editor compatibility remains documented, with the automatic
  Alpine/VS Code launch warning and its coupling removed.

## Implementation detail

Within the required directories, choose modules that keep the public CLI calls
easy to audit, and expose no private core lifecycle helpers to the frontend.
The test-fixture mechanisms named above are guidance: reuse the
existing test harnesses and 03.2.07's shared lifecycle matrix rather than
adding parallel frameworks.

Use a consistent representation of the effective host set for proxy rendering
and reuse comparison. Keep JSON string encoding and connection-record parsing
in focused, format-specific helpers; shell quoting is not JSON encoding. Pass
local process arguments as arrays and reuse the same settings interpretation
for generation verification and later inspection. These mechanisms support the
contracts above without introducing a general serialization framework.

Concentrate file parsing, editor selection, and bootstrap-host composition in
their frontend owner. Reuse core policy through public commands rather than
copying lifecycle or attachment decisions into frontend helpers. Shared public
declarations remain the source of interface membership. Share test setup and
recording where useful, but specify expected child-command behavior and policy
outcomes independently of the production composition being tested. Evaluate
simplification by fewer policy owners and dependencies, not by a line-count
target or an additional abstraction layer.
