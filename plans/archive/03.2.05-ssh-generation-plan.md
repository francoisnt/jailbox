# 3.2.05. SSH generation and resume validation

## Intent

### Goal

Make one development-container object one atomic SSH generation.

### Sequence

Implement after 03.2.04 and before 03.2.06. This plan owns creation,
read-only SSH validation, startup validation, and generation cleanup through
stop. Public-CLI resume and running no-op integration depend on 03.2.06,
which owns invoking these checks before convergence mutation or start and
verifying preservation and refusal through the CLI. Network/home attachments
and supporting-resource validation belong to that lifecycle integration;
SSH checks remain owned by the SSH module.

### Behavior

Before container creation atomically prepare fresh client/server pairs,
`authorized_keys`, pin, and client config. The generation exists only with
its container; failure removes only invocation-created artifacts. No-op/resume
preserve identities. Resume validates pairs, pin, config, mount, ownership,
modes, regular non-symlink types, runtime material, and strict checking before
start; it never repairs a surviving generation. Stop ends it and next up rotates
both identities.

Atomicity means complete preparation before container creation and
invocation-only rollback, not a transaction spanning the filesystem and
Podman. On handled creation or startup failure, remove invocation-created
containers that depend on new SSH material before removing that material.
Preserve pre-existing state. If cleanup fails, report the remaining state and
explicit recovery instead of claiming successful rollback. Forced termination
need not run rollback; leftovers obey the same validation and recovery rules.

With no development-container object, surviving complete or partial generation
material is orphaned. Up refuses without overwriting, reusing, or deleting it
and directs stop then up, subject to 03.2.06's home-aware recovery precedence.
Unrelated runtime files alone do not constitute an orphaned SSH generation.

Successful stop removes generation material after removing its development
container, including partial or orphaned material when the container is already
absent. Cleanup is repeatable and configuration-independent, preserves unrelated
runtime files, and respects existing inspection-failure and home-retention
rules. Failed container removal must preserve that container's generation.
Clean continues to remove all project runtime state.

Before starting a stopped container, validate persistent host material and
inspect configured mounts and dependencies, including expected network/home
attachments and supporting resources. Validate generated config, matching
client/server pairs, authorized keys, pin, mount source and read-only settings,
without printing key contents. Pre-start checks do not require nonexistent
tmpfs contents. The entrypoint validates material visible through its mounts
at startup; normal SSH readiness then proves strict pinned authentication.
Running reuse also requires validation and readiness through 03.2.06.

Client private key, pin, and config stay host-only. Mount only server material
and authorized keys read-only. Preserve `--userns=keep-id` for StrictModes;
mutable daemon state such as `sshd.pid` uses the `/run` tmpfs. Entrypoint
validates and starts sshd but never mutates authentication files. Container
roots, capabilities, no-new-privileges, and socket isolation remain unchanged.

In the container's UID mapping, the authorized-keys file and every parent
directory through `/` must be owned by root or the runtime user and must not
be group- or other-writable. The server private key must be readable by sshd
and have no group or other permission bits. Validate these properties without
repair, including parent directories; a read-only mount alone does not make
unsafe ownership or mode bits acceptable.

Any future user-namespace change must provide equally strict ownership and pass
the same runtime assertions. Pairs are created once per container generation,
not per launch. The sandbox may read its server key for sshd but cannot use it to
authenticate to the host.

### Tests and documentation

Portable/runtime coverage proves rollback, preservation, rotation, all damaged
state failures, read-only mounts, absent client state, ownership/modes, and
strict pinning. Incompatible ownership fails readiness without chmod/chown or
relaxed StrictModes. Update setup, entrypoint, runtime rationale, SSH units, and
runtime tests.

### Acceptance criteria

- Each new container has fresh identities; resume preserves and validates them.
- Handled creation failure leaves no partial new material when rollback
  succeeds; cleanup failures identify leftovers and recovery.
- Orphaned complete/partial material refuses up without mutation; repeated
  stop removes it while preserving unrelated runtime files and applying stored
  home retention. Stop then up restores service with fresh identities.
- Container-removal failure preserves its generation. Failure cleanup removes
  invocation-created dependent containers before their authentication material.
- Validation rejects missing, altered, mismatched, symlinked, wrong-type,
  wrong-owner, and wrong-permission material without repair. Persistent checks
  work while stopped; startup checks validate the mounted material.
- StrictModes works through keep-id without writable server or mounted client
  secrets.
- Every connection enforces strict pinned host-key checking.
- 03.2.06 owns public-CLI no-op/resume integration, validation before mutation
  or start, orphan refusal and home-aware recovery, and broader resource
  rollback. Its tests prove preserved identities and non-mutating refusal.
- 03.2.07 extends coverage with independently constructed interruption and
  damaged-state fixtures, including forced termination without rollback.

### Non-goals

- Resume rotation/repair, automatic orphan cleanup during up, lifecycle locking,
  a cross-system transaction, or moving SSH out of core.

## Implementation detail

### Existing implementation migrations

- Replace `setup_ssh_keys` in `host/ssh.sh`, which deletes and recreates launch
  state, with creation and read-only validation paths. Replace
  `pin_ssh_host_key`'s post-start discovery with pin preparation from the new
  server public key before container creation. Update `bring_up_sandbox` in
  `jailbox` accordingly; 03.2.06 owns removing the absence guard and wiring reuse.
- Extend `stop_jailbox` in `host/container-runtime.sh`, including its early
  return when no Podman resources are removable, to clean generation material.
  `SSH_DIR` also contains generated `gitconfig`; do not delete the whole
  directory as generation cleanup.
- Update the early `stop` dispatch in `jailbox`: it returns before
  `initialize_launch_state`, so `initialize_ssh_state` currently never runs
  and the SSH path variables remain empty during stop. Initialize SSH paths
  before cleanup using the project identity already established by
  `initialize_project_names` (`PROJECT_HASH` and `PROJECT_STATE_ROOT`). Keep
  this independent of configuration loading and the other launch initializers.
- Replace the writable server-material mount and separate
  `/etc/ssh/jailbox_authorized_keys.source` mount in `start_jailbox_container`
  in `host/container-runtime.sh` with read-only prepared authentication material.
- Remove authentication-file copying, chmod, deletion, and server-key generation
  from `container/entrypoint.sh`. Replace its writable-directory requirement
  and best-effort metadata checks with non-mutating startup validation.
- Update `container/setup.sh` to locate the PID file outside the read-only
  authentication mount and rewrite comments about per-launch key generation.
