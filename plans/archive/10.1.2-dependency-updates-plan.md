# 10.1.2. Dependency updates

## Intent

Implement this plan before the other active plans. It stands alone; its
number only places it first.

### Goal

Keep dependencies current, keep one authoritative place for each pinned
version, and flag compatibility problems that affect users early, while
every change to `master` goes through a reviewed pull request.

- Maintainers prepare updates on their own checkout with repository scripts
  and submit them as ordinary PRs, so the normal gates test each one.
- A release is refused while any tracked dependency is out of date.
- A daily run tests the newest release against new editor versions, because
  that is what users run, and records the result.
- Automation never commits to `master`. It writes only tags, GitHub
  Releases, and a data-only `compatibility` branch.

### Updates

An update is one dependency moving to its newest version:

| Update | Pinned in | Newest means |
| --- | --- | --- |
| `CODE_VERSION`, `REMOTE_SSH_VERSION`, `OPEN_REMOTE_SSH_VERSION` | `versions.env` | newest stable release (one update each) |
| `CODIUM_VERSION` with `CODIUM_COMMIT` | `versions.env` | newest stable release and its build commit (one update) |
| `BASE_IMAGE_DEBIAN`, `BASE_IMAGE_ALPINE`, `BASE_IMAGE_FEDORA` | `versions.env` | newest stable series, by today's Docker Official Images rule (one update each) |
| `GO_SERIES` | `src/go.mod` `go` directive, mirrored in the root `Containerfile` | newest stable Go series |

An update is written as space-separated `KEY=VALUE` pairs: one pair for most
updates (`BASE_IMAGE_DEBIAN=debian:13`, `GO_SERIES=1.28`), both pairs for
VSCodium (`CODIUM_VERSION=1.143.17232 CODIUM_COMMIT=c072…`). A list of
updates concatenates them, each key at most once. Each key accepts only its
own strict value format; values are data and are never evaluated as shell.

- One script lists the pending updates for a checkout, one complete update
  per line, with VSCodium's build commit read from its release package.
  With `--check` it fails when any update is pending, when a lookup fails,
  or when the pinned `CODIUM_COMMIT` does not match the pinned VSCodium
  package.
- One script applies a list of updates: it writes the pins, regenerates the
  files built from them, and restores the tree on any failure. It refuses to
  run while those files have staged or unstaged changes.
- `just update` applies every pending update in one step.

### Tested commits

The pins decide the tested versions. Gate runs no longer accept per-editor
version overrides. Releases keep building and testing with the newest patch
of the Go series, and gate reuse keeps requiring that exact Go release. Gate
reuse counts only the full gate workflows; the daily release check neither
proves nor blocks reuse.

### Release

Before using any test result or building its package, the release runs the
`--check` above and stops if it fails, naming the pending updates and the
command that prints their full values. Otherwise it proceeds as today on its
starting commit. A manual release starts only from the default branch. After
publishing, it records its `release` row in the compatibility history.

### Daily release check

- Tests the newest published release: the highest version with a `release`
  row in the history. Only the editor gate runs: editor versions affect
  nothing else, and the other gates passed for that tag at release.
- The gate's steps come from the tag's `tests/ci/editor-gate.sh`, which
  applies the requested updates, installs the editors, and runs
  `tests/run editor`. Every editor gate run uses it. Its path, subcommands,
  and update arguments are the interface `master`'s workflow calls on older
  tags, so they stay stable. The check starts with the first release that
  contains the script.
- Skips a tag and editor version set that already has a `pass` or `fail`
  row; `error` rows do not suppress retries.
- `fail` means an editor's test step failed, and failed again when rerun in
  the same job. A failure before the tests start, a failure that does not
  repeat, or a missing result is `error`. Image building inside a test step
  counts as part of the test. The two editors run in parallel, and each
  result comes from the latest attempt of its own editor's job: a rerun that
  stops before producing a result counts as `error`, never as an earlier
  attempt's result.
- A tag whose Go series is unsupported records one `fail` with its own issue
  saying a new release is needed, not that an editor failed; the tag is not
  checked again.
- A `fail` files an issue before its row is recorded. A result that is
  already recorded files no issue and records nothing; a rerun after a failed
  recording may file a duplicate issue, which is accepted. Issues are only
  created, never searched or closed by automation; each names the row to
  delete to retry.
- A failed check blocks nothing; shipping a new release is the fix.
- Scheduled and manual runs start only from `master` and never overlap.

### Compatibility history

- The history lives on the `compatibility` branch, which has no shared
  history with `master` and holds only data: `releases.csv`, and the frozen
  `master.csv` of earlier full-gate runs. `master` no longer contains the
  `compatibility/` directory.
- `releases.csv` columns, in order: `target`, `kind` (`release` or
  `editor-check`), `commit`, `tested_at`, `result` (`pass`, `fail`, or
  `error`), the eight version columns from `versions.env`,
  `RUNTIME_BASH_VERSION`, `RUNTIME_PODMAN_VERSION`, `run_url`. Existing rows
  become `release` and `pass`. A `release` row has every field; an
  `editor-check` row leaves unobserved fields empty.
- The release recorder and the daily check's report job are the only
  writers. A write lands only on the branch head it started from, retries
  when the branch moved, and fails on any other rejection. Writers fail
  rather than create the branch when it is missing.
- Reporting runs from `master`'s scripts, so the format and issue rules stay
  current.

### Write access

Jobs that run tested code stay read-only and keep no credentials in their
checkout: the gates and the daily check with its third-party editors. Only
the release write jobs and the daily report job get write access, and none
of them writes to `master`.

### Removed behavior

- The Go-support, base-image, and editor pin-advance jobs in
  `.github/workflows/canary.yml`, which becomes the daily release check in
  `.github/workflows/release-check.yml`; its issues use the `release-check`
  label.
- `scripts/bump-base-image.sh`, `scripts/canary-base-images.sh` (its
  stable-series lookup moves to `scripts/lib/base-images.sh`),
  `scripts/canary-report.sh`, and `scripts/lib/record-compatibility.py`.
- `scripts/resolve-latest-versions.sh`, whose editor lookups join the other
  newest-version lookups in one script, and `tests/unit/canary-versions.sh`,
  renamed for that script.
- The `code_version`, `codium_version`, `remote_ssh_version`, and
  `open_remote_ssh_version` inputs of `.github/workflows/test-gates.yml`, and
  the `JAILBOX_*` editor overrides read by `tests/ci/setup-linux.sh` and
  `scripts/record-compatibility.sh`.
- `PINS_LAST_VERIFIED` in `versions.env` and the "Last verified" line of the
  generated tested-matrix block; Git history dates each update.
- `compatibility/releases.csv` and `compatibility/master.csv` on `master`.
- `tests/unit/base-image-updates.sh` and `tests/fixtures/base-image-updates/`;
  their generator and stable-series coverage moves to the new tests.

### Non-goals

- Automatically opened update PRs. They fit the PR rule but need a token
  other than the workflow's own, since its PRs do not start the gates.
- Maintenance branches for hotfixes.
- Release notes, which `10.1.3-release-notes-plan.md` covers.

### Documentation

Update every description of the old flow: the generated tested-matrix text
(and so `docs/development.md`, including its history links),
`CONTRIBUTING.md`, `ARCHITECTURE.md`, `AGENTS.md` (the Go series, the CI
gates, and the rule that every change to `master` goes through a PR),
`plans/supported-versions.md`, and comments in `versions.env`,
`.github/dependabot.yml`, and the changed scripts.

### Rollout

The `compatibility` branch must exist, seeded with the current history in
the new format, before the first release or daily run that uses this code.

### Acceptance

Unit tests with fixture repositories cover:

- applying each key, invalid keys and values, refused edits, and an
  unchanged tree on failure;
- listing pending updates, failed lookups, and `--check` refusing outdated
  pins, failed lookups, and a mismatched VSCodium build commit;
- the daily check: target selection from `release` rows, the skip rule,
  retry after `error`, one Go-support `fail` per tag and no later checks of
  it, issue filing before recording, no second issue for a recorded result,
  a missing editor result, and a missing history branch;
- recording: rows land on the `compatibility` branch, retries without
  duplicates when it moves, a rejection fails once, and `master` never
  changes;
- release reuse ignoring the daily check;
- no automation searching or closing issues.

`tests/unit/release-workflow.sh` asserts the workflow wiring, including the
release's pin check and which jobs hold write access. CI gates this depends
on: all five, since every gate job's setup changes.

## Implementation detail

Guidance only; the implementer chooses the mechanisms.

- `go-version.sh` exits 1 both for an unsupported series and for a failed
  lookup; give "unsupported" its own status.
- `tests/run` can report through a step output whether a suite failed, so
  the workflow tells test failures from setup failures.
- Push with `--force-with-lease=refs/heads/compatibility:<base>` so a
  rewound branch is rejected too; after a rejection, fetch to tell a moved
  branch from other rejections.
