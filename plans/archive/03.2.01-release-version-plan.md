# 3.2.01. Release version stamping and bump policy

## Intent

### Goal

Stamp each build with an exact version, expose `jailbox --version`, and make
pre-1.0 bump suggestions compatible with downstream version-range pinning.

### Sequence

Implement after 03.1 and before the digest, which hashes this exact version.

### `--version` contract

Output is one line on stdout and nothing else: the name `jailbox`, a single
space, and a version token. A released build's token is its exact version in
`MAJOR.MINOR.PATCH` form, without the tag's leading `v`. The number below shows
the shape; it is not a value to reproduce:

```text
jailbox 0.8.0
```

A build carrying no stamp reports one documented development token instead.
That token is part of this external surface: it is constant for a given build,
it cannot parse as `MAJOR.MINOR.PATCH`, and a consumer can tell the two apart
without further context.

The stamp alone decides which spelling a copy reports — a well-formed stamp
yields its value, an absent stamp yields the development token — so this holds
for every build state, including an install made from a source checkout, which
carries no released artifact and therefore keeps reporting development.

`--version` is configuration-independent, non-mutating, requires no Podman, and
never reads project configuration. It validates the stamp before printing it
and before any other consumer reads it: only `MAJOR.MINOR.PATCH` is accepted,
and a present-but-malformed stamp fails closed. The command exits non-zero
with a diagnostic on stderr and writes nothing to stdout, so a consumer never
sees a partial or substituted value.
That validation is what lets 03.2.02 hash the version as a field that is
control-character-free by construction.

`--version` and the digest consume the same value: the token this command
prints is exactly the `EXACT_VERSION` field of 03.2.02's digest stream.

### Stamping and packaging

Tarball construction stamps a version file into the release tree from the
`vMAJOR.MINOR.PATCH` already validated by `scripts/build-tarball.sh`, without
rewriting tracked source or consulting Git at runtime. The stamp is a build
artifact and never tracked source: packaging fails rather than shipping a stamp
it did not write itself, so a committed or leftover value can never reach a
release. Install and update retain the stamp of the tree they install.

Before creating or pushing the release tag or publishing release assets,
validate the final tarball: the archived stamp must equal the selected release
version without its leading `v`, and the command extracted from that tarball
must report exactly `jailbox VERSION` with that same value. Missing, malformed,
or mismatched stamps and command output block the release. Publish the exact
validated artifact; do not rebuild it after validation. The published checksum
file and the `latest` alias must be the ones produced by that same validated
build, not regenerated from a later one.

Final-artifact construction and validation must succeed before tag creation.
All three release gates remain prerequisites to tagging and publication.

Source and released builds therefore report different values and produce
incompatible digests, which is intended: version binding prevents a build from
resuming resources created under different hardening rules.

### Bump policy and manual selection

The public API comparison includes the new `--version` flag.

Before 1.0, adding a configuration key or CLI flag is patch; removing or
changing one is minor. After 1.0, normal major-version compatibility applies:
additions are minor while removals and changes are major. jailbox's release
version is the sole API/schema version.

Before 1.0, downstream consumers — external orchestrators, and a standalone
frontend if the deferred split is revived — pin a minor-line range such as
`>=0.8.0,<0.9.0`, in the same illustrative numbering as the output above.

Public review covers environment keys, `config-schema`, machine schemas,
commands, and the configuration file's accepted-value grammar. The generated
comparison diffs declaration names, so a grammar change — tightening included,
since previously valid files begin to fail — is classified by that review
rather than by the diff.

At release time, a maintainer can request a higher bump through
`scripts/release.sh --bump patch|minor|major` or the release workflow's manual
input. Omitting the override keeps automatic selection. The requested level
is a minimum: both local and CI selection use the higher of the automatic
and requested levels, ordered patch < minor < major. An equal or lower request
never reduces the automatic requirement; invalid values fail before dispatch
or publication. Review identifies breaking changes invisible to the name
comparison, and the maintainer requests the appropriate higher level.

The local release flow displays the automatic suggestion and lets the
maintainer accept it or select a higher level before final confirmation.
`--yes` accepts the selection without prompting; `--dry-run` and
`--print-version` remain non-interactive and honor an explicit override.
A major request before 1.0 selects `v1.0.0`. Preserve `--first-major` as the
existing pre-1.0-only spelling for that choice. Reject simultaneous first-major
and explicit bump selections through both the script's arguments and the
workflow's manual inputs, before dispatch or CI version selection respectively.

The override travels with the individual release request to CI, which applies
it alongside its own automatic classification at the commit being released.
Both the script's request-tag dispatch and the workflow's manual dispatch
must support it. A subsequent request without an override uses automatic
selection. Existing release requests without an override remain valid.

Ephemeral request tags must never match the version-tag glob
`v[0-9]*.[0-9]*.[0-9]*`, so they cannot participate in release-version discovery.
Every supported request-tag encoding must trigger the release workflow.

### Tests and documentation

Portable tests cover dispatch, both spellings, the fail-closed malformed stamp,
packaging's refusal of a stamp it did not write, the install/update lifecycle
retaining a stamp and tolerating its absence, API classification, and suggested
bumps before and after 1.0. Cover manual selection, override propagation through
both dispatch paths, equal and lower requests, invalid inputs, non-interactive
modes, first-major compatibility, conflicting selections on both entry paths,
and a later request without an override. Assert that supported request tags
cannot match the version-tag glob and are covered by the workflow trigger.
Document both version spellings, the bump and pinning policy, and interactive
and explicit release-time bump selection.

Portable tests also cover final-artifact validation against the selected
release version, including rejection of missing, malformed, and mismatched
stamps or command output. Verify that the release workflow orders this
validation before tag creation and publishes the validated artifact.

### Acceptance criteria

- A released build reports its stamped value and an unstamped build reports the
  documented development token, both in the documented one-line form.
- A malformed stamp fails closed instead of reporting a value.
- Packaging refuses a stamp it did not write, and install and update preserve
  the stamped value.
- The selected release version, final tarball's stamp, and extracted command's
  output agree before any release tag is created or pushed; publication uses
  that same validated artifact.
- Automatic declaration-name comparison suggests patch for additions and minor
  for removals before 1.0; after 1.0, it suggests minor for additions and major
  for removals.
- Maintainers can raise the bump at release time, and the choice reaches CI
  through either dispatch path without lowering its automatic requirement or
  affecting subsequent requests.
- For breaking changes invisible to the name comparison, a maintainer-selected
  minor bump before 1.0 or major bump afterward enforces the compatibility
  policy through both release entry paths.

### Non-goals

- Registry lookup, a separate protocol version, dependency installation, or
  coupled product versions.

## Implementation detail

Extend the argument parsing, selection, confirmation, and request dispatch in
`scripts/release.sh`, including `suggest_bump`. Declare `--version` in
`host/public-api.sh` and update its policy comment, which states the superseded
pre-1.0 rule. Keep local and CI bump policy shared.

Migrate `.github/workflows/release.yml`, which currently creates and pushes the
release tag before building the tarball, to construct and validate the final
artifact before tag creation. Update its manual inputs, request-tag triggers,
and request handling together so every supported request carries its chosen
minimum bump through CI selection and retains request-tag cleanup.

The request encoding and prompt mechanics are implementation choices within
the tag-namespace, selection, and propagation constraints above.
