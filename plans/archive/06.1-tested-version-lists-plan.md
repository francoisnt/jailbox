# 6.1. Tested version lists

## Intent

Keep a list of successful tested version combinations for master and each
release, using the existing full test runs. Store the lists in
`compatibility/master.csv` and `compatibility/releases.csv`, linked from README.

Each row names its target, tested commit, test date and CI run, editor and
extension versions, VSCodium server commit, development-image tags, and the Bash
and Podman versions observed by the Linux runtime gate. Append only after all existing gates pass;
release rows also require successful publication. Repeated reports of the same
combination and commit must not duplicate rows or discard previous results.

Keep existing scheduling, version selection, pin updates, test execution and
publication behavior. This is passive history: it does not authorize reuse,
select new dependency candidates, or schedule tests of older releases. Historical
passes do not establish compatibility for other mixtures, today's master, or
macOS runtime. Do not invent entries for past runs without recorded versions.

## Implementation detail

Expose runtime versions from the existing shared gate. Add a small append step
to canary and release workflows, keeping tested checkout data separate from the
current master branch receiving the CSV update. Preserve unrelated changes if
master moves. Validate CSV input and test deduplication and failure handling.

Run development checks, affected suites, generated-file checks, and workflow
validation. Verify protected workflow replacements in a copied checkout.
