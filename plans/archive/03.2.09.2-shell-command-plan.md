# 3.2.09.2. jailbox shell

## Intent

### Goal

Open one interactive login shell in an already-running compatible sandbox.

### Sequence

Requires `03.1-environment-only-configuration-plan.md` and
`03.2.09.1-exec-command-plan.md`, reusing its preflight, transport, and
`03.2.09-connection-info-and-validate-plan.md` validator rather than duplicating
digest/lifecycle/network/editor behavior.

Editor-filtered attachment depends on 03.2.11's policy composition migration.
That plan owns verification that shell attaches after filtered editor launch
with identical composed policy and refuses changed policy without mutation.
Keep shared attachment checks intact until that integration lands.

### Behavior

`jailbox shell` consumes canonical environment policy, validates every
policy-bearing resource, and either attaches or refuses without lifecycle
mutation. It belongs to the machine layer and is also directly usable by
humans with the same effective environment policy used at launch. It does not
read `jailbox.conf`, accept `--config`, or reconstruct editor-added policy.
Attachment uses generated strict-host-key SSH with a remote PTY.

Require both local stdin and stdout to be TTYs before attaching. The fixed
remote command must `cd` to `/home/jailbox/project` and then explicitly open
interactive login Bash; failed `cd` aborts instead of silently opening in
home. Supply that initial directory and the SSH session environment, including
jailbox-owned proxy variables, before login startup files run. Bash reads
startup files inside the sandbox, not the host's profiles. Respect their normal
customizations, including changes to PATH, directory, and proxy variables;
the initial directory and environment are not enforced after startup files run.
No command arguments are accepted.

Use ordinary interactive SSH terminal behavior: terminal Ctrl-C interrupts
the foreground remote command, terminal resizing reaches the remote PTY, and
normal exit or disconnect restores the local terminal. Preserve SSH behavior
for signals sent directly to the local client, distinct from terminal Ctrl-C.
Propagate the remote exit status; 255 remains ambiguous with SSH failure.
Disconnecting does not guarantee termination of every remote process.

Require attach tooling but no Base64, cksum, editor, file config, or launch-only
initialization. Missing/incompatible/unhealthy states use the validator's
recovery and 03.2.09.1's current-side no-values digest diagnostic, and never
launch or repair resources or prompt for permission to do so. Recovery is an
explicit caller action; an absent sandbox can be launched with `jailbox up`
before retrying `jailbox shell`.

Declare `shell` as a non-lifecycle command in `host/public-api.sh`, with the
required help and handler mappings. Usage and public-API comparison derive
membership from that declaration. Reject trailing arguments. Its handler
reuses 03.2.09.1's attach validation without its exec-only Base64 requirement
or wrapper-build `cksum`.

### Tests and documentation

Portable/runtime tests cover parsing, real TTY/login behavior, cwd/environment,
resize/signals/status/disconnect, all shared-validator refusals, filtered proxy,
and no lifecycle mutation. Explicitly cover either local stream not being a
TTY, failed remote cd, absent/stopped/unresponsive sandbox, no editor, supported
SHA-256 without cksum, proxy liveness, and public API/help output. Verify
rejection of `--config` and trailing arguments, independence from host profiles
and project config files, and refusals without launch prompts.

Login tests prove the shell is interactive and a login shell, startup files
observe the initial project directory and proxy environment, and their directory
and environment customizations remain effective. Terminal tests distinguish
terminal Ctrl-C from direct local-client interruption, exercise initial size
and resize propagation, check terminal restoration after normal exit and
disconnect, and verify exit statuses including 255.

README distinguishes login `shell` from non-login `exec` and presents the
lifecycle command table as this plan leaves it; 03.2.11 revises it again.
Document environment-only attachment, explicit launch/recovery, sandbox-local
startup files and their customization boundary, and SSH disconnect/status
limits. Humans may use their editor's terminal or invoke shell with matching
environment policy; no file-configured human shortcut is added.
Run `tests/run portable`, `tests/run runtime`, and `tests/run matrix`.

### Acceptance criteria

- A compatible running sandbox opens the expected interactive login shell.
- Every validator failure refuses before opening the interactive shell and
  preserves state. Host-side checks precede live validation; the latter may
  use SSH as required by 03.2.09.
  Focused refusal tests enforce 03.2.09's diagnostic facts and recovery rules,
  including required data-loss warnings and manual-fix or inspection-error cases.
- This plan owns shell integration into 03.2.07's shared runtime matrix. Extend
  its existing cases with command-level assertions for every constructed state
  and recovered state, providing valid local TTYs so terminal preflight cannot
  mask lifecycle validation. Compatible running states open the login shell;
  other states refuse before attachment without lifecycle mutation. Reuse the
  shared expectations rather than defining a separate matrix. Follow 03.2.09's
  bounded snapshot and sample-maintenance requirements, adding shell-specific
  non-mutation evidence and accounting for the added assertion workload in
  timing comparisons.
- This plan owns command-level verification of the shared attachment-time
  digest behavior inherited from 03.2.09 and 03.2.09.1: missing explicit or
  implicit Containerfiles cause stale-sandbox refusal before transport without
  building or mutation, `DEV_IMAGE` bypasses discovery, and incompatible
  inventory members outside the requested network mode refuse attachment.
- Ordinary interactive SSH behavior meets the terminal and status contract
  above, without promising termination of every remote process on disconnect.
- Sandbox-local login startup files run with the initial project directory and
  session environment, and their subsequent customizations are respected.
- Shell consumes only environment policy and never prompts to launch or repair
  a sandbox; refused attachments leave lifecycle and managed runtime state intact.
- Both stdin and stdout must be TTYs, and remote cd failure never opens a shell
  in the wrong directory.
- Shell requires neither Base64, cksum, nor an editor.

### Non-goals

- Non-interactive commands, automatic launch/repair, editor behavior, or a
  separate compatibility mechanism.
- Argument passing, a non-TTY fallback, or a file-configured human shortcut.

## Implementation detail

Reuse the existing attachment preflight and validator boundary, keeping
exec-only argument encoding out of shell preparation. A fixed remote command
can change to the project directory and then replace itself with interactive
login Bash, stopping on directory-change failure. The SSH invocation can use:

```sh
ssh -F "$SSH_CONFIG" -tt -- "$SSH_HOST" <remote-command>
```

Reuse existing test fixtures and matrix expectations; provide valid local TTYs
for attachment checks and bound terminal-test waits so failures cannot hang a
gate.
