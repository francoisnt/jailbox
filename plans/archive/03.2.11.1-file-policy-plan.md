# 3.2.11.1. Prepare frontend file policy and initialization

## Intent

### Goal and place in the sequence

Read 03.2-machine-boundary-plan.md and 03.2.11-editor-frontend-plan.md first.
Prepare the frontend-owned file parser, policy composer, and safe initialization
behavior. This is the first implementation step in the frontend series.
The public-command switchover belongs to 03.2.11.4; this step does not yet
change which configuration source the existing commands consume.

The result is a tested frontend implementation under `host/frontend/` that
03.2.11.4 can wire into bare launch, `--no-editor`, explicit file validation,
and `init`. The existing path remains operational until that switchover.
No new external command or temporary compatibility surface is introduced here.

### File grammar and policy composition

The strict parser survives as frontend code and the file remains the
frontend's permanent human surface. Environment callers are unaffected. The
parser keeps both of its current value rules — no whitespace and no shell
metacharacters — and adds rejection of ASCII control characters (bytes
0x01–0x1F and 0x7F). The combined rule rejects a strict superset of what
03.1's environment contract rejects, so every value the file admits is
already a legal environment value and the file-to-environment mapping is
byte-clean by construction. Reject NUL bytes anywhere in the selected file
before parsing can silently discard them, naming the selected file and the
line where determinable; file input, unlike environment values, can contain
NUL. The existing whitespace rule already covers TAB and the newline family; retain
ordinary line delimiters and permitted formatting whitespace in the file.

The composer implements the file-policy requirements in the complete launch
sequence of 03.2.11.4-frontend-cutover-plan.md: trusted file selection, strict parsing,
config anchors, duplicate handling, environment namespace replacement, unrelated
environment preservation, and notices without values. Editor selection and its
bootstrap-host contribution are supplied by 03.2.11.2; headless composition
uses no editor contribution. Public declarations determine configuration-key
membership; new declarations must propagate or fail a complete mapping check.

### File validation and initialization contract

The following describes the final public behavior. This step prepares and
unit-tests its frontend implementation; 03.2.11.4 owns activation and removal
of the listed old implementation artifacts.

This step prepares 03.2.09's file-validation handoff; 03.2.11.4 activates it.
`jailbox --config PATH validate`
uses the frontend's existing strict parser, validates file-only keys, and
composes the same machine environment and protected config anchors as
`--no-editor`. It invokes `jailbox validate` as a child without `--config` in
the composed machine environment specified in 03.2.11.4, including its notice
and preservation rules. Inherited `JAILBOX_CONFIG_*` values cannot affect this
explicit file-validation path. `jailbox validate` without `--config` remains
environment-only, even when a jailbox.conf exists. Document
`jailbox --config jailbox.conf validate` as the default-file check.

No editor discovery, bootstrap-host addition, profile generation, up, or
connection-info call occurs during file validation. Its success checks the
file's headless machine policy and local inputs, not editor readiness or
existing sandbox compatibility. Propagate core failures and emit no frontend
success after a failed child; syntax failures name the selected file and line.
Reuse the parser and composition helpers, not a second validation implementation.

`init` creates the minimal configuration independently of sandbox state. It
requires neither Podman nor any machine-command call, including `status`.
Preserve no-overwrite behavior, strict path checks, and safe file publication:
existing destinations, including symlinks and directories, must not be
overwritten, and failed preparation or publication must not leave partial
configuration or report success. Creating the file does not mutate existing
sandbox resources; later launches enforce policy compatibility through core.

The init migration originally assigned to 03.2.11 by archived 03.2.06 and
03.2.08 is prepared here and activated in 03.2.11.4. At activation, remove
`run_init`'s
`require_sandbox_absent` call, Podman prerequisite, and core identity
initialization in `jailbox`, and remove the obsolete helper from
`host/container-runtime.sh`. Migrate `init_project_config` from
`host/common.sh` into the frontend while retaining its publication safeguards.
In `tests/unit/init-config.sh`, replace `test_init_needs_podman_only` and its
"init still requires podman" assertion with a regression proving successful
initialization without Podman. Remove the obsolete
`tests/fixtures/init-podman.sh` fixture and its setup references. Update both
README.md passages: remove the `status` section's "initialization requires
successful `absent` plus newline" contract and the troubleshooting row requiring
absent containers before `init`.

`init` also seeds advisory protection suggestions. The fixed candidate set,
in output order, is `.env`, `.git/hooks`, `AGENTS.md`, `CLAUDE.md`, and
`.github/workflows`. List each existing candidate as a commented path, without
an assignment, and explain that selected paths should be added comma-separated
to the single live `READONLY_PATHS=` assignment. Detection checks path existence
without reading candidate contents. Absent candidates are skipped without
stubs, nothing is enabled, and the effective created policy remains minimal.
Enabling suggestions must leave one assignment rather than require duplicate
keys or inline comments, neither of which the parser accepts. Document the
candidate set and order. Interactive and flag-driven initialization remains
backlog work.

### Verification and handoff

- Unit tests cover the file grammar, control characters and NUL before byte
  loss, selected/default path rules, anchors, duplicate handling, and composed
  environment behavior. Test new declared keys propagating or failing an
  explicit missing mapping rather than silently disappearing.
- Unit-test initialization publication, no-overwrite behavior, suggestions,
  candidate order, and unchanged minimal effective policy. Candidate detection
  checks existence without reading contents. Test permission-sensitive cases
  under both `0022` and `0002`.
- Verify the prepared file-validation path delegates to a stub public `validate`
  command without editor or lifecycle activity; failures prevent success output.
- Run `tests/run portable`. Keep existing public workflows and their applicable
  gates passing; do not replace their assertions with future behavior early.
- 03.2.11.4 must activate these paths, run real core-child validation without
  Podman/SSH, remove the old init state guard and parser/adapter paths, and
  migrate init fixtures and README contracts named above. Its acceptance
  requires these exact behaviors through the real CLI.
- 03.2.11.5 verifies the completed composition and initialization contract
  across the integrated gates. Passing helper tests here is not that handoff.

### Acceptance criteria

The prepared frontend preserves every file/init contract above and passes
its focused portable tests. It has no dependency on private core globals,
Podman, or sandbox state. Remaining activation work is assigned explicitly to
03.2.11.4, with no public behavior claimed before activation.

## Implementation detail

Separate parsing/composition from command activation so the change can be
reviewed without a simultaneous dispatch rewrite. Reuse existing publication
and parsing logic where sound, adapting it to frontend-owned state. Avoid a
second machine-policy validator: core `validate` remains its public owner.
Temporary coexistence with the current implementation ends in 03.2.11.4.
