# 3.2.07.1. Targeted Bash execution safety

## Intent

### Goal and sequence

Fix the concrete failure-propagation, temporary-file cleanup, and variable-scope
findings from the audit at commit `ccdfa53`. Keep successful public behavior,
configuration, resource identity, security policy, and recovery semantics intact;
operational failures must no longer become success or authorize dependent work.

Read `03.2-machine-boundary-plan.md` first. Implement after 03.2.07 and before
03.2.08. This is a bounded hardening step in the existing release unit, not a
redesign of Bash orchestration.

### Required outcomes

#### Required discovery fails closed

- Installer target resolution must fail when parent creation or canonicalization
  fails; it must not substitute another target. Failure to inspect an unmanaged
  target must refuse replacement, never classify it as empty. Do not move or
  remove the target or alter its launch symlink after either refusal.
- Project-name derivation must propagate failed slug construction rather than
  silently switch to a hash-only name. A genuinely empty slug from successful
  sanitization remains valid, and successful names remain byte-for-byte unchanged.
  No resource operation may follow failed identity derivation.
- Public-API comparison must require successful extraction and comparison of
  both inputs before emitting `added`, `removed`, or `unchanged`. Producer errors
  must return failure without a success classification, including when they
  occur behind process substitutions or before a later successful pipeline.
  Preserve support for historical declaration layouts and intentionally absent
  historical arrays; distinguish those cases from a failed required read.
- Release preflight must not treat failed working-tree or tag inspection as a
  clean tree, an empty tag inventory, or evidence that no major release exists.
  Callers must distinguish an inspection error from a valid negative answer.
  No version-success output or dispatch may follow those required failures.
  Preserve the existing explicitly advisory remote-tag-refresh fallback.

#### Generated files have bounded cleanup

The minimal Git identity file and local editor settings must be prepared fully
before publication. Failed creation, writing, permission setup, or publication
must return failure and remove that operation's temporary artifact when removal
is possible. Cleanup failures must be reported while preserving failure status.
An existing destination must not be removed or replaced before a complete new
artifact is ready. Preserve existing successful contents, permission policy,
and the absence of a generated Git identity when none is available.

These operations must preserve the caller's working directory, shell settings,
and traps on both success and failure. Their cleanup must coexist with launch
rollback and must not remove unrelated runtime files or surviving resources.
After failed Git identity preparation, dependent mount/container creation stops;
after failed editor settings preparation, editor launch stops.

The editor migration in 03.2.11 must retain and verify these publication and
cleanup properties when moving the writer into the frontend. That plan owns
JSON encoding and allowlist changes; this plan does not implement them.

#### Targeted mutation helpers retain their failure contract

Home-volume preparation and plain/filtered network setup must stop dependent
work after failed required creation, inspection, policy-file preparation, or
proxy startup, even when the helper is invoked conditionally. Do not report
successful setup merely because a later state assignment succeeds. Existing
retryable subnet allocation and resource-reuse behavior remain intact.

Keep attempted-creation tracking before engine mutations, including operations
that can create a resource and then report failure. Let the existing launch
rollback preserve pre-existing resources and dependencies needed by survivors;
do not undo that tracking to make a failed helper appear side-effect-free.
Validate through the real CLI that failure still reaches the rollback owner and
that readiness success is not printed afterward.

This hardens the identified helper boundaries. It does not make the entrypoint
a supported sourced library or require every host function to be callable in
every possible Bash context. Before adding a conditional call, verify the
affected callee chain instead of wrapping an unchecked sequence in `|| return`.

#### Temporary variables remain private

Image-build command assembly and SSH readiness polling must not overwrite
unrelated caller variables. Preserve intentionally shared selected-image and
SSH state, the existing retry count, and command arguments. Do not add a new
state object or move shared-state setup into subshells to fix local temporaries.

### Acceptance and verification

- Reproduce and fix each audit finding below, distinguishing current executable
  failures from conditional-helper hazards. Add behavioral regressions in the
  existing suites rather than a new harness or test mode.
- For required discovery, cover tool failure with empty and plausible partial
  output. Verify nonzero status, no success result, and no dependent mutation.
  Keep successful empty/absent cases distinct. Release fixtures use isolated
  repositories and a dummy Git identity; never dispatch or publish a release.
- For both generated-file writers, cover success and failures after temporary
  creation, during preparation, and at publication. Verify destination
  preservation, temporary cleanup, caller-trap/settings isolation, and no
  dependent launch. Cover handled interruptions and report cleanup failure;
  do not promise cleanup after SIGKILL or power loss.
- Exercise the targeted mutation helpers through conditional invocation as well
  as the ordinary CLI path. Assert that failed creation prevents later dependent
  engine calls and that normal launch rollback retains the right resources.
- When a fix changes an instrumented operation, review the affected fault
  contract against the required security or recovery role. Preserve independent
  coverage floors and verification that removing a required role fails the gate;
  do not derive expectations solely from the implementation's current trace or
  reduce them merely to obtain a pass. Incidental command counts and spellings
  may change when the replacement still exercises the required failure boundary.
- Verify the temporary-variable fixes preserve caller values without tests that
  merely require particular helper names or a particular shell syntax.
- Set permission fixtures explicitly and verify relevant cases under both
  `0022` and `0002`. Preserve Bash 4.4 host compatibility, the Bash 3.2 installer,
  and the entrypoint's Bash 3.2-parseable version guard. Container POSIX scripts

- Run `tests/run portable`, `tests/run runtime`, `tests/run matrix`, and
  `tests/run editor`: this scope includes host lifecycle, identity, distribution,

- Review README claims for any affected failure/recovery behavior. Do not change
  successful public schemas, flags, defaults, identity, or release bump policy.

  Archive this plan with `git mv` once implementation and required verification

### Non-goals

- A Go migration, broad module restructuring, blanket addition of error checks,
  mandatory subshell conversion, or a general serialization framework.
- Shell-option changes, including enabling `inherit_errexit`.
- Lifecycle locking, concurrent mutations, filesystem race hardening, or a new
  guarantee of atomic installation across crashes. Those are separate designs.
- The JSON/allowlist fixes and frontend separation owned by 03.2.11, or the
  attachment commands and shared validator owned by their existing plans.
- Changes to CI selection, supported Podman versions, container policy, or the
  existing intentional best-effort/advisory checks outside the findings.

## Implementation detail

### Failure mechanisms and shell-option decision

Three distinct mechanisms require explicit checks:

- Bash normally clears errexit inside command substitutions. Without
  `inherit_errexit`, a failed intermediate command can be followed by a successful
  command that hides the failure from the assignment consuming the substitution.
- A surrounding command can discard a substitution's failure status, as in
  `[ -z "$(false)" ]`. Process-substitution failures likewise do not establish
  failure of the consuming command. Check producers before interpreting output.
- Conditional invocation can suppress errexit throughout a function's call
  chain, including subshell functions and command substitutions, even with
  `inherit_errexit` enabled.

Keep shell-option behavior unchanged in this bounded fix. `inherit_errexit` is
available at the host's Bash 4.4 floor but unavailable to the Bash 3.2 installer;
enabling it also changes existing capture behavior beyond the audited sites.
It addresses only the first mechanism and cannot replace explicit checks.
It would make the audited installer path-resolution failure stop on newer Bash,
but that fix is unavailable at the installer's supported Bash 3.2 floor. The
current identity caller's conditional assignment still suppresses errexit with
the option enabled, and the other discovery findings discard producer statuses.
This decision is scoped to this plan; explicit failure checks remain the
standing requirement.

The audit read production orchestration, credential/mount/network handling,
installer and selected release tooling. It did not inspect individual test
implementations. The following were reproduced using short Bash probes against
the current functions, with disposable directories or stubbed external tools.
No real Podman resources, developer Git configuration, or release state changed.

The Git identity writer also starts with `rm -f -- "$gitconfig_file"` before
checking whether Git is available. Remove that premature destination deletion
as part of the publication fix. The current caller only invokes the writer
when the destination is absent, so this is a helper-level preservation hazard,
not evidence of current CLI data loss.

The identity failure changes derived resource names, not the project-path hash.
The CLI can consequently fail to recognize its existing containers, home volume,
and networks; cleanup under the same failure targets the altered names. A false
API `unchanged` result can underselect the required release bump. Failed required
Git status/tag reads can also bypass their respective release preflight checks.
These consequences motivate fixing required discovery before mutation helpers.

The audit found no failure from false guards in the inspected
`[ -n "$x" ] && cmd` sequences followed by another statement. It also found no
`local name=$(...)` declaration masking in the inspected host, installer,
entrypoint, and release tooling; the declaration/assignment rule is preventive
rather than a migration target. The audit changed documentation only and did
not run test gates.

The probe statuses identify injected failures, not new public exit-code promises.
Recheck the named code against the tree before editing; a subsequent change may
already satisfy an outcome. Do not treat a successful gate as evidence that an
unchecked producer status is safe, or a conditional probe as proof that the
current direct CLI call is broken.

### State ownership and functional-style guidance

Apply this distinction to the audited code being changed:

| Kind of state | Treatment |
| --- | --- |
| Temporary values, including loop counters and command arrays | Keep local to the function. |
| Configuration and project identity | Establish during setup, then treat as read-only once finalized for the invocation. Shared reads remain reasonable. |
| Operation state, including attempted creations and rollback inventory | Keep mutable under one clear owner, with explicit updates available to cleanup. |

Prefer pure helpers for policy decisions and transformations where they make
the changed code easier to understand: explicit inputs, a status or well-defined
result, and no state mutation. Keep external inspection and mutation separate
from those decisions, with effects apparent at call sites. Avoid hidden writes
more strongly than shared reads of established configuration. Use an
operation-local scope where it naturally owns temporary work, while preserving
the lifecycle owner's access to the complete rollback inventory.

This is design guidance for the existing findings, not an additional refactor.
Do not eliminate all globals, require Bash `readonly`, force structured state
through text protocols, or extract helpers solely to meet a purity rule. Retain
intentional shared state where it makes Bash simpler and its ownership is clear.

### Suggested implementation groups

1. Fix required producer-status propagation in the installer, identity, and
   release paths. Carry failures through the complete producer chain; checking
   only the final `comm`, `printf`, or assignment is insufficient. Preserve
   legitimate historical API fallbacks and empty slug/tag cases.
2. Give the two generated-file writers a bounded cleanup scope. Subshell
   functions are suitable because their results are published files and status,
   not state assignments needed by the caller. Keep explicit checks inside
   them: a subshell does not restore errexit when called conditionally.
3. Harden the identified home/network helper chains and localize the confirmed
   temporary variables. Preserve ordinary functions for network state and image
   selection. Review adjacent call sites only as needed for correct propagation
   and rollback; do not convert the entire lifecycle to a new execution model.

The existing subshells in `init_project_config`, `create_ssh_generation`, and
the downloader manager's `sync_file` already isolate their operation state.
The existing resource inventory/removal helpers explicitly distinguish absence
from engine errors, and digest serialization captures required producer status.
Use those patterns where appropriate; they are not targets for uniform rewrites.
Installer traps currently belong to a standalone process, so replacing them
solely to preserve a hypothetical sourcing caller is unnecessary.

Keep fixtures within the existing test structure and inspect that coverage in
the implementation session before adding assertions. The audit probes are
evidence of bounded failures, not replacements for the required gates.

For changed fault paths, migrate the relevant entries in
`lifecycle_fault_requirements` in `tests/lib/lifecycle-contracts.sh` and, only
where necessary, their checking in `tests/lib/lifecycle-assertions.sh`.
For example, the current Git identity requirements name removal and multiple
permission-setting operations; retain the protection and publication coverage
without requiring redundant commands after safe preparation changes. Keep
trace/event correspondence and automatic sweeping of newly observed operations.
This is a targeted contract review, not a redesign of the fault harness.

Share fixture setup, isolated identities, recording, and cleanup where existing
helpers fit. Keep expected security and recovery outcomes independently
specified; a production decision helper must not also compute its test's
expected answer. Retain the resource ledger and interruption machinery that
protect the test host and establish recovery coverage.

Use the same understandable prepare/validate/publish/cleanup pattern for the
two file writers, but extract a common helper only if it reduces the concepts
and calling conventions involved. A short repeated pattern is acceptable;
do not build a callback-based transaction framework to remove it. Keep the
installer self-contained and avoid extracting tiny utilities solely to reduce
line count.
