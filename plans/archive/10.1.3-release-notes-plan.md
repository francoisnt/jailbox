# 10.1.3. Generated release notes

## Intent

Implement after `10.1.2-dependency-updates-plan.md` and before the other
active plans. Publish concise notes on every GitHub release so users can see
what changed, whether they need to act, and what CI verified. Starting the
release is the only step required from the maintainer.

### What readers see

- **Highlights.** A few user-facing bullets, with required upgrade actions
  first. When local AI highlights are unavailable, use non-merge commit
  titles for changes to packaged files or their build inputs, including
  source compiled into shipped programs. Skip commits that only update
  pins and the content generated from them.
- **Interface changes.** List every breaking and additive change from the
  `src/public-api.sh` comparison used for version selection. Use the
  comparison's classification to mark breaking changes. Omit this section
  for the first release.
- **Dependency changes.** Compare `versions.env` at the two release points.
  Report pins that change a shipped default or a dependency jailbox uses
  when it runs. Today that means the Debian image in the starter
  `Containerfile` and the Alpine base for the egress proxy. Show the old and
  new values or an added or removed label. Test-only pins belong in the
  verification details.
- **Verified with.** Link the successful release run. Identify the observed
  Bash and Podman versions as Linux runtime results, list the tested editors,
  extensions, and images, and label install checks by platform.
- **Install or upgrade.** Link the instructions and the full Git comparison
  when there is a previous release.

Omit empty change sections. Use the highest version tag as the shared
baseline for version selection and release notes. Compare against the exact
release commit.

### Release and preview

On a release started by `scripts/release.sh`, use the local Codex CLI once
after version selection, when it is available. Run it without prompts in a
read-only sandbox with a time limit. Draft from the shipped Git changes,
with newly archived plans as context. Use the Git fallback if Codex is
missing, fails, times out, or returns blank or oversized Markdown. The
interactive command shows the notes before its existing confirmation.
`--yes` skips the existing prompts and includes the highlights when available.

Carry the highlights with the release request. CI includes them when the
request's previous release and target commit match its decision. If the
text or range is invalid, warn and continue with the Git fallback. Direct
GitHub dispatch uses that fallback.

After the gates and package checks pass, CI prepares a GitHub draft for the
exact tested commit. Reuse or replace any draft from an earlier attempt at
that version. Publish the prepared draft by ID once the current run's notes
and all expected assets are in place. GitHub creates the lightweight version
tag at publication. Failed preparation or uploads leave the version untagged.

Show the reason for the selected bump in the local preview and CI log.
`scripts/release.sh --dry-run` runs the same bump selection and highlight
drafting as a local release, with verification marked pending. It stops
before creating or pushing the request tag and uses local tags if fetching
tags fails. Rendering the same release inputs, including any supplied
highlights and verification data, yields the same notes. Use the successful
run that supplies the `release` row in `compatibility`'s `releases.csv` for
verification details.

### Acceptance

- Cover additions and removals in the same release, a requested minimum
  bump, and the first release without a baseline. Verify that additions,
  removals, and value changes for shipped pins appear in the dependency
  section and that test-only versions appear only in the verification details.
- Verify both release entry points, unattended local dispatch, and the
  fallback for a timed-out draft or a mismatched range. Check that the
  fallback includes build input changes and omits pin-only commits even
  when they update shipped generated content. Check that dry run uses the
  same draft and fallback without creating or pushing a request tag.
- Verify that multiline Markdown survives transit and that a reused request
  tag cannot supply highlights from another request.
- Verify the notes come from the successful test run and that publication
  creates the tag for the tested commit after the notes and assets are in
  place. Verify a retry after an upload failure publishes one release and
  leaves no duplicate draft for that version. Cover a successful publication
  followed by a failed history write.
- `11.2.4-public-interface-plan.md` owns keeping the interface section
  complete when the release comparison moves to Go.

## Implementation detail

Extend `scripts/public-api-diff.sh`, which currently returns a single
classification, so version selection and rendering share the detailed
comparison. Remove the `Create and push release tag` step from
`.github/workflows/release.yml`. The existing release action can find drafts
through the paginated release list and publish them by ID. Reuse the release
gate outputs already passed to the compatibility recorder.

A release-request tag annotation can carry the highlights and their range
while keeping dispatch a Git push. Use `git tag --cleanup=verbatim` to
preserve Markdown and verify the workflow reads the triggering annotation.

Update the release workflow and describe the local Codex setup, automatic
fallback, and preview in the release instructions in `CONTRIBUTING.md`.
