# 3.1. Environment configuration overrides

## Goal

Allow orchestrators to override any public configuration key with a documented
`JAILBOX_CONFIG_`-prefixed environment variable, without adding a mode flag or a
second configuration path. The selected configuration file remains the
reviewable, protected baseline; exported overrides produce the effective
configuration used by that invocation.

## Sequence

Order 3.1. This is a stable insertion after
`03-launch-core-and-up-plan.md`, whose `up` command is the primary orchestration
entry point, and before `04-config-digest-plan.md`, which must hash the complete
effective configuration. Plans 5 and 6 inherit the same override processing for
`exec` and `shell` so an orchestrator can reproduce the launch declaration when
it attaches.

## Public interface

Every key in `CONFIG_SCALAR_KEYS` and `CONFIG_ARRAY_KEYS` has one environment
override named by prefixing the key with `JAILBOX_CONFIG_`. For example:

```text
DEV_IMAGE       -> JAILBOX_CONFIG_DEV_IMAGE
EGRESS_ALLOW    -> JAILBOX_CONFIG_EGRESS_ALLOW
READONLY_PATHS  -> JAILBOX_CONFIG_READONLY_PATHS
EDITOR          -> JAILBOX_CONFIG_EDITOR
```

Derive this mapping from the canonical declarations in `host/public-api.sh`;
do not maintain a second hand-written key list. Adding a public configuration
key must automatically add its environment spelling and coverage.

The portable gate must also enforce the integrity of those declarations. The
keys on the left side of `CONFIG_DEFAULTS` must equal exactly the union of
`CONFIG_SCALAR_KEYS` and `CONFIG_ARRAY_KEYS`: no missing defaults, undeclared
extras, or duplicate defaults. A key must not appear more than once in either
public-key array or appear in both the scalar and array declarations. This
makes the declarations a reliable source for defaults, parsing, environment
override derivation, and plan 4's digest coverage.

The precedence order is:

```text
built-in defaults < selected configuration file < exported environment override
```

There is no `--env`, `--env-config`, or enablement flag. Setting a recognized
`JAILBOX_CONFIG_<KEY>` variable is the explicit opt-in. An unset variable leaves
the file or default value intact; a variable that is present with an empty value
intentionally replaces it with the empty scalar or empty array. Inspect
presence, not non-emptiness, when deciding whether to apply an override.

The dedicated `JAILBOX_CONFIG_` namespace contains configuration overrides
only. Reject any present `JAILBOX_CONFIG_*` name that is not derived from a
public configuration key, so an orchestrator typo cannot silently fall back to
weaker or otherwise unintended policy. Existing operational, installation,
test, and internal `JAILBOX_*` names outside this narrower prefix retain their
current meanings and are not inspected by configuration loading.

Remove the existing special `JAILBOX_EDITOR` override from `host/editor.sh`,
`host/preflight.sh`, tests, and README guidance. It receives no compatibility
alias or deprecation period: editor selection through the environment uses
`JAILBOX_CONFIG_EDITOR`, the ordinary derived spelling of the public `EDITOR`
key. Like every scalar override, a present empty value clears a configured
`EDITOR`, after which bare launch may use its normal editor discovery.

## Parsing and validation

Environment inputs are the same strict data as file inputs and must reach the
same key-specific validation before any launch mutation:

- Scalar variables contain the value directly. Shell quoting used to set a
  variable is not part of its value; do not apply the config file's optional
  quote-removal syntax to environment data.
- Array variables use the same comma-separated representation as the config
  file. An empty variable is an empty array. Reject empty members and validate
  each member under the same rules as a file-provided array.
- Parse and validate the selected file as a valid baseline before applying any
  override, then validate the completed effective configuration again.
  Diagnostics for an invalid override identify the environment variable rather
  than inventing a config-file line number.
- Never use an environment-provided string as a shell variable name,
  associative-array subscript, arithmetic expression, or shell program.
  Indirection may use only validated names derived from the repository-owned
  public-key declarations.

File parsing remains all-or-nothing. A valid environment override does not
excuse a malformed or unknown setting in the selected file, and it does not
make a missing required configuration file acceptable.

## Configuration anchor and selection

The default `$PROJECT_DIR/jailbox.conf` anchor remains required for every
launch and attach command, including when environment variables provide every
effective value. `--config PATH` continues to select the one file parsed as the
baseline, and the default anchor remains independently validated and protected
as established by plan 1.1.

This is a security boundary, not configuration ceremony. An existing sandbox
has the project mounted writable; allowing a launch with no persistent anchor
would let that sandbox plant `jailbox.conf` for a later invocation. An
orchestrator provisions the anchor once, either with `jailbox init` while no
sandbox exists or as part of its project setup.

The selected file is still protected even when overrides replace all of its
values. Environment configuration does not create a distinct sandbox identity,
does not change project-scoped resource names, and does not introduce an
environment-only selected-config marker.

Commands that intentionally bypass configuration selection and loading —
`init`, `stop`, `--clean`, `--uninstall`, and help — continue to ignore
configuration overrides and retain their lighter preflight contracts. Commands
that optionally load configuration apply overrides whenever they do load it;
the environment must not make an otherwise optional file mandatory.

`doctor` and `ssh-config` use this common configuration pipeline without a
command-specific override branch. When no config file is selected, the common
pipeline applies recognized overrides over the built-in defaults without
requiring an anchor; when a config is selected, it applies overrides over that
parsed baseline. Common validation rejects unknown `JAILBOX_CONFIG_*` names
before these commands' existing light preflight. Their only distinction is that
a missing config remains acceptable; they acquire no Podman, SSH, SHA-256,
editor, or other launch-only requirement as a result.

## Digest and attachment contract

Plan 4 hashes the final parsed values after environment overrides. It does not
hash the raw environment representation or record whether a value came from a
default, file, or environment: equal effective policy should produce equal key
records. The selected-config identity remains a separate digest input because
the exact selected file is a protected launch input.

`JAILBOX_CONFIG_EDITOR` needs no dedicated digest record. Its effect is
represented by the effective `EDITOR` scalar like every other override.

An attach invocation must reproduce every override needed to obtain the launch
configuration. Omitting an override falls back to the selected file; if that
changes any effective value, `exec` or `shell` reaches the ordinary stale-
sandbox digest failure and directs the user to `jailbox up`. This conservative
failure is intentional: attaching under policy broader than the caller's
current declaration must not be reduced to a warning.

For orchestrators, the supported pattern is to construct one environment and
reuse it for `up`, `exec`, and `shell`, for example:

```sh
JAILBOX_CONFIG_DEV_IMAGE=registry.example/dev:stable \
JAILBOX_CONFIG_EGRESS_ALLOW=packages.example,registry.example \
jailbox up
```

## Public API and documentation

Treat the derived environment spellings as public configuration interfaces.
Declare the public `JAILBOX_CONFIG_` namespace once in `host/public-api.sh` and
teach `scripts/public-api-diff.sh` to include that declaration, so release-
version selection recognizes the addition of environment override support
without duplicating the configuration keys. Future additions and removals of
public configuration keys already imply the corresponding derived environment-
interface change.

The existing `JAILBOX_EDITOR` interface was not declared in
`host/public-api.sh`, so the generated diff cannot retrospectively detect its
removal. Name that removal explicitly in release notes and migration
documentation; do not claim the script discovered it. The declared namespace
addition still makes the complete plan an additive public-API change under the
repository's pre-1.0 version policy.

Document the precedence order, unset-versus-empty behavior, scalar and array
formats, the continuing anchor requirement, and the need to reproduce
overrides for attachment. Launch output should name the keys overridden by the
environment without printing their values; this makes inherited CI state
visible without exposing future sensitive configuration values. Preserve
declaration order in that output for deterministic diagnostics. Plan 5 owns the
corresponding attach-mismatch diagnostic, and plan 6 reuses it.

## Non-binding implementation notes

- Keep default application, file parsing and baseline validation, environment
  override application, and final effective validation as distinct phases in
  `host/common.sh`. This ensures an override cannot conceal invalid file data.
- Reuse focused scalar and array assignment/validation paths, but give
  environment failures source-aware diagnostics rather than routing them
  through `config_die` with a fictitious line number.
- Derive override names only from `CONFIG_SCALAR_KEYS` and
  `CONFIG_ARRAY_KEYS`. Validate each repository-owned key before any indirect
  lookup, consistent with the associative-subscript rules in `AGENTS.md`.
- Add a focused portable unit assertion over the public declarations rather
  than relying on parser behavior to expose drift indirectly. Exercise each
  failure direction with mutated fixture declarations: missing and extra
  defaults, duplicate defaults, duplicate public keys, and scalar/array
  overlap.
- Update editor selection and preflight to consume effective `EDITOR` directly;
  remove `${JAILBOX_EDITOR:-$EDITOR}` and every user-facing reference to the
  superseded special override.
- Add unit coverage at the configuration-loading layer and lifecycle coverage
  proving overrides reach `up`. Plan 4 adds digest-vector coverage for the
  effective result, and plan 5 adds real attachment coverage.

## Acceptance criteria

- Every public scalar and array key has the derived `JAILBOX_CONFIG_<KEY>`
  override; adding a public key automatically receives coverage without editing
  a second list.
- `CONFIG_DEFAULTS` contains every public scalar and array key exactly once and
  no other key; every public-key array is duplicate-free, and the scalar and
  array sets are disjoint. Focused fixture mutations prove each violation fails
  the portable test.
- With no recognized overrides, configuration behavior is unchanged.
- A non-empty scalar override replaces the file value, and a present empty
  scalar replaces it with the empty value. An unset variable preserves the file
  value.
- Array overrides use comma-separated values, preserve declared item order,
  accept a present empty value as an empty array, and reject empty or invalid
  members exactly as file arrays do.
- Invalid file data still fails even when an environment override would replace
  the affected key. Invalid environment data fails clearly, names its variable,
  and causes no launch mutation.
- `JAILBOX_CONFIG_EDITOR=code` and `JAILBOX_CONFIG_EDITOR=codium` select the
  corresponding editor. A present empty `JAILBOX_CONFIG_EDITOR` clears a
  file-provided `EDITOR`; an unset one preserves it. `JAILBOX_EDITOR` no longer
  affects selection and is removed from documentation and tests.
- Launch diagnostics list overridden key names in public declaration order and
  never print their values.
- The default configuration anchor and any selected config retain their
  validation and read-only protection when all effective values come from the
  environment.
- `init`, `stop`, `--clean`, `--uninstall`, and help remain independent of
  configuration overrides and do not gain configuration or tooling
  prerequisites.
- Through the same configuration pipeline used by other config-consuming
  commands, `doctor` and `ssh-config` apply recognized overrides over the
  selected config or, when none is selected, over built-in defaults. With no
  command-specific override branch, both reject an unknown
  `JAILBOX_CONFIG_*` name while retaining their optional-config behavior and
  existing light preflight requirements.
- Bare launch and `up` produce the same effective configuration from the same
  file and environment. Plan 4 produces the same digest for them, and plans 5
  and 6 require matching overrides when attaching.
- A file value and an environment override producing the same effective value
  have identical per-key digest input. Changing, omitting, or clearing an
  override changes the digest exactly when it changes effective policy.
- An unknown `JAILBOX_CONFIG_*` variable fails clearly before launch mutation.
  Existing unrelated `JAILBOX_*` variables outside that prefix are neither
  treated as configuration nor rejected.
- The generated public-API check recognizes the declared `JAILBOX_CONFIG_`
  namespace as an additive public-interface change. Release documentation names
  the removal of the previously undeclared `JAILBOX_EDITOR` interface without
  claiming the generated diff detected it.

Run `tests/run portable`. Also run `tests/run runtime` because overrides can
change image selection, mounts, network policy, and editor-launch behavior.
Run `tests/run editor` when the editor override migration can be exercised in an
environment with Podman, an editor, and a display or Xvfb.

## Non-goals

- An environment-only mode or a flag that disables config-file loading.
- Removing the default policy anchor or allowing environment variables to
  satisfy project initialization.
- Reading `.env` files, accepting arbitrary container environment variables,
  or sourcing shell fragments.
- Array merging, appending, subtraction, or per-item environment variables.
- Recording configuration provenance in the digest or resource names.
- Printing environment-provided configuration values.
