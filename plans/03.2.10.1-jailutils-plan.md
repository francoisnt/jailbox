# 3.2.10.1. jailutils shared runtime repository

## Goal

Create an independent `jailutils` source repository for runtime
utilities whose contracts are shared specifically by jailbox and JailIDE.
Consume one pinned source revision from each product without committing copied
source, requiring a separately installed library, or placing product-specific
code in Shell Release Toolkit.

## Sequence

Implement after 03.2.10 has adopted Shell Release Toolkit and before 03.2.11
creates the reduced JailIDE repository. First create and test the common
repository, then add its pinned submodule to jailbox. Include both the toolkit
adoption and common-submodule pin in the exact jailbox commit inherited by
JailIDE. Plan 03.2.11 retains that pin while reducing the JailIDE tree, and plan
03.2.15 pushes the tested common commit to its canonical remote before either
consumer release so both submodule URLs resolve.

## Ownership boundary

The common repository is ecosystem infrastructure, not a generic shell product
or a user-installed component. It owns only stable mechanisms that both
products execute with identical semantics. It knows that jailbox produces and
JailIDE consumes a documented public interface, but it does not own either
product's commands, schemas, policy, state, lifecycle, or diagnostics.

Initially extract one module: a strict encoder/decoder for the versioned,
line-oriented Base64 record envelope used by jailbox machine commands and
JailIDE. It owns record framing, field-name grammar, Base64 portability, and
structural rejection of malformed or duplicate records. The caller supplies
the allowed/required field schema and validates decoded values. Unknown valid
fields remain available to the caller so each public command can apply its
documented forward-compatibility rule.

SemVer release calculation stays in Shell Release Toolkit. JailIDE's jailbox
compatibility-range policy and evaluation stay in JailIDE until a second real
runtime consumer demonstrates an identical reusable contract. Configuration
parsing, path/identity validation, diagnostics, command discovery, locking, and
all container/editor behavior remain product-owned for the same reason.

## Repository and history

Create a clean locally excluded `jailutils/` clone beneath this
checkout while the workspace is the only confirmed writable location. Build
it from the reviewed coordinated jailbox history using path-limited filtering
for the record codec and its directly relevant tests, followed by an explicit
extraction commit recording the full source commit and original paths. Do not
rewrite jailbox history or import unrelated product code.

The repository has its own README, MIT `LICENSE`, `AGENTS.md`, contribution
guidance, and tests. Its public contract is the module API plus behavioral
tests. Record-envelope compatibility is governed by jailbox's public release
version and documented machine schema; repository source identity is the pinned
full commit and file digest. No remote, push, tag, or release occurs without
separate explicit authorization.

## Submodule consumption

Add the repository to each consumer at
`vendor/jailutils` as a normal Git submodule. Record
`https://github.com/francoisnt/jailutils.git` in `.gitmodules` and
a full pinned commit in the gitlink. Before that remote exists, candidate tests
use an explicit command-local URL override pointing at the isolated local clone;
never commit the override or rewrite the canonical URL. The submodule is the
only editable source location: neither consumer commits copied common source or
patches over the submodule. A common update is an explicit reviewed gitlink
change accompanied by affected product tests. Consumers never follow a branch
or resolve a moving tag during build or test.

CI and release builds initialize only the declared submodule, verify its origin,
commit, clean state, and allowlisted file inventory, and fail
closed when it is missing or mismatched. Do not use recursive initialization,
arbitrary submodule discovery, or executable build hooks from the common
repository. Pull-request workflows receive read-only contents permission.

Developer commands may diagnose an uninitialized submodule and print the exact
non-recursive initialization command, but must not fetch implicitly. Normal
installed runtime never invokes Git, reads `.gitmodules`, or accesses the
common repository separately.

## Packaging and runtime loading

Each consumer package copies the allowlisted files from its pinned submodule
checkout into that product's own release tree. The packaged copy is a build
artifact, not tracked duplicate source. Record the full common commit and file
digest in product build metadata and include them in package
reproducibility checks.

Installed jailbox and JailIDE source their own packaged copy through a fixed
product-relative path after verifying that the expected file exists. They
never search system paths, the sibling source repository, the other product's
installation, or environment-selected locations. Users install, update, and
uninstall each product independently; there is no shared writable installation
and one product cannot replace or remove the other's copy.

When a jailbox container helper needs an allowlisted primitive, the wrapper
image copies the same pinned file into a fixed jailbox-owned image path and
records the common commit and digest as image metadata. The
container-specific executable and its argv, lifecycle, and security policy stay
in jailbox; it may call or source only the packaged primitive. Image builds use
the already initialized build context and never fetch or initialize submodules.

## Tests

The common repository exposes exactly one user-facing `portable` gate covering:

- encode/decode round trips including empty and multiline values;
- strict field grammar, malformed Base64, duplicate records, truncation, and
  unknown valid fields;
- Linux and macOS command portability and the declared Bash baseline;
- caller-supplied required/allowed schemas without embedded product fields;
- deterministic output and locale-independent behavior; and
- fixtures with names unrelated to jailbox or JailIDE.

Jailbox tests prove its machine commands produce records through the pinned
module and preserve their documented schemas. JailIDE portable tests prove it
parses fake and packaged jailbox output through the same pinned module while
retaining independent value/policy rejection. A coordinated test requires both
gitlinks to resolve to the same full common commit before release.

## Adding later utilities

A utility moves here only when both products need the same runtime semantics,
its contract necessarily refers to the jailbox/JailIDE ecosystem but its API
does not branch on the calling product's identity, and independent
common-repository fixtures can test it completely. A product-agnostic contract
with a second real independent consumer belongs in Shell Release Toolkit
instead. The extraction change must remove both former implementations, retain
relevant history, document module compatibility, and update both pinned
gitlinks. Single-product helpers and shared concepts with different policy
remain local.

## Acceptance criteria

- Shell Release Toolkit contains no Jailbox/JailIDE-specific runtime code.
- Both consumer repositories track only a gitlink and integration code, not
  duplicate common source files.
- Consumer release archives are self-contained and require no common-package,
  source-repository, network, or Git access at runtime.
- Both consumers use and test the same exact common commit and independently
  retain their schemas and security policy.
- Host packages and the jailbox wrapper image identify and test every packaged
  common copy against that same commit and digest.
- Common changes and breaking contracts cannot enter either consumer through a
  moving reference or implicit fetch.

## Non-goals

- A general-purpose shell utility collection or inclusion in Shell Release
  Toolkit.
- An installed shared library, package-manager dependency, subtree, generated
  committed source copy, or automatic submodule update.
- Product schemas, policy validation, configuration parsing, state, Podman,
  SSH lifecycle, proxy, editor, or release-provider behavior.
