# 3.1.1. Trusted wrapper setup inputs

## Goal

Add an independently reviewable jailbox configuration capability for trusted
caller scripts that extend wrapper-image construction without weakening the
strict-data configuration model or exposing unrelated host inputs.

## Sequence

Implement after 03.1 establishes the canonical environment grammar and before
03.2.01. Plans 03.2.02 and 03.2.06 add content identity and execution behavior;
this plan owns the public key, trust boundary, input validation, and stable
acquisition of the authorized bytes.

## Public interface and trust boundary

Add `WRAPPER_SETUP` as an ordered public array with the derived environment
spelling `JAILBOX_CONFIG_WRAPPER_SETUP`. Its members name explicitly trusted
POSIX `sh` scripts that later run as root during wrapper-image construction.
An empty or absent array adds no caller setup. The generic 03.1 array grammar,
index rules, support floor, aggregate size checks, command applicability, and
validation-before-mutation contract apply without a separate count limit.

Selecting a script is deliberate authorization to execute trusted caller code,
not evaluation of configuration syntax. Jailbox validates the selected object
and preserves the authorized bytes; it does not certify script behavior,
portability, idempotence, or safety.

## Validation and protected inputs

Classify every member as an existing regular file with no symlinked path
component, canonicalize it for reading, and reject duplicates by canonical
path. External scripts are allowed. Automatically add project-contained
scripts to the effective read-only paths so a running sandbox cannot rewrite a
later build input or remove protection through caller configuration.

Validate and snapshot every script before the first lifecycle mutation. Stable
acquisition must ensure the bytes used later for hashing and image construction
are exactly those authorized during validation, including across a path-change
race. Read-only protection constrains the sandbox, not the host user: a later
host edit changes the content digest and prevents reuse, but cannot change bytes
already snapshotted or built.

Keep selection paths for validation, copying, protection, and diagnostics only.
Plan 03.2.02 defines content-addressed configuration and wrapper-cache identity;
plan 03.2.06 defines the isolated build context, ordered root execution, build
environment, failure behavior, and snapshot cleanup.

## Tests and documentation

Portable tests cover absent, empty, ordered, duplicate, missing, non-regular,
symlinked, external, and project-contained inputs. Prove validation and stable
snapshot acquisition occur before a fake lifecycle mutation, protected paths
cannot be overridden, and adversarial path replacement cannot change the
authorized bytes. Plans 03.2.02 and 03.2.06 own digest/cache and real build-time
execution coverage respectively.

Document that setup scripts are trusted caller-selected root code, not sandboxed
configuration data; jailbox validates file identity and acquisition rather than
the script's safety. Document the Containerfile as the ordinary user-owned image
customization path and this interface as an automation/downstream composition
boundary. Run `tests/run portable`; also run `tests/run runtime` for the final
integrated implementation under 03.2.06.

## Acceptance criteria

- `WRAPPER_SETUP` is introduced independently of the 03.1 transport refactor
  and follows its generic array grammar without an application-defined maximum.
- Every selected input is completely validated, protected when project-local,
  and stably snapshotted before lifecycle mutation.
- A running sandbox cannot change an unprotected project path to alter a later
  setup, and a host race cannot change the bytes after validation.
- The public documentation states plainly that callers authorize trusted code
  which later executes as root during wrapper-image construction.

## Non-goals

- Script behavior analysis, a restricted setup language, auxiliary file
  bundles, package-manager abstraction, or execution before 03.2.06.
- JailIDE user configuration for arbitrary setup scripts; JailIDE uses the
  interface internally only for its product-owned editor setup.
