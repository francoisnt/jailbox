### Consumer compatibility and durable documentation

This plan owns the charter and 03.2.08/09 consumer verification handoffs
transferred from 03.2.11, their original recipient in the archived plans,
and completes the closing verification assigned by the active 03.2.11.
Audit the existing public-command, frontend, runtime, and editor tests before
adding coverage. Map version discovery, schema discovery, environment
composition, connection parsing, and failure sequencing to their existing
owners. Add focused cross-command assertions only for demonstrated gaps;
independent command tests and the actual frontend provide the consumer evidence.
Version-range selection belongs to external orchestrators. The frontend neither
pins its own version nor discovers declarations it already knows.

Public-command tests verify version/schema framing and declaration propagation.
Frontend tests verify compatible trailing connection fields, missing required
fields, duplicate/malformed/truncated records, invalid required values, and
failed child commands with plausible success stdout. Never launch an editor or
attach after a failed required command or malformed connection result.

Connection fixtures enforce 03.2.09's ASCII field-name grammar and required
value meanings: the project ID is the 12-character lowercase hexadecimal hash,
the SSH alias is the declared public alias, paths obey their owning policy, and
the proxy URL is empty or the validated internal endpoint. Verify opaque valid
trailing values, and distinguish byte-preserving framing from semantic validity
of required fields; encoding support for TAB/newline does not authorize those
bytes in fields whose owning policy rejects them.

Use the existing real-CLI frontend and attachment scenarios in the runtime gate
and real frontend/editor integration in the editor gate. Retain 03.2.11.5's
assertion ownership: core SSH, networking, and sandbox-security checks stay in
runtime/matrix. Portable frontend fixtures supply synthetic compatible additions
and malformed connection responses. Extend existing tests where the audit finds
a gap; no separate automation consumer or compatibility framework is required.

### Caller serialization

This plan owns the charter's caller-serialization documentation. Machine
guidance requires orchestrators to serialize lifecycle mutations per project
and exclude them throughout dependent sequences such as `up` then
`connection-info`. Frontend guidance explains that concurrent launches,
stops, and cleans for one project are unsupported: the frontend does not
lock the sequence or exclude another terminal or process. Review both
sections for these limits without implying an atomic transaction or
protection throughout a long-lived editor session.

### Acceptance criteria

- Packaging and installation recursively include the complete runtime tree.
  Portable regressions prove newly added files ship and install automatically,
  and failed copying preserves the existing installation. Complete releases
  install successfully, with installer Bash 3.2 compatibility preserved.
- Release archives and installed copies retain README.md; ARCHITECTURE.md and
  CONTRIBUTING.md remain repository-only. The packaging review verifies that
  README does not link to either guide and installation does not require them.
- A reviewable coverage mapping assigns version/schema discovery, declaration
  propagation, environment composition, connection parsing, and failure
  sequencing to existing public-command and frontend tests. Any demonstrated
  cross-command gaps have focused regressions.
- Frontend fixtures accept compatible trailing connection fields and refuse
  missing, duplicate, malformed, truncated, or semantically invalid required
  records before launch. Failed commands cannot authorize dependent work even
  when they emit plausible success stdout. Valid trailing values remain opaque.
- Runtime verifies the existing real-CLI composition and attachment scenarios;
  editor verifies the real frontend. Version-range selection remains external
  consumer policy. All four existing gates pass before series completion.
- The durable architecture document is linked from CONTRIBUTING,
  matches the completed code, covers the topics above, and links to tests.
  Its glossary and walkthrough explain the concepts needed to understand the
  lifecycle and test strategy; no pending behavior is presented as shipped and
  no stale frontend-transition caveats remain. Maintaining shipped contracts
  does not require consulting archived plans.
- Machine and frontend documentation explain caller serialization, the lack
  of frontend locking, the complete up/connection-info interval, independent
  caller interference, and the absence of long-lived session protection.
- The final cross-series review resolves inconsistent public documentation and
  confirms every integration handoff is completed and verified.
