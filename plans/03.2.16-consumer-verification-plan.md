### Installer required-file coverage

This plan owns complete installer dependency validation as a release
requirement, following 03.2.11's directory migration and installer path updates.
`install.sh` maintains `REQUIRED_PATHS` manually and currently omits
`container/runtime/bin/jailbox-exec-argv`,
`container/runtime/bin/jailbox-write-editor-settings`, the streamed checks in
`container/checks/`, and the AWK helpers in `container/runtime/lib/jailbox/`.
Validate the completed `src/` layout, including core and frontend modules and
the shared declarations and host helpers. Runtime paths in this section are
relative to the installed bundle; packaging flattens `src/` into that root. Directory-based installation copies
these dependencies, but required-file validation can accept an incomplete
payload.

Installation must reject payloads missing any required runtime dependency.
Cover host modules, container programs, streamed checks, and runtime
data/helpers. New dependencies must enter the required inventory or fail an
explicit completeness check; adding only today's omitted filenames does not
satisfy this requirement. The expected inventory must remain complete when
files are missing from a candidate payload. Preserve installer Bash 3.2
compatibility and verify the complete release still installs successfully.

Keep README.md in release archives and installed copies. ARCHITECTURE.md,
CONTRIBUTING.md, and test sources remain repository-only documentation and
development material. Preserve that distinction in `scripts/build-tarball.sh`'s
`RELEASE_PATHS` and `install.sh`'s bundle-copy logic; the architecture guide is not
a required installation dependency. Review the packaged and installed README
to verify that it does not link to ARCHITECTURE.md or CONTRIBUTING.md, using
either local paths or repository URLs. Repository-only documents may retain
relative links to one another.

### Consumer compatibility and durable documentation

This plan owns the charter and 03.2.08/09 consumer verification handoffs
transferred from 03.2.11, their original recipient in the archived plans,
and completes the closing verification assigned by the active 03.2.11.
Extend portable frontend fixtures and a small external automation consumer
fixture to exercise public version discovery, compatible range selection,
schema discovery, environment composition and connection parsing. Range
selection belongs to the consumer fixture; do not add a frontend self-version
pin or require the frontend to discover declarations it already knows. Test
valid additional schema keys and trailing connection fields, missing required
keys, unknown types, duplicate/malformed/truncated records, incompatible
versions, and failed child commands with plausible success stdout. Never launch
an editor or attach after any failed command or malformed result.

Connection fixtures enforce 03.2.09's ASCII field-name grammar and required
value meanings: the project ID is the 12-character lowercase hexadecimal hash,
the SSH alias is the declared public alias, paths obey their owning policy, and
the proxy URL is empty or the validated internal endpoint. Verify opaque valid
trailing values, and distinguish byte-preserving framing from semantic validity
of required fields; encoding support for TAB/newline does not authorize those
bytes in fields whose owning policy rejects them.

Run the automation fixture against the real CLI in the runtime gate. Exercise
the real frontend's editor integration in the editor gate, retaining
03.2.11.5's assertion ownership: core SSH, networking, and sandbox-security
checks stay in runtime/matrix, not duplicated in editor. Portable fixtures supply synthetic future
compatible and malformed responses. These checks extend existing gates; they
are not a new product, compatibility framework or user-facing test mode.

Creation of ARCHITECTURE.md, originally assigned here, was brought forward
to the 03.2.11 decomposition so readers can understand the architecture before
implementing it. It is linked from CONTRIBUTING and distinguishes
current behavior from planned frontend behavior. 03.2.11.5 owns updating it
for the implemented frontend. This plan owns the final review and corrections
against the completed series, including removal of stale transition caveats.
The guide must retain its lifecycle walkthrough, testing strategy, diagrams,
and glossary, and cover core/frontend ownership, public-command composition,
lifecycle decisions, resource retention and cleanup,
digest versus build inputs, SSH generations, the caller-serialization
obligation and its limits, security boundaries, and test/release
responsibilities. Keep public commands
and byte-format contracts in user documentation and link to relevant tests.
Verify the guide against the completed code; archived plans must not be needed
to understand or maintain the shipped contracts. This plan owns the final
cross-series documentation review and resolution of inconsistencies.

### Caller serialization

This plan owns the charter's caller-serialization documentation. Machine
guidance requires orchestrators to serialize lifecycle mutations per project
and exclude them throughout dependent sequences such as `up` then
`connection-info`. Frontend guidance explains that concurrent launches,
stops, and cleans for one project are unsupported: the frontend does not
lock the sequence or exclude another terminal or process. Review both
sections for these limits without implying an atomic transaction or
protection throughout a long-lived editor session.

### Acceptance criteria

- Installer validation covers every shipped runtime dependency in the completed
  layout. Portable regressions remove a required dependency from each category
  and verify rejection of the incomplete payload, and prove newly introduced
  dependencies cannot silently escape validation. Complete releases install
  successfully, with installer Bash 3.2 compatibility preserved. This coverage
  is required before release.
- Release archives and installed copies retain README.md; ARCHITECTURE.md and
  CONTRIBUTING.md remain repository-only. The packaging review verifies that
  README does not link to either guide and installation does not require them.
- Consumer fixtures prove compatible additional schema keys and trailing
  connection fields work, while missing required keys, unknown types,
  duplicate/malformed/truncated records, incompatible versions, and failed
  commands with plausible stdout refuse before editor launch or attachment.
- Required connection values obey their owning policies; valid trailing values
  remain opaque. Consumer range selection does not become a frontend self-pin.
- Portable fixtures exercise synthetic future and malformed responses; runtime
  verifies the automation consumer against the real CLI, and editor verifies
  the real frontend. All four existing gates pass before series completion.
- The durable architecture document is linked from CONTRIBUTING,
  matches the completed code, covers the topics above, and links to tests.
  Its glossary and walkthrough explain the concepts needed to understand the
  lifecycle and test strategy; no pending behavior is presented as shipped and
  no stale frontend-transition caveats remain. Maintaining shipped contracts
  does not require consulting archived plans.
- Machine and frontend documentation explain caller serialization, the lack
  of frontend locking, the complete up/connection-info interval, independent
  caller interference, and the absence of long-lived session protection.
- The final cross-series review resolves inconsistent public documentation and
  confirms every integration handoff is completed and verified.

### Non-goals

A new product, compatibility framework, test mode, protocol version, frontend
version pin, lifecycle locking, or a separate release for the frontend.

## Implementation detail

Derive the required inventory from complete release contents or verify the
maintained inventory against shipped runtime dependencies. Enumerating only
files present in a candidate payload cannot detect its missing files. Extend
the existing portable distribution and installation tests for these checks.

Extend existing frontend fixtures and gate harnesses rather than adding a
parallel test framework. Keep expected consumer behavior independent of the
production composer. Use the completed code and its tests as the evidence for
the architecture guide and cross-series review.

Run `tests/run portable`, `tests/run runtime`, `tests/run matrix`, and
`tests/run editor`.
