# 10.1. Policy-controlled host command forwarding (draft)

## Intent

Status: draft, deferred for design review. This document does not authorize
implementation and has no scheduled place in the implementation sequence.
Proceed with `11.1-go-frontend-plan.md`; forwarding is not a prerequisite or
acceptance requirement of that migration. Reconsider its implementation after
the Go migration rather than expanding the Bash implementation now. The current
Go plan migrates the frontend and keeps the machine core in Bash; it does not
settle the implementation language or ownership of a future forwarding service.

### Recommended Git direction

Prefer running Git inside jailbox against an independent clone with its own
writable Git metadata. Keep the original repository outside the container's
writable mounts. Review and import selected commits through host-controlled Git
operations, without copying sandbox Git configuration or hooks or running host
Git inside the sandbox-controlled checkout.

Create that clone without hard-linked objects or alternate object storage, for
example using `git clone --no-local` without `--shared` or `--reference`. A linked
Git worktree shares repository storage and does not provide this isolation.
Hooks, editors, and other Git helpers run inside the sandbox. Treat imported
source as untrusted until reviewed before host execution.

This recommendation changes the workflow: edits happen in a separate working
copy, and uncommitted starting changes need an explicit transfer policy. It is
design input, not a new cloning or synchronization feature assigned to the Go
migration. Default host Git forwarding and mandatory read-only sandbox `.git`
are not requirements of this draft.

### Forwarding design for evaluation

The remaining sections retain the forwarding proposal for evaluation; they are
not settled implementation requirements. The approval interface, actual default
policy, editor integration, rule-overlap behavior, and client/transport choice
still need decisions before this draft can become an implementation plan.

Let users expose selected host commands inside a jailbox container under their
normal names. A container-side wrapper forwards the original arguments and
project working directory; a host service authorizes the request and executes
the host program. Stream command input and output and support ordinary pipelines
and exit statuses for noninteractive commands.

### Activation and trust

- Use the project-root file `jailbox.host-policy` as the readable policy.
  Its presence alone grants nothing: an explicit host action approves the exact
  file contents for the canonical project root. Keep that approval outside
  container-writable state. Changed contents require fresh host approval;
  stop/start alone does not approve them. Project configuration and container
  requests cannot grant authority. Direct machine callers require the same
  project-and-content approval.
- Automatically protect an existing policy file read-only, including when
  forwarding is disabled or unapproved. Validate and snapshot approved contents
  before publishing a usable endpoint or wrappers; keep the snapshot outside
  container-writable state and refuse conflicting hidden-path policy. Include
  policy contents in compatibility checks. Activate approved changes through
  stop/start; editing the source never reloads a running service, and reuse under
  different contents fails explicitly.
- Run as the invoking host user. Resolve each policy executable through the
  trusted host environment, retain its absolute path for the session, and fail
  preparation if it is unavailable. Never resolve host executables using
  container-provided `PATH`. Commands inherit the service's launch-time host
  environment, including Git identity and credential-helper settings.
  Requests cannot override it. A retained absolute executable path is not a
  guarantee against replacement by another host process.
- Any container process able to reach the endpoint receives the configured
  authority. The host validates every request independently of wrappers and
  binds it to the authorized project and container generation. Do not expose
  an unrestricted host shell, engine socket, or host SSH credentials.

### Policy language

Each logical line permits one complete invocation. Fixed text matches literally
and in order; `{{regex}}` matches variable text within one argument. Separate
lines express different argument counts, flags, or orders. Execute the matched
argument array unchanged.

```text
# Git runs in the mapped project working directory.
git status --short
git diff --stat
git add -- src
git commit \
    -m {{.*}}

virsh start {{dev-linux|dev-windows}}
podman run --rm --name test-{{[a-z0-9-]+}} approved-image
```

These Git lines illustrate argument matching only, not safe defaults. Host Git
can run sandbox-controlled hooks or helpers and discover nested repositories;
read-only top-level metadata and regex matching alone do not prevent that.
The recommended Git workflow above avoids host Git execution in that checkout.
Additional paths or argument counts need additional definitions.

- Match the received argument array, never a space-joined command string.
  Anchor each complete argument pattern. Regex sections cannot consume another
  argument, including with `.*`. Preserve empty arguments and literal spaces,
  newlines, quotes, and shell metacharacters in captured values.
- Require exactly one complete matching definition. Reject missing, extra,
  unknown, or ambiguous arguments without execution; never ignore flags.
  Construct the output array directly, without shell evaluation or re-splitting.
- Use the lexical and regex rules below. Reject malformed policy at load time,
  with physical source-line diagnostics. Enforce finite limits on policy size,
  pattern size and matching time. Exceeding a limit rejects the request without
  execution. Do not add subcommand trees, implicit
  optional/repeated arguments, or shell evaluation.

#### Lexical and regex rules

- Space and tab separate arguments outside quotes and regex sections. Adjacent
  literal, quoted, and regex fragments form one argument pattern.
  Empty quotes define an empty literal argument. The executable name is literal.
- Single or double quotes group literal text containing spaces; matching quote
  characters open and close the group and are removed. Regex sections remain
  active inside either quote style. Outside regex sections, backslash makes the next
  character literal, including quotes, backslash, and braces.
  There are no shell escapes such as backslash-`n` meaning newline.
- An unescaped `{{` opens a regex section, which ends at the first unescaped
  `}}`. While scanning a regex, backslash and its following character are kept
  together unchanged. Quotes and spaces inside it are regex text.
  Delimiters have no awareness of regex character classes or repetition braces;
  group a pattern when needed to avoid a closing-brace collision. Thus write
  `{{([0-9]{2})}}` for two digits, rather than `{{[0-9]{2}}}`. Literal braces
  can be represented inside a regex with escaped braces.
- Escape a literal opening `{{` with backslash. Quotes and regex sections must
  close on the same physical line. Angle brackets are ordinary literal text.
- A backslash immediately before a line ending, outside quotes and regex,
  continues a definition only at an argument boundary. Replace it and the line
  ending with one separating space. Blank lines and lines whose first nonblank
  character is `#` are ignored between definitions; comments cannot interrupt a
  continued definition. Reject unfinished continuations. Unquoted newline ends
  the definition; inline `#` is literal text. Reject backslash-newline inside
  quotes or regex sections and outside an argument boundary, such as
  `git commit` immediately followed by backslash-newline.
- Regex syntax is case-sensitive POSIX extended regular expressions in the C
  locale, with byte-oriented matching and no implementation-specific extensions
  or backreferences. Dot includes newline bytes. Require a full match of the
  complete argument, treating regex fragments as grouped expressions and all
  other fragments as literals. Do not implement full matching using anchors
  that can also match beside a final newline.

Examples of one-argument patterns:

| Policy text | Meaning |
| --- | --- |
| `{{.*}}` | Any bytes in one argument, including an empty value |
| `"two words"` | The single literal argument `two words` |
| `--name=test-{{[a-z0-9-]+}}` | A fixed prefix followed by a matching suffix |
| `{{([0-9]{2})}}` | Exactly two ASCII digits |
| `\{\{literal}}` | The literal argument `{{literal}}` |

For example, `git commit -m "example message" -C /bad/path` does not match the
four-argument commit definition: `-C` and its value are extra arguments. A
message containing those same characters inside one argument is ordinary data.

### Wrappers and working directories

- Publish one Bash shim per distinct policy executable name in a managed,
  read-only directory first in the normal container `PATH`. Shims use one shared
  forwarding client and preserve the original argument array. Existing local
  executables may remain installed, including Git; verify ordinary lookup finds
  the shim through shell, exec, and editor-terminal entry paths. Do not remove
  packages or claim that shadowing prevents explicit local execution.
- Check host executable availability and wrapper lookup separately. Never count
  the forwarding shim as evidence that the real program exists on the host.
  Diagnose unusable names or collisions with required runtime helpers before
  enabling the feature. Denial, transport failure, and an unavailable host
  executable never fall back to local execution.
- Accept calls only from the container project root or a subdirectory. Map the
  directory's project-relative location to the host project root, validate
  containment on the host, and execute there. Do not trust textual prefixes,
  symlink redirection, or a caller-selected host root. The container client also
  checks its actual working directory; the host cannot authenticate an arbitrary
  process's directory merely from the directory claimed in a socket request.
  Endpoint access authorizes requests within the registered project mapping.
- Command arguments receive no path translation or filesystem validation.
  Programs resolve relative paths from the mapped working directory, including
  `..` and symlinks according to their own behavior. Absolute container paths
  are passed unchanged and may not identify the corresponding host files.
  Regexes restrict spelling only; mapping the working directory does not
  confine a command's filesystem access.

### Execution and lifetime

- Carry requests through a managed, host-initiated SSH connection using the
  existing sandbox credentials and strict host-key checking. Expose only the
  project-bound service, without requiring a host SSH server or handing
  host-login credentials to the container. Do not depend on an editor-owned SSH
  process remaining alive. The transport must preserve the stream and lifecycle
  properties below; a reverse socket is an implementation option.
- Reuse `exec`'s NUL-delimited, Base64-encoded argument representation and its
  49,152-byte encoded limit. Share validation rather than inventing another
  quoting format. This is encoding, not compression. Frame request metadata
  separately so stdin remains the command's data stream.
- Noninteractive execution streams binary stdin, stdout, and stderr without
  Base64 encoding, retains separate output streams, and returns command exit
  status. Handle EOF, backpressure, cancellation, and broken connections without
  hanging dependent processes or automatically replaying a command.
- Service or transport failure makes pending requests fail nonzero promptly;
  distinguish an execution result from an interrupted or unknown outcome.
  While the service is alive, cancel owned foreground request process groups on
  disconnect, stop, or rollback, using bounded termination and cleanup. Do not
  undo completed host effects or remove containers/VMs deliberately started by
  an approved command.
- Core owns service startup, readiness, generation binding, and
  cleanup. Enabled launches must not succeed with partial policy publication,
  missing wrappers, or unusable forwarding. Stop and failed-launch rollback
  revoke the endpoint and clean up owned service/transport resources. Preserve
  unrelated sessions and pre-existing resources; surface failures without
  masking the original error. Status and recovery remain available when policy
  input is invalid. Ordinary disabled launches need no forwarding service.
- If the service or transport fails while the container survives, wrappers fail
  clearly and `up` refuses reuse with stop/start guidance. Healthy reuse retains
  the existing service. Require `stop` followed by `up` to recreate forwarding;
  never replay an interrupted command. Abrupt service death can leave host
  commands running with an unknown outcome. Automatic repair and recovery of
  those processes are outside this version; do not retain request-process
  recovery records or signal potentially reused PIDs.

### Scope and acceptance

Commands receive pipes rather than a terminal, even when invoked from a container
terminal. Output appears as it arrives, but programs may disable colors, paging,
or progress animations. Interactive editors and terminal prompts are outside
this version; policies should permit noninteractive forms such as
`git commit -m {{.*}}`. No pseudo-terminal, terminal-mode changes, or resize
protocol is required.

The policy author grants the actual capabilities of the
approved program and its children. Argument matching alone does not confine
configuration, helper execution, network access, or filesystem effects. Such
grants can bypass container hidden/read-only paths and egress restrictions;
document the distinction in the security guide and README threat model. The
host snapshot remains authoritative even if a command changes the source policy.

This feature does not by itself make jailbox's full test suite work through
forwarded Podman: temporary workspace sharing, published-port reachability, and
resource ownership remain separate integration work. Do not provide implicit
authority for other containers, VMs, or host paths through a broad example rule.

Acceptance covers:

- Literal/regex matching against the examples above, multiline
  equivalence, escaping, malformed policy, ambiguity, extra-argument injection,
  empty arguments, and bounded input; invalid requests must have no execution
  side effects.
- Exact-content approval, rejection of changed policy after restart, policy
  protection and snapshots, launch-time environment, unavailable executables,
  shadowing, mapped root/subdirectory calls, path escapes, direct endpoint
  requests, unchanged path arguments from nested directories, and isolation
  between projects and container generations. Path-escape checks apply to the
  mapped working directory, not arbitrary command arguments.
- Exact binary streaming and exit status, piped input, separate stdout/stderr,
  concurrent requests, cancellation/disconnect behavior, and execution without
  a host terminal even when the caller has one.
- Service death, refusal of unhealthy reuse, explicit stop/start without replay,
  lifecycle failure and interruption cleanup, disabled operation, installed
  packaging, and preservation of existing `exec`, shell, and editor behavior.

Acceptance uses the existing five gates, with real Linux runtime/matrix and
both editor integrations. Follow repository rules for local development checks
and platform claims.

## Implementation detail

Reuse or extract framing from `src/host/core/commands/exec.sh` and
`src/container/runtime/bin/jailbox-exec-argv`, preserving their existing public
behavior and regression coverage. Their current noninteractive SSH execution
does not implement the new reverse request protocol.

Keep host authorization and service/resource lifetime in core, container shims
and client assets under `src/container/`, and host-approval interaction in the
frontend. Integrate through the public CLI boundary; frontend code must not
source core or manipulate its private state. Declare added configuration and
machine surfaces in `src/public-api.sh`, deriving consuming lists and validating
their mappings. Include new assets in syntax/lint, packaging, compatibility,
readiness, and lifecycle contracts rather than introducing a separate test gate.

Thin per-command Bash shims can invoke a single shared client. Choose the
smallest transport implementation that satisfies byte streaming and cancellation
requirements, declare any new runtime dependencies, and keep substantial helper
programs in ordinary source files. Implementation language and helper layout
remain implementation choices.
