# 3.2.13. JailIDE launch, composition, and anchoring

## Goal

Implement the complete human launch path using only one installed compatible
jailbox executable and deterministic final environment policy.

## Sequence

Implement after 03.2.11/12 and jailbox 03.2.09. Its successful editor gate is a
precondition for core removals in 03.2.14.

## Module ownership

Implement editor behavior in JailIDE-owned Go packages, using jailbox's
`host/editor.sh` only as a behavioral reference until 03.2.14 deletes it.
Separate:

- editor binary/version and Remote SSH extension discovery;
- isolated profile path/settings generation;
- deterministic policy composition and jailbox client invocation; and
- connection-info parsing and editor launch.

Write JailIDE-owned unit and editor-gate tests for settings generation,
preflight, and launch. Downloader/proxy container management stays out of
JailIDE; only bootstrap-host composition and editor-local `http.proxy`
settings are represented. JailIDE contains no Podman commands, core name/hash
derivation, SSH credential generation, or direct state reads.

## Launch sequence

Bare `jailide` performs these ordered steps:

1. Canonicalize the project and default/selected configuration paths.
2. Resolve jailbox once, require the compatible version, and parse
   `config-schema` from that same executable.
3. Parse the selected `jailide.toml` through 03.2.12.
4. Resolve editor by the exact precedence in 03.2.12 and validate the supported
   binary/version and Remote SSH extension before lifecycle mutation.
5. Compose final core scalar/array values.
6. Invoke that jailbox path as `up` with the final environment.
7. If and only if up succeeds, invoke the same path as `connection-info` with
   the byte-identical environment.
8. Strictly parse the NUL-delimited connection records, generate isolated
   editor settings, and launch Remote SSH at the reported host/path.

Never infer safety from diagnostics or continue after either core command
fails. Reopening/resume works only because constrained up and connection-info
accept the same policy. JailIDE never automatically calls stop or clean.

## Deterministic composition

Begin arrays in file order. Append JailIDE-composed members in fixed documented
order, retaining the first occurrence and dropping later byte-identical
duplicates:

- append bootstrap destinations for the selected editor to
  `EGRESS_ALLOW`; and
- append JailIDE's embedded editor-dependency script to `WRAPPER_SETUP`; and
- append the default `jailide.toml` and any distinct selected in-project
  config/policy inputs to `READONLY_PATHS`.

Export scalars as bare `JAILBOX_CONFIG_<KEY>`, arrays as contiguous indexed
members, explicitly empty arrays as an empty bare name, and omit unset keys.
Construct a fresh child environment so inherited unknown `JAILBOX_CONFIG_*`
variables cannot accidentally alter policy; only parsed/composed declarations
are exported. Use the identical constructed environment for up and
connection-info. Unit tests snapshot variable names/order without values that
could later become sensitive.

Editor choice selects bootstrap hosts, while JailIDE always contributes the same
shared editor setup script. Both the hosts and exact setup-script bytes enter
the digest. Switching editors or changing the script bytes against existing
resources refuses; document `jailbox stop` followed by a fresh JailIDE launch.
JailIDE asks up only to create absent state, resume validated stopped state, or
complete a dependency-safe matching partial set.

## Editor wrapper setup

Ship one self-contained POSIX `sh` setup script embedded in the `jailide`
binary. It independently detects `apt-get`, `apk`, `dnf`, or `yum` in that
order,
refuses a base image without a supported package manager, and installs the
supported editors' shared remote-server runtime requirements:

- apt: `procps`, `libc6`, and `libstdc++6`;
- apk: `procps`, `musl`, `libgcc`, `libstdc++`, `flock`, `gcompat`,
  `krb5-libs`, and `webkit2gtk-4.1`;
- dnf: `procps-ng`, `glibc`, `libgcc`, and `libstdc++`; and
- yum: `procps`, `glibc`, `libgcc`, and `libstdc++`.

The script performs the appropriate package-index update and cleanup and
contains no Podman, jailbox lifecycle, host-path, credential, profile, editor
configuration, or launch behavior. Both Code and VSCodium use the same script;
editor-specific host compatibility checks and egress destinations remain in
JailIDE composition. Before composition, JailIDE materializes the embedded
script to the content-addressed regular file
`~/.local/state/jailide/setup/<sha256>.sh` with no symlinked path component,
verifies the on-disk bytes against the embedded copy, and passes that path
to jailbox without ever executing it directly; jailbox remains authoritative
for validation and content identity of the complete final array.

## Connection parsing and editor settings

Parse the NUL-delimited record contract from 03.2.09 directly. Require one each
of `ssh_config`, `ssh_host`, `remote_path`, `project_id`, and `proxy_url` in the
documented order; reject duplicates, invalid paths/alias/project ID, malformed
or unterminated records, or a missing field. Ignore valid trailing future
fields. JailIDE owns this field schema and all value validation policy.

Use the reported SSH config and alias for Remote SSH and open `remote_path`.
Set editor `http.proxy` exactly when reported `proxy_url` is non-empty and
omit it otherwise. Never copy the egress allowlist into editor settings.
Remote session `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, and lowercase
variants remain exclusively jailbox-generated SSH session behavior.

Profiles live at
`~/.local/state/jailide/profiles/<project-id>/`. Regenerate JailIDE-owned
settings atomically, preserve unrelated profile content according to the
existing extracted contract, and do not touch legacy jailbox profile state.

## Configuration anchoring

The default `$PROJECT_DIR/jailide.toml` must exist and have no symlinked path
component even when `--config` selects another file. Apply the same trusted
input classification to the selected file. Add default and selected
in-project files to final read-only paths; external selected files are outside
the project mount and are not represented as project-relative paths.

JailIDE trusts project files at invocation start. It does not persist hashes,
monitor Git/worktree changes, or distinguish legitimate host edits from other
writers. Every host caller that derives policy from an in-project file must add
that input to final read-only paths. Core cannot protect files it never sees.
State this limit in both products' threat-model guidance.

Core continues to protect its selected Containerfile independently. Equal final
core policy within one jailbox release is digest-equivalent regardless of raw
JailIDE file path or formatting.

## Security invariants

The development/proxy hardening, socket isolation, project-external runtime
state, proxy-only egress, and strict pinned SSH remain core-enforced. JailIDE
does not weaken or reproduce them. Every known in-project policy input is
validated and made read-only before launch.

## Tests and documentation

- Unit-gate tests use a fake jailbox executable to record exact command order,
  path reuse, environment construction, schema/connection parsing, failures,
  deterministic deduplication, editor setup-script materialization and
  byte verification, and absence of Podman/direct-state access.
- Editor tests install an exact built jailbox artifact and exercise supported
  VS Code/VSCodium versions, Remote SSH validation, first launch, reopen,
  stopped resume, editor-switch refusal, filtered/unfiltered/collision-fallback
  proxy settings, reduced core packages plus the JailIDE setup contribution,
  profiles, and anchored selected/default configs.
- Assertions prove no launch occurs after editor/preflight/config failure and no
  editor starts after core failure.
- README owns quick start, editor precedence/matrix, bootstrap destinations,
  profiles, proxy behavior, switch recovery, anchors, and integrity limits.

Run JailIDE `tests/run unit` and `tests/run editor`.

## Acceptance criteria

- Bare JailIDE follows the eight-step sequence with one executable and identical
  final environment for up and connection-info.
- Array composition is stable and unchanged inputs produce an unchanged digest.
- Direct launch supplies only the exact embedded editor setup script through
  `WRAPPER_SETUP` and proves that changing its bytes prevents attachment to
  older resources.
- Editor launch uses only validated machine fields; proxy settings exactly
  follow `proxy_url`.
- Every known policy input is anchored and protected, with the residual
  host-writer boundary documented honestly.
- Source/tests contain no Podman, core resource derivation, lifecycle repair,
  or any jailbox code dependency beyond the installed executable.

## Non-goals

- Automatic recovery, direct state inspection, Git-integrity monitoring,
  credential management, scheduling, or editor support outside the matrix.
