# 11.1. Go frontend and standalone core

## Intent

Replace the Bash frontend with a native Go `jailbox` executable and expose the
existing Bash machine interface as `jailcore`. Keep both in this repository and
one coordinated release. The frontend continues using the host's Podman stack
through core; this migration can be implemented, tested, and released on its
own.

VM execution is deferred in `12-go-vm-frontend-plan.md`. That specification
depends on this frontend and public core boundary; this plan has no dependency
on VM work. Runtime selection, VM provisioning, guest-engine access, an outer
proxy, and new cross-platform runtime claims belong to that later work. Do not
add a `RUNTIME` key, VM defaults, or unused backend abstractions here.

### User commands and machine boundary

- Keep `jailbox` for initialization, editor and headless launch, validation,
  status, shell/exec, stop, clean, installation management, help, and version.
  Preserve strict configuration syntax, defaults, editor selection, and the
  existing initialization template. Launch and attachment compose file policy;
  status and recovery retain core's inspection scope and remain usable without
  valid launch configuration. Do not infer the interface from environment
  variables or the presence of a configuration file.
- Move environment-driven machine callers to `jailcore COMMAND`. Preserve
  `JAILBOX_CONFIG_*`, command semantics, output framing, exit statuses,
  recovery scope, and core state/resource identities. Core never reads
  `jailbox.conf` and works without a Go frontend or toolchain. Treat the command
  migration as an incompatible API change with the required version bump and
  migration documentation; update repository callers in the same release.
- The frontend invokes an explicitly selected, compatible core installation
  through public CLI child processes, never an arbitrary executable on `PATH`.
  Check the supported core version range before dependent operations, with an
  explicit policy for source builds. Do not source core modules, inspect its
  private files, invoke Podman directly, or duplicate its lifecycle logic.
- Keep membership, defaults, and command declarations authoritative in
  `src/public-api.sh`, including which executable accepts each command.
  Generate Go's consuming data at build time. Missing per-member mappings must
  fail explicitly. Native Go execution must not run Bash just to discover its
  configuration grammar or command set.

### Preserve existing behavior

Port configuration parsing and environment composition, automatic protection
anchors, editor discovery, bootstrap-domain contributions, isolated editor
settings, and connection handling. Preserve both VS Code and VSCodium,
headless operation, and child-process arguments, working directory, streams,
exit status, and cancellation. Editor domains are added only to a nonempty
configured allowlist; headless launch adds none. Inherited machine policy must
not silently override the selected file policy.

Core continues owning containers, networks, SSH, home state, machine path
validation, and readiness. Preserve the read-only root, dropped capabilities,
no-new-privileges, absence of engine sockets, protected-path behavior, fresh SSH
credentials, strict host-key checks, and core-managed Tinyproxy. The language
migration changes neither image-build networking nor egress enforcement.

Keep current platform coverage explicit: Linux has real container/editor
acceptance; macOS retains portable coverage without claiming verified runtime
support. Keep the Go code buildable for Linux, macOS, and Windows and isolate
OS-dependent operations, but Windows runtime support and its installer are
deferred. Cross-compilation is not evidence of working containers or editors.

### Checkout, distribution, and acceptance

Provide one documented build-and-run workflow for a source checkout. Frontend
tests build and use the current tree's Go executable with matching core and
runtime assets. Core-only tests run the current Bash sources without building
Go. Never fall back to an installed or stale cached executable; the shared
`dev` version token is not a content identity. A failed build must not run an
older binary.

Users install verified native frontend artifacts together with the matching
core payload and version data, without a Go toolchain. Preserve source install,
update, uninstall, and retained user-state behavior, documenting the developer
toolchain required for source builds. Keep core independently usable and cover
both checkout and installed layouts. Existing sandbox resources remain
discoverable and recoverable after upgrading to the split executables.

Acceptance requires all four existing gates, including both editors on Linux.
No virtualization infrastructure or new user-facing gate is required:

- `portable` covers native Go tests, formatting/static checks, generated-data
  conformance, configuration and command behavior, packaging, and installation.
  Retain existing Bash/core coverage and macOS portable checks. Include Windows
  cross-compilation without treating it as runtime verification.
- `runtime` verifies unchanged container security and the Go headless workflow.
- `matrix` retains core's declaration-derived lifecycle and interruption tests.
  Test frontend delegation and failure propagation separately from core's
  resource-mutation matrix, without weakening either's assertions.
- `editor` verifies real attachment, bootstrap, settings isolation, and reopen
  behavior through the Go frontend for VS Code and VSCodium.

Cover strict parser equivalence, invalid/missing declarations, incompatible or
wrongly selected core installations, malformed and forward-compatible
connection records, and `jailcore` with no frontend installed. During
development use `tests/run dev` and affected suites, adding fast Go checks to
that workflow. CI and release acceptance retain all four gates.

## Implementation detail

Keep the Go module in `src/host/frontend/`, replacing its Bash implementation
while retaining ownership of frontend assets there. Keep the machine modules
in `src/host/core/`, runtime assets under `src/`, tooling under `scripts/`, and
test integration under `tests/`. Use ordinary Go build/test mechanisms rather
than introducing a runtime provider framework.

Required migration:

- Split `src/jailbox` and `src/host/cli.sh` into the Go frontend and standalone
  Bash core entrypoint. Remove replaced Bash frontend modules after moving
  their behavior and coverage. Preserve the template in
  `src/host/frontend/jailbox.conf.template` and the validation/trailing-field
  contract in `src/host/frontend/connection.sh` in their Go consumers.
- Extend `src/public-api.sh` and `scripts/gen-public-api.sh` for the two
  command surfaces and generated Go declarations. Keep core lifecycle
  membership and required test contracts authoritative; do not classify
  frontend delegation as ownership of container mutations.
- Update `src/install.sh`, `scripts/build-tarball.sh`, release validation, and
  layout tests for native frontend artifacts and the independently runnable
  core payload. Migrate the current packaging assumption that all of `src/`
  can simply be copied as an executable shell distribution. Keep the shell
  installer Bash 3.2-compatible and select artifacts by host OS/architecture.
- Update source callers, test fixtures, and developer commands that currently
  execute `src/jailbox` directly. Provide a shared way for frontend tests to
  prepare and locate the current build; keep core tests directed at core.
- Integrate Go tooling into `tests/run`, `scripts/lint.sh`, and
  `.github/workflows/test-gates.yml` while retaining shell discovery and core
  tests. Add the Go build/test toolchain to the root `Containerfile`; this
  does not grant the development container engine access.
- Update `AGENTS.md`, README, `CONTRIBUTING.md`, `ARCHITECTURE.md`, and the
  automation/development guides for the executable split, source workflow,
  packaging, and Go prerequisites. Replace Bash-only frontend ownership and
  entrypoint requirements with Go rules while preserving Bash core and shell
  installer requirements. Keep frontend delegation and core lifecycle test
  responsibilities distinct, and document actual platform coverage.
