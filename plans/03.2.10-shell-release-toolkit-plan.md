# 3.2.10. Shell Release Toolkit extraction and adoption

## Goal

Extract the distribution and release mechanics demonstrably shared by jailbox
and JailIDE into an independent MIT-licensed `shell-release-toolkit` product,
without integrating with a release host or adding a runtime or installation
dependency.

## Sequence

Implement after jailbox plans 03.2.01–03.2.09 form one reviewed coordinated
commit and before creating the reduced JailIDE repository in 03.2.11. Record
that exact jailbox commit as the extraction point. The toolkit candidate and
jailbox integration must pass locally before JailIDE inherits the coordinated
jailbox history. The extracted interfaces remain release candidates until
JailIDE becomes the second real consumer in 03.2.11. Plan 03.2.15 publishes and
pins the toolkit before either consumer product is released.

## Product boundary

The toolkit supports self-contained Bash command-line applications and their
declared static runtime resources. Its maintainer implementation may require
Bash 4.4, while generated installers retain their declared Bash 3.2 baseline.
The toolkit does not integrate with a release hosting provider and owns these
shared mechanisms:

- strict declarative product and package manifests;
- versioned single-root tarball construction and portable SHA-256 output;
- a self-contained streamed installer with verified release download, safe
  archive inspection, managed-target markers, atomic replacement and rollback,
  symlink publication, update, and scoped uninstall;
- `vMAJOR.MINOR.PATCH` validation, comparison, and bump calculation;
- clean-tree, branch/upstream, tag, and release-request safety;
- mapping a product-owned `added`, `removed`, or `unchanged` API classifier to
  a declared pre-1.0/post-1.0 bump policy;
- deterministic release-candidate assembly and verification; and
- deterministic generation of shell-source lint discovery and tested-version
  matrix rendering used identically by both consumers.

The toolkit knows no jailbox, JailIDE, Podman, SSH, editor, project-policy,
state-layout, compatibility policy, or product command semantics. It does not
own dependency installation, package-manager formats, publication, provider
credentials, installed runtime libraries, or a general CI framework.
Product-specific file inventories, public API declarations/classifiers, gate
commands, documentation, and dependency policy remain in each consumer.

A mechanism belongs in the toolkit only after a second real, independent
consumer demonstrates an identical reusable contract whose semantics can be
stated without reference to jailbox, JailIDE, or their ecosystem. Fixtures,
anticipated consumers, and configurable abstractions do not satisfy that rule.
Until then, the mechanism remains in its owning product. Applying this rule
excludes publication providers, provider adapters, ecosystem-specific shared
runtime mechanisms, and payload types not exercised by both initial consumers.

The `v0.1.0` reusable behavior is further limited to mechanics already working
in jailbox at the recorded extraction commit and portable without new product
design. Every such mechanism must trace to this source inventory:

- `install.sh`: streamed install, update, and uninstall; checksum verification;
  safe archive inspection; atomic replacement and rollback; marker ownership;
  and symlink publication;
- `scripts/build-tarball.sh`: versioned single-root archives and portable
  SHA-256 output;
- `scripts/release.sh`: version validation, comparison, and bumping; clean-tree,
  branch, upstream, and tag safety; classifier-to-bump mapping; and
  gate-before-tag ordering;
- `scripts/public-api-diff.sh`: the classifier mechanism only, with public API
  declarations remaining product-owned;
- `scripts/lint.sh`: shell-source discovery; and
- `scripts/gen-tested-matrix.sh`: tested-version matrix rendering.

Anything else is deferred from `v0.1.0` regardless of merit. New manifest,
lock, generation/checking, provenance, CLI, and self-hosting structure is
permitted only as extraction scaffolding needed to make those existing
mechanics independently consumable, deterministic, and auditable; it cannot
introduce new product behavior.

## Public identity and commands

Set the public identity to:

```text
display name:       Shell Release Toolkit
repository:         shell-release-toolkit
executable:         shell-release-toolkit
install directory: ~/.local/share/shell-release-toolkit/
first release:      v0.1.0
license:            MIT
```

Expose this command surface:

```text
shell-release-toolkit generate --manifest FILE --output DIR
shell-release-toolkit check --manifest FILE --output DIR
shell-release-toolkit package --manifest FILE --version vMAJOR.MINOR.PATCH --dist DIR
shell-release-toolkit suggest-version --manifest FILE --base REF
shell-release-toolkit release --manifest FILE [--first-major] [--dry-run] [--yes]
shell-release-toolkit --version
shell-release-toolkit --help
```

Each command accepts one manifest rather than discovering product state.
Generation/checking uses the explicit output tree; packaging uses the exact
already validated version and distribution directory; version/release commands
use the explicit base or manifest-declared release branch. `--help` and
`--version` are stable and configuration-independent. Machine modes keep stdout
schema-only and send diagnostics to stderr.

The toolkit uses its own manifest and unrelated fixture to exercise these same
public commands. Its first release is built and checked by the exact candidate
artifact; subsequent releases self-host through the prior immutable release.
Consumer repositories may execute a verified extracted artifact without
installing it globally.

## Repository and history

Create a clean locally excluded `shell-release-toolkit/` clone beneath this
checkout because only the current workspace is confirmed writable. Never add
it to tracked `.gitignore`, include it in jailbox discovery/package operations,
or let either product source it directly.

Build its history in an isolated clone from the recorded extraction commit.
Use history filtering only for `install.sh`, `scripts/build-tarball.sh`,
`scripts/release.sh`, `scripts/public-api-diff.sh`, their directly relevant
portable/lifecycle units, `scripts/lint.sh`, and
`scripts/gen-tested-matrix.sh`. Do not rewrite or modify the jailbox repository.
Follow the filtered history with one explicit
extraction commit recording the full source commit and original paths, then
genericize in ordinary reviewable commits. If a retained commit cannot stand
without unrelated source, omit that commit rather than importing the whole
jailbox history; record the omitted origin in toolkit provenance documentation.

The toolkit has its own README, MIT `LICENSE`, changelog, `AGENTS.md`,
contribution guidance, version source, tests, release scripts, and exactly one
user-facing `portable` test gate. No remote, push, tag, or release is created
without separate explicit authorization.

The README normatively defines a toolkit-conforming repository as having a
declarative product manifest; a generated self-contained installer;
API-diff-driven SemVer with a declared pre-1.0/post-1.0 bump policy; generated
lint discovery and tested-version matrix rendering; one portable gate; and
committed generated outputs pinned by an immutable toolkit lock.

## Declarative consumer contract

Define one strict, non-evaluated manifest format for immutable product facts:
product/display names, executable and marker names, release location/assets,
install/data/bin defaults and supported overrides, required bundle paths,
installed paths, executable paths, archive paths, minimum installer/maintainer
Bash versions, bump-policy mode, declared shell source classes, and tested
version/matrix inputs.
Repeated path records preserve declaration order. Reject unknown/duplicate
scalar fields, missing required fields, absolute or traversing archive paths,
unsafe names, conflicting destinations, and any manifest capable of escaping
the staged archive or managed install root.

The only executable extension point is a product-owned API-classifier command
whose stdout is exactly `added`, `removed`, or `unchanged`; reject extra output,
failure, or any other value. The toolkit invokes no arbitrary sourced hooks.
Workflow callers supply explicit gate commands and receive no implicit write
permission.

Generated self-contained product files carry the exact toolkit version, full
commit, and manifest digest in a header. Generation is deterministic and
atomic. Consumer portable gates obtain the exact pinned toolkit artifact,
verify its SHA-256, regenerate into temporary storage, and compare byte for
byte. Generated outputs are committed so checkout, packaging, installation,
update, and uninstall never require network access to the toolkit.

Each consumer records one lock containing the canonical toolkit repository,
release version, full commit, release-archive SHA-256, and manifest digest.
Normal product development and release use only that immutable lock. A tooling
update is an explicit reviewed change containing the lock, manifest, generated
outputs, and resulting tests; it cannot publish a consumer automatically.

Generate product-local `scripts/lint.sh` and
`scripts/gen-tested-matrix.sh` from those declarations. Their shared discovery,
coverage-failure, rendering, and check behavior belongs to the toolkit and is
tested identically by jailbox and JailIDE. Generated copies are not editable
consumer implementations. Each product still owns `tests/run`, `versions.env`,
dependency/setup scripts, gate membership and commands, workflow permissions,
matrix values, and every source-category declaration. Provider workflows call
the generated tools but remain consumer-owned.

## Adoption by another repository

A new consumer declares its immutable product/package facts, shell source
classes, tested-version inputs, bump policy, product-owned API-classifier
command, and explicit gate commands in its manifest. It receives a generated
self-contained installer, package frontend, lint discovery, and tested-version
matrix renderer. Its file inventory, public API declaration, gate membership
and commands, version/matrix data, dependency setup, workflows, permissions,
and publication remain product-owned.

The consumer commits generated outputs and an immutable lock naming the
canonical toolkit repository, release version, full commit, release-archive
SHA-256, and manifest digest. Its portable gate verifies the artifact, performs
deterministic regeneration in temporary storage, and compares every output byte
for byte. Adoption of an already-supported contract requires no toolkit change.
A new consumer does not justify expanding toolkit scope; any proposed mechanism
must independently satisfy the product-agnostic two-real-consumer rule.

## Installer and release security

The streamed installer remains parseable by macOS Bash 3.2. Maintainer commands
may require Bash 4.4 or newer. Preserve jailbox's current secure installer
behavior while making product identity declarative: validate the complete
download and archive before target mutation, never trust archive paths or
checksums by position, refuse broad/unmanaged/symlinked targets, use
collision-resistant same-parent staging and backup paths, restore on failure,
publish the executable link only to the owned target, and uninstall only the
matching marker/link. Product A can never replace or remove product B.

Release tooling never creates a version tag or final candidate before the
supplied complete gate succeeds. It requires the declared release branch at
the exact upstream head, distinguishes local from remote Git tags, and refuses
ambiguous or already tagged versions. It stops after producing and verifying
the local candidate, version, checksum, and tag intent. Provider-specific
upload, release creation, credentials, permissions, and already-published
checks belong to each consumer's release workflow. Toolkit code receives no
publication credentials and cannot publish or elevate caller permissions.

## Independent proof and tests

Use minimal fixtures with different names, paths, file inventories, and API
changes to test failure cases and deterministic mechanics. Fixtures are test
inputs, not evidence for admitting a feature to the product boundary. The
portable gate covers:

- manifest grammar and all unsafe path/name/conflict cases;
- deterministic generation and package bytes;
- Linux/macOS checksum portability and Bash-version syntax;
- local-bundle and streamed verified installation;
- new install, managed update, rollback at each publication boundary, and
  interrupted cleanup;
- malicious checksums and empty, multi-root, traversing, link, duplicate, and
  malformed archives;
- refusal of `/`, home, unexpected basenames, symlinked and unmanaged targets;
- exact marker/link ownership and cross-product uninstall isolation;
- SemVer boundaries, classifier failures, bump policies, branch/upstream/tag
  refusal, and no tag on gate failure;
- fixture packaging/install/update/uninstall from the produced artifact.

Tests use temporary explicit targets and local HTTP/fixture remotes where
needed; they never mutate real user installation roots, tags, or releases.

## Jailbox adoption

Replace the implementation in root `install.sh`, `scripts/build-tarball.sh`,
and generic portions of `scripts/release.sh` with deterministic toolkit outputs
and a jailbox-owned manifest/classifier. Preserve the public install/update/
uninstall interface, paths, archive names, release initiation, version stamping,
and 03.2.01 bump policy. Keep `host/public-api.sh` and its semantic extraction
product-owned. Replace editable generic implementations of `scripts/lint.sh`
and `scripts/gen-tested-matrix.sh` with deterministic toolkit outputs, while
keeping jailbox's gate dispatcher, version/matrix data, setup scripts, and
workflows product-owned. Remove generic implementation tests only after
equivalent toolkit tests exist; retain jailbox integration tests for its exact
manifest, package contents, version stamp, streamed/local lifecycle, target
isolation, lint/matrix declarations, and release-policy mapping.

Until toolkit `v0.1.0` is published in 03.2.15, integration uses one recorded
local candidate archive, full commit, and SHA-256 from the nested clone. Build
that candidate archive with the final `v0.1.0` version stamp, and generate every
candidate consumer file with that same version and commit before comparison. It
may not read or execute the toolkit worktree directly. The final pin replaces
the candidate coordinates and must regenerate byte-identical consumer outputs
or the affected plans and gates are rerun.

Run the toolkit portable gate and jailbox `tests/run portable`. Also run
jailbox runtime when adoption changes any packaged runtime path or artifact;
otherwise packaging/install lifecycle coverage remains owned by portable.

## Acceptance criteria

- Jailbox and JailIDE both exercise every toolkit mechanism with identical
  semantics; fixtures supplement but do not substitute for those two real
  consumers.
- The toolkit retains relevant security history and records exact provenance
  without importing unrelated jailbox history.
- Consumers are self-contained and have no installed/runtime toolkit
  dependency or source-checkout dependency.
- Immutable locks, deterministic generated files, and product integration tests
  make toolkit updates explicit and auditable.
- The README defines the complete toolkit-conforming repository standard, and
  the documented adoption path can apply it without modifying the toolkit.
- Jailbox's observable installation, package, release, and bump behavior is
  unchanged except for recorded toolkit provenance.
- No remote mutation or release occurs in this implementation plan.

## Non-goals

- Running the toolkit itself under shells other than its documented Bash
  versions; non-Bash, compiled-executable, or arbitrary mixed-file-tree
  payloads; building consumer payloads; system package formats, Homebrew,
  Debian/RPM repositories, OCI publication, release-provider integration, or
  arbitrary project hooks.
- Runtime libraries or Jailbox/JailIDE-specific utilities; shared product
  policy, configuration parsers, path/identity validation, diagnostics, command
  discovery, state, editor/container setup, or coordinated release ownership.
- A subtree, submodule, floating dependency, dynamically downloaded runtime
  library, or automatic consumer upgrade.
