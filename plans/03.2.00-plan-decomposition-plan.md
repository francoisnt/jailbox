# 3.2.0. Decompose the JailIDE split plan into implementable chunks

## Goal

Replace the single 1069-line `03.2-jailide-repository-split-plan.md` with a
short charter plus fourteen sub-plans, each of which can be read and fully
understood in one sitting before implementing it, and rewrite plans 3.1 and 4
through 8 so the active plan set describes the post-split products
consistently.

No active plan may retain the superseded file-based jailbox configuration
model, editor behavior in jailbox, single-container digest contract, or attach
behavior that bypasses the shared compatibility validator.

This is a documentation-only reorganization. It settles where the existing
requirements live; it changes no product behavior, no source file, and no test.
Every decision already settled in 3.2 survives the move unchanged.

## Sequence

Order 3.2.0. It precedes release-order step 1 of the split, because that step
("rewrite plan 3.1") is itself one of the outputs described here. No
implementation work may begin until this decomposition is complete, since the
sub-plans are what gets implemented.

This document must be tracked and committed before decomposition begins,
because its required final move into `plans/archive/` can only preserve history
if `git mv` operates on a tracked file. A partially staged copy does not
satisfy this: the complete current file is staged and committed as one
prerequisite planning commit. That commit is a precondition of the work, not
part of it; the "do not stage or commit" editing rule below governs the
decomposition's own output.

When the decomposition is complete and its audit recorded, `git mv` this
document into `plans/archive/` like any other completed plan. It is the record
of how the monolith was allocated and why, which the resulting plan set does
not restate.

## Repository layout

### Current state

The checkout at `~/project` is the jailbox repository and remains so. Its
history, remote, and identity are untouched; nothing is renamed, rewritten, or
force-pushed, and jailbox keeps every file it still owns after the split.

The JailIDE working clone already exists and is correctly configured. It is not
future work, and the plan set must not describe creating it:

- it lives at `~/project/jailide`, cloned from this repository so that the
  editor, profile, configuration-format, and editor-gate files carry their
  existing history rather than being reconstructed;
- its worktree is clean and it shares the current jailbox commit;
- it is excluded from the jailbox worktree through `/jailide/` in
  `.git/info/exclude`, which is developer-local state, not a product ignore
  rule; and
- it has a fetch-only `jailbox-upstream` remote and no `origin` yet.

Nothing may add `jailide/` to jailbox's tracked `.gitignore`. A nested
developer checkout is not a permanent property of the product, and `.gitignore`
is shipped configuration. The existing local exclude is the correct mechanism
and is already working.

### Synchronization before reduction

The clone still points at the commit it was taken from, which predates every
core change in 03.2.01 through 03.2.09. Reducing it at that commit would fork
the two repositories before the shared work exists, and JailIDE would silently
miss the release-version stamping, bump-policy, and public-API changes it is
required to inherit and retarget.

`03.2.10` must therefore import the coordinated core commit before it reduces
anything:

- fetch from the local jailbox repository at `~/project`, not from
  `jailbox-upstream`. The coordinated commits are unpublished, so the remote
  cannot serve them, and `jailbox-upstream` stays fetch-only and untouched;
- import the exact jailbox commit that contains 03.2.01 through 03.2.09, named
  by its full identifier rather than by a branch tip that can move;
- require JailIDE's current `HEAD` to be an ancestor of that commit and advance
  to it with a fast-forward-only operation, so no JailIDE-specific history or
  merge commit exists before the declared divergence point; and
- record that identifier in the JailIDE repository so the coordinated pair
  stays identifiable after the histories diverge.

That exact commit is the divergence point. After JailIDE reduction begins, do
not merge, fast-forward to, or otherwise import a later jailbox commit
wholesale: doing so could reintroduce deleted core files or entangle the two
products' histories. Test JailIDE against later coordinated jailbox candidates
through the installed local package or prerelease artifact. When a later
jailbox interface change requires a JailIDE source change, port that specific
change explicitly in a JailIDE commit and record the tested jailbox commit or
artifact version in the coordinated handoff. `03.2.14` verifies the divergence
point and the final tested pair as part of the cutover.

### Required end state

The nested location is temporary and must not survive into either release, but
it must survive all the way through implementation. `~/project` is the only
confirmed mounted tree, so a clone moved outside it becomes unreachable to the
agent doing the work. The clone therefore stays nested through 03.2.10 to
03.2.13, and `03.2.14` owns the move as the last step before the JailIDE
release:

1. move the clone host-side, out of the jailbox worktree, to a sibling checkout
   beside the jailbox repository at a path the user selects;
2. add the standalone JailIDE `origin` and confirm `jailbox-upstream` stays
   fetch-only, so the split never pushes to jailbox;
3. remove the `/jailide/` line from `.git/info/exclude`, since nothing nested
   remains to exclude; and
4. confirm that both repositories' complete gate sets behave identically before
   and after the move, proving that nothing depended on the nested path.

Until then `03.2.10` owns the nested-state obligations. No jailbox source,
test, workflow, or document may reference the clone at runtime, and `03.2.10`
must confirm that ShellCheck discovery in `scripts/lint.sh`, unit-suite
discovery under `tests/`, and packaging in `scripts/build-tarball.sh` never
reach it. JailIDE's editor gate installs a built jailbox package or prerelease
artifact rather than reading `~/project` directly, so the installation boundary
is exercised exactly as a release would exercise it, from either location.

`03.2.10` also owns reducing the clone to the JailIDE surface. That is a
selective removal, not a blanket one: delete the files jailbox alone owns —
`jailbox`, `host/`, `container/`, jailbox's tests, and the inherited `plans/`
directory, which is replaced by JailIDE's own plan series — while retaining and
adapting the repository infrastructure both products genuinely share, including
`scripts/release.sh`, `scripts/public-api-diff.sh`, `scripts/lint.sh`
discovery, the CI gate scaffolding, `install.sh`, and contribution guidance.
Retained infrastructure is retargeted at JailIDE's own surface rather than
rewritten from nothing, which is the same decision that makes JailIDE reuse the
public-API diff and automatic bump machinery.

## Chunking rules

- One chunk answers one review question and has a single acceptance surface.
  There is no minimum length: a chunk is as long as its contract requires and
  no longer. Cap it at roughly 220 lines, and if it passes 260 while being
  written, split it by observable behavior rather than shortening away security
  rationale or acceptance criteria.
- Each chunk is a complete plan in the house style: `## Goal`, `## Sequence`
  with its prerequisites, behavior sections, the security invariants that
  behavior can affect, tests and documentation, explicit migration and removal
  steps naming affected symbols and files, `## Acceptance criteria`, and
  `## Non-goals`. Per `AGENTS.md` it must describe all work required to move
  the repository from its current state to the state that chunk defines.
- A chunk must be understandable and implementable without reading the
  monolith, and without resolving a contradiction left in another plan.
- Each chunk is independently gate-runnable at its position in the sequence. A
  chunk never leaves the tree in a state where a documented command is missing
  its enforcement.
- Single source of truth. Each normative rule and its detailed acceptance
  criteria live in exactly one plan. Other plans state a dependency and may
  keep a consumer-level assertion, but never restate the owning contract. The
  one deliberate exception is a security invariant a chunk can violate, which
  that chunk restates.
- No history of the discarded direction. Text moved out of 3.2 is rewritten as
  though the combined document had never existed, matching the `AGENTS.md`
  plan-authoring rule.
- Decomposition is not redesign. If splitting a section exposes a
  contradiction, gap, or ordering conflict inside 3.2, stop and raise it as an
  explicit question. Do not resolve it silently inside a chunk, and do not
  leave a marker in the plan text to resolve it later.

## Ordering constraints the split plan implies

The order above is not arbitrary, and the charter must state these three
dependencies directly rather than leaving a reader to infer them from numbers:

- **Version before digest.** The digest hashes the exact jailbox release
  version, so package-time version stamping and `--version` must land before
  the digest exists. This is why 03.2.01 precedes 03.2.02.
- **Digest before label removal.** The configuration digest is what replaces
  `jailbox.project` as the reuse gate. Removing the ownership label first would
  leave a release in which nothing gates reuse, so 03.2.03 follows 03.2.02.
- **JailIDE before core removal.** The removals in 03.2.13 are evaluated only
  once their JailIDE replacements exist and pass their gates, matching
  release-order steps 5 and 7, so 03.2.10 through 03.2.12 precede it.

The end-state jailbox surface is nonetheless stated in the charter, which every
implementer reads first: config files, `init`, `--config`, `EDITOR`,
`JAILBOX_EDITOR`, editor discovery and launch, profiles, bootstrap-host
composition, `ssh-config`, and the editor gate all leave jailbox; SSH and the
generic runtime prerequisites for SSH-attached development tools stay. Knowing
the target early keeps earlier chunks from building on surfaces that are about
to disappear, while 03.2.13 remains the only plan that executes and gates the
deletions.

## What stays in the charter

`03.2-jailide-repository-split-plan.md` is rewritten in place, keeping its
filename and history, as a charter of at most 220 lines containing only: the
goal and dependency direction, the ownership boundary for both products and
the end-state jailbox surface above, the repository layout summarized in one
short paragraph, the cross-repository coordination point for remote IDE-server
runtime prerequisites, the seven security invariants, the ordered index of
sub-plans with the dependency constraints above, and the non-goals.

It carries no configuration grammar, lifecycle state table, machine-output
schema, label name, migration procedure, source file path, test matrix, or
acceptance criterion. Where a sub-plan is authoritative for its scope, the
charter is authoritative for the boundary, the invariants, and the order.

## Chunk ownership

Each entry states what distinguishes the chunk and, where it is easy to get
wrong, what the chunk does *not* own. The mapped source region supplies the
content.

### 03.1 and the temporary file compatibility adapter

`03.1` is a full rewrite, not an edit: the environment becomes the only
canonical configuration channel. Retitle and `git mv` the file. Remove the
override framing, the precedence ladder, selected-file identity, `EDITOR`,
`JAILBOX_EDITOR`, `JAILBOX_CONFIG_EDITOR`, comma-separated arrays, override
diagnostics, and the non-goal excluding per-item environment variables.
Preserve the exact index grammar, 256-member limit, unknown-name rejection,
unset and default semantics, declaration integrity, and complete validation
before mutation. Limit configuration-consuming commands to `up`, `exec`,
`shell`, and `connection-info`.

Core still reads `jailbox.conf` between this chunk and 03.2.13, so `03.1` must
define that window explicitly rather than leaving a plan that removes file
handling while the file still works. It defines a temporary file compatibility
adapter with these properties:

- the adapter is the only remaining file-reading code path, and it converts a
  parsed file into exactly the same final values the environment interface
  produces, mapping file arrays onto the indexed member form;
- there is one validation path. The adapter feeds the environment-shaped
  validator and never validates separately, so file-configured and
  environment-configured launches cannot diverge;
- the adapter is a fallback, not a layer. No `JAILBOX_CONFIG_*` variable
  present means the file supplies the configuration; any present variable means
  the environment is the complete configuration and the file is not read. No
  precedence, merge, or per-key override vocabulary returns;
- no end-state acceptance criterion depends on the adapter, and no other chunk
  may build on it; and
- `03.2.13` deletes the adapter, and that deletion changes no behavior for a
  caller that already sets the environment.

following.

Narrative coverage:

- every narrative line of the current 3.2 — 1 through 919 and 1057 through
  1069 — claimed by exactly one destination in the table above, with the three
  content-level splits resolved sentence by sentence.
