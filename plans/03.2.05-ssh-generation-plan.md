# 3.2.05. SSH generation and resume validation

## Goal

Make one development-container object one atomic SSH generation.

## Sequence

Implement after identity and before constrained up.

## Behavior

Before container creation atomically prepare fresh client/server pairs,
`authorized_keys`, pin, and client config. The generation exists only with
its container; failure removes only invocation-created artifacts. No-op/resume
preserve identities. Resume validates pairs, pin, config, mount, ownership,
modes, regular non-symlink types, runtime material, and strict checking before
start; it never repairs a surviving generation. Stop ends it and next up rotates
both identities.

Split `host/ssh.sh` into explicit creation and resume validation. Resume also
verifies expected network/home attachments, supporting resources, generated
config, matching client/server pairs, mount source, and container runtime
material before start, without printing key contents.

Client private key, pin, and config stay host-only. Mount only server material
and authorized keys read-only. Preserve `--userns=keep-id` for StrictModes;
mutable daemon state such as `sshd.pid` uses the `/run` tmpfs. Entrypoint
validates and starts sshd but never mutates authentication files. Container
roots, capabilities, no-new-privileges, and socket isolation remain unchanged.

Any future user-namespace change must provide equally strict ownership and pass
the same runtime assertions. Update `container/entrypoint.sh` and
`container/setup.sh`: pairs are created once per container generation, not per
launch. The sandbox may read its server key for sshd but cannot use it to
authenticate to the host.

## Tests and documentation

Portable/runtime coverage proves rollback, preservation, rotation, all damaged
state failures, read-only mounts, absent client state, ownership/modes, and
strict pinning. Incompatible ownership fails readiness without chmod/chown or
relaxed StrictModes. Update setup, entrypoint, runtime rationale, SSH units, and
runtime tests.

## Acceptance criteria

- Each new container has fresh identities; resume preserves and validates them.
- Failed creation leaves no partial new material.
- StrictModes works through keep-id without writable server or mounted client
  secrets.
- Every connection enforces strict pinned host-key checking.

## Non-goals

- Resume rotation/repair or moving SSH out of core.
