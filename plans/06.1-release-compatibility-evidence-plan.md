# 6.1. Per-release compatibility evidence

## Intent

Keep test results on `master` in `compatibility/master.csv` and
`compatibility/releases.csv`. The first records development results for reuse;
the second records release attempts and results. Show successful release
combinations in GitHub release notes, linked from README. Move routine release
testing to its successor while keeping older results.
Select GitHub's designated latest published release, excluding drafts and
prereleases; no eligible release means no release test, not a pass.

- Check daily for latest stable editors/extensions, matched editor servers,
  upstream Podman, current Bash, and existing container distribution families.
  Test these together, preserving existing platform/editor coverage and Bash 4.4.
  Other packages follow their distributions' stable channels. Verify installed
  versions and require an installation method compatible with the runner. Report
  unavailable candidates as setup failures; do not silently substitute older ones.
  Latest container candidates are development images; the shipped proxy image
  keeps each target's embedded pin. Record both image roles for reuse checks.
- Run the development canary on `master` daily, even without dependency updates.
- For the latest release, consult its CSV and test only a new combination,
  a new release without a qualifying result, or an explicit rerun. Without an
  explicit rerun, skip unchanged attempted combinations, including failed setup,
  failed tests, and interrupted attempts. Image digests, runner revisions,
  and package inventories are observations, not release-test triggers.
  The lookup key is release identity (version tag and resolved commit) plus
  editor, extension, Podman, current Bash, and development-distribution versions.
- Resolve target commits once per attempt. Use each revision's own tests by
  default; record any necessary, narrowly scoped harness fixes. Released runtime
  code and embedded pins remain unchanged. An unusable harness is not a pass.
- Run all four gates. When both targets have identical commits, dependency
  combinations, and required coverage, run once and report for both.
- Reuse only complete passing results recorded by our shared gates for the exact
  commit, observed dependency combination (including development and proxy image
  identities), and required coverage, with no later unresolved failure. Missing
  proof at release publication requires fresh gates. A pin-bump commit is a
  different commit. Every release builds and validates its versioned
  package before tagging and publication.
- Seed a new release's list from qualifying canaries for its exact commit,
  copying development rows into the release CSV with original dates and test
  identities; otherwise test its first combination.
  Non-canary results may satisfy release gates but are not listed as canaries.
- Record attempts in the appropriate CSV with target/version, date, tested commit,
  run type, unique execution/attempt identity, requested and observed dependency
  versions, image identities, platforms, coverage, per-gate results, and outcome.
  CI links are optional references. Deduplicate by target plus execution/attempt
  identity; interrupted attempts remain incomplete.
  Unreadable history is an error, not permission to assume a pass or an untried set.
  Generate notes from successful release rows, listing each combination once.
  Historical passes do not guarantee other mixtures or today's environment.
- Keep failures visible in Actions and target-specific issues until resolved;
  serialize CSV and note updates, preserve unrelated work, and allow reporting
  retries without rerunning tests. Publish results after testing; combine CSV and
  eligible pin updates in one commit where possible. If `master` moved, append results safely
  without bypassing the pin-update guard. Record the tested commit, not the
  reporting commit. In-flight runs report to their original release. Only
  development success may advance pins under the existing tested-commit guard;
  it cannot clear failures of different released code.

No exhaustive version matrix, new test mode, dependency-floor changes, frozen
environments, or separate evidence archive. Existing security and platform
coverage remain unchanged; Linux/portable results do not prove macOS runtime.

This plan owns scheduled current-Podman testing and host/engine result recording
previously assigned in backlog.md and supported-versions.md. Minimum-version
selection, enforcement, and verification, plus broader host coverage, remain there.

Acceptance requires proof of scheduling/skips, identical-target reuse, rejection
of partial or mismatched evidence, correct release transitions, explicit reruns,
and CSV/note deduplication without content loss. Prove release tests cannot use a
fix present only on `master`, and validate both publication paths. CSV validation,
reuse, release scheduling, and list generation must work from a checkout without
CI history.

## Implementation detail

- Extend .github/workflows/canary.yml and scripts/resolve-latest-versions.sh
  beyond their editor-only resolution and single development-pin comparison.
  Adapt tests/ci/setup-linux.sh's default-repository Podman installation and
  test image preparation to use the selected candidates without changing releases.
- Extend .github/workflows/test-gates.yml to select the subject and report commit,
  observed versions, coverage, and job results. Replace unconditional gate
  execution in .github/workflows/release.yml with verified reuse or fresh gates;
  update tests/unit/release-workflow.sh accordingly.
- Keep CSV processing in repository scripts; CI handles execution and publishing.
- Adapt scripts/canary-report.sh's version-only issue matching for separate
  targets and successful-combination note updates. Limit writing permissions to
  reporting jobs. Update README and scripts/gen-tested-matrix.sh to distinguish
  release history from development pins.

Run development checks and affected suites, then all four gates and generated-file
checks for acceptance. Record any limits on real-platform or live-reporting checks.
