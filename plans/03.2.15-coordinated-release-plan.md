# 3.2.15. Coordinated validation, repository moves, and releases

## Goal

Prove the final `shell-release-toolkit`, `jailutils`, jailbox, and
JailIDE repositories through their artifact boundaries, move all extracted
repositories out of the temporary nested checkout, establish safe remotes, and
publish the toolkit and push the tested common commit before releasing the two
user products.

## Sequence

Run after 03.2.14 and before continuing plans 5–8. This plan owns operational
cutover and immutable final pins only; product behavior must already satisfy its
owning plan. Publishing, remote creation, pushes, tags, and host-side moves each
still require the user's explicit authorization and supplied destinations.

## Coordinated identifiers and artifacts

Record in handoff/release evidence:

- the 03.2.10 toolkit extraction source commit, filtered-history head, final
  candidate commit, local candidate archive, and SHA-256;
- the 03.2.10.1 common extraction source commit, filtered-history head, final
  candidate commit, and both consumer gitlinks;
- the full jailbox divergence commit imported by JailIDE in 03.2.11;
- the final jailbox candidate commit after 03.2.14;
- the final JailIDE candidate commit;
- both consumers' candidate toolkit locks and generated-file manifest digests;
- the ordered caller-setup content digests, JailIDE setup-script digest, and
  final wrapper-image cache identity;
- the exact jailbox prerelease artifact filename, SHA-256, and reported version
  installed for JailIDE testing; and
- JailIDE's declared compatible jailbox range.

Build and test through archives installed into isolated prefixes. Neither
consumer may execute or source the toolkit or jailbox worktree. Where a later
core interface change requires JailIDE adaptation, identify the explicit
JailIDE commit; never merge post-divergence jailbox history wholesale.

## Pre-move gate sequence

Against the coordinated local candidate artifacts:

1. run the complete toolkit `tests/run portable` gate, including its unrelated
   fixture lifecycle;
2. run the complete common `tests/run portable` gate;
3. run complete jailbox `tests/run portable` and `tests/run runtime`;
4. run complete JailIDE `tests/run portable` and `tests/run editor`; and
5. record skips only where a gate itself reports a supported platform skip,
   never as a passing complete gate.

This is the final local-candidate rerun after core removal. Compare it with the
pre-removal run required by 03.2.14 so the evidence proves JailIDE replacements
worked before deletion and still work after it.

## Host-side repository moves

The nested locations cannot survive release. Ask the user for distinct sibling
target paths and repository URLs. With all four worktrees clean and gates
recorded:

1. move complete `shell-release-toolkit/`, `jailutils/`, and
   `jailide/` Git working copies to their selected sibling paths, preserving
   `.git` directories and permissions;
2. verify all three moved HEADs and their extraction/divergence records are
   unchanged;
3. add each standalone repository's supplied `origin` fetch/push URL;
4. in JailIDE retain `jailbox-upstream` with its existing fetch URL and a
   disabled push URL, and prove a normal push cannot target jailbox;
5. verify both consumers' committed common-submodule URL is the canonical
   remote, remove any local candidate override, preserve the exact gitlink, and
   prove non-recursive clean initialization from that remote;
6. remove exactly the toolkit, common, and JailIDE entries from jailbox
   `.git/info/exclude`; and
7. verify no tracked `.gitignore` in any product gained a nested-checkout rule.

Do not perform any move or remote mutation without the user's selected path and
URL. Do not push during the move.

## Post-move independence proof

From each standalone checkout:

- confirm clean status, expected branch/HEAD, remotes, and no nested copy;
- rebuild candidate packages/generated files through installed or extracted
  candidate artifacts, not sibling worktrees;
- rerun the toolkit/common portable gates and all four jailbox/JailIDE gates;
- search all four repositories for old nested absolute/relative paths;
- prove discovery, packaging, tests, and workflows cannot descend into sibling
  repositories; and
- compare gate results, packages, generated outputs, and checksums with the
  pre-move evidence.

Any location-dependent result blocks release and is fixed in the owning
repository, followed by the complete affected gate set.

## Publication and final consumer pins

Before any explicitly authorized push, tag, or release, display all four
repositories' remotes and exact commits. Each repository pushes only to its own
origin. Never push toolkit, common, or JailIDE commits or tags to jailbox; never
push consumer commits to the toolkit or common origin.

Release `shell-release-toolkit` `v0.1.0` first. Verify its tag maps to the
tested commit and independently verify the published archive checksum and
contents.
In jailbox and JailIDE, replace local candidate coordinates with the canonical
repository, `v0.1.0`, full release commit, archive SHA-256, and manifest digest;
regenerate all outputs, including lint and tested-matrix tools, from the
published archive. They must be byte-identical to the candidate outputs; if not,
review the diff as a product change and rerun every affected gate.

Commit the final locks/generated files separately in each consumer, then rerun
jailbox portable/runtime and JailIDE portable/editor using only the published
toolkit artifact. Toolkit publication never publishes a consumer automatically.

Push `jailutils` to its canonical remote at the tested commit and confirm the
committed submodule URL resolves. Keep both consumer gitlinks byte-for-byte
unchanged, initialize them from the canonical remote, verify the packaged common
metadata, and rerun both consumers' complete gates. Pushing common code never
publishes a consumer automatically.

Release the final environment-only jailbox version next. Verify its published
artifact checksum and `--version`, install that exact artifact, and rerun
JailIDE's compatibility check and complete gates if published bytes differ from
the prerelease artifact. Release JailIDE `v0.1.0` last against that exact
jailbox version, the published toolkit pin, and the unchanged published
`jailutils` gitlink.

No stable jailbox release supports both configuration interfaces. No transition
release, duplicate editor implementation, floating toolkit reference, or
shared installed library is published.

## Release notes and documentation

Toolkit notes document its Bash-application and provider-independent scope,
two-real-consumer admission rule, manifest and generated-file contracts,
toolkit and installer Bash compatibility, installer threat model, immutable
consumption, consumer proof, and extraction provenance.

Common documentation describes its narrow Jailbox/JailIDE boundary,
record-envelope API, submodule consumption, packaged-copy model, commit/digest
identity, tests, and extraction provenance.

jailbox notes:

- removed `jailbox.conf`, `init`, `--config`, editor interfaces, bare editor
  launch, profiles, and `ssh-config`;
- direct human editor users to JailIDE and environment callers to the canonical
  interface;
- document the toolkit only as maintainer/release provenance, not a user
  dependency;
- document trusted ordered wrapper setup, root build-time execution, content-
  based compatibility/cache identity, and the absence of runtime script access;
- explain stop, ephemeral/persistent home behavior, malformed-label
  preservation, and clean data loss; and
- state that the version-bound digest makes upgrades require stop/up, except a
  persistent/legacy-to-ephemeral change requires warned clean/up.

JailIDE notes document v0.1.0 installation, compatible jailbox version, config
and init, its editor-dependency setup contribution, editor matrix, profiles,
proxy/bootstrap behavior, legacy cleanup, lack of automatic jailbox
installation/migration, and no user-facing toolkit dependency. Add cross-links
only after standalone repository URLs exist.

## Security invariants

All product security invariants are verified through immutable artifacts before
and after relocation. Toolkit generation cannot change product policy or gain
consumer publishing authority. Consumer installers remain self-contained,
cross-product target isolation is proven, and remote configuration prevents
cross-repository pushes. No step reintroduces a file interface or editor logic
in core, direct Podman access in JailIDE, a container-engine socket, a floating
build input, or a dynamically downloaded runtime library.

## Acceptance criteria

- Extraction/divergence/final commits, every artifact checksum/version, both
  toolkit locks, the JailIDE compatible range, and all complete gates are
  recorded.
- All three standalone moves preserve history and HEAD, establish correct
  origins, retain only the intended fetch-only upstream, and remove local
  excludes.
- Toolkit and common portable gates plus all four consumer gates behave
  identically before and after relocation, and published toolkit regeneration
  is byte-identical or handled as a reviewed product change.
- The reduced jailbox wrapper lacks editor-only packages, while the exact
  JailIDE setup contribution restores every supported editor gate without
  changing jailbox-owned SSH, egress, or runtime hardening.
- No runtime/build/test/document path depends on nesting or a sibling worktree.
- Shell Release Toolkit releases first, `jailutils` is pushed at the tested
  commit before jailbox releases second, and JailIDE releases last. Each release
  goes only to its own remote and names the exact immutable dependencies tested.
- Release notes cover toolkit provenance, removed interfaces, migration,
  persistence, and destructive recovery without presenting toolkit as a user
  prerequisite.

## Non-goals

- New product behavior, automatic dependency installation, a dual-interface
  transition release, shared runtime utilities, floating references, or
  wholesale post-divergence merging.
