# 3.2.15. Coordinated validation and releases

## Goal

Prove the final jailbox and JailIDE repositories against each other through
installed artifact boundaries only, establish safe remotes, and release
jailbox before JailIDE.

## Sequence

Run after 03.2.14 and before continuing plans 5–8. This plan owns operational
cutover and final pins only; product behavior must already satisfy its owning
plan. Remote creation, pushes, tags, and releases each still require the
user's explicit authorization and supplied destinations.

## Coordinated identifiers and artifacts

Record in handoff/release evidence:

- the final jailbox candidate commit after 03.2.14;
- the final JailIDE candidate commit, Go toolchain version, and module
  dependency pins;
- the exact jailbox prerelease artifact filename, SHA-256, and reported
  version installed for JailIDE testing;
- JailIDE's declared compatible jailbox range; and
- the ordered caller-setup content digests, JailIDE setup-script digest, and
  final wrapper-image cache identity.

Build and test through archives installed into isolated prefixes. Neither
product may execute or read the other's source checkout. Where a later core
interface change requires JailIDE adaptation, identify the explicit JailIDE
commit and the newly targeted jailbox artifact.

## Final gate sequence

Against the coordinated local candidate artifacts:

1. run complete jailbox `tests/run portable` and `tests/run runtime`;
2. run complete JailIDE `tests/run unit` and `tests/run editor` against
   the installed jailbox candidate; and
3. record skips only where a gate itself reports a supported platform skip,
   never as a passing complete gate.

This is the final local-candidate rerun after core removal. Compare it with
the pre-removal run required by 03.2.14 so the evidence proves JailIDE
replacements worked before deletion and still work after it.

## Repository independence

With both worktrees clean and gates recorded:

1. if JailIDE was developed nested inside the jailbox checkout, move the
   complete working copy to a user-selected sibling path, verify its HEAD is
   unchanged, and remove exactly its entry from jailbox `.git/info/exclude`;
2. add each repository's supplied `origin` fetch/push URL only with the
   user's explicit authorization;
3. verify no tracked `.gitignore` in either product gained a nested-checkout
   rule; and
4. search both repositories for absolute or relative paths into the other and
   prove discovery, packaging, tests, and workflows cannot descend into a
   nested or sibling repository.

Rerun both products' complete gates from their standalone checkouts and
compare results, packages, and checksums with the earlier evidence. Any
location-dependent result blocks release and is fixed in the owning
repository, followed by the complete affected gate set.

## Publication

Before any explicitly authorized push, tag, or release, display both
repositories' remotes and exact commits. Each repository pushes only to its
own origin; never push either product's commits or tags to the other.

Release the final environment-only jailbox version first. Verify its
published artifact checksum and `--version`, install that exact artifact, and
rerun JailIDE's compatibility check and complete gates if published bytes
differ from the prerelease artifact. Release JailIDE `v0.1.0` last against
that exact jailbox version.

No stable jailbox release supports both configuration interfaces. No
transition release or duplicate editor implementation is published.

## Release notes and documentation

jailbox notes:

- removed `jailbox.conf`, `init`, `--config`, editor interfaces, bare editor
  launch, profiles, and `ssh-config`;
- direct human editor users to JailIDE and environment callers to the
  canonical interface;
- document trusted ordered wrapper setup, root build-time execution, content-
  based compatibility/cache identity, and the absence of runtime script
  access;
- explain stop, ephemeral/persistent home behavior, malformed-label
  preservation, and clean data loss; and
- state that the version-bound digest makes upgrades require stop/up, except
  a persistent/legacy-to-ephemeral change requires warned clean/up.

JailIDE notes document v0.1.0 installation of the Go binary, the compatible
jailbox version, config and init, its editor-dependency setup contribution,
editor matrix, profiles, proxy/bootstrap behavior, legacy cleanup, and the
lack of automatic jailbox installation or migration. Add cross-links only
after standalone repository URLs exist.

## Security invariants

All product security invariants are verified through immutable artifacts
before and after any relocation. Installers and archives remain
self-contained, cross-product target isolation is proven, and remote
configuration prevents cross-repository pushes. No step reintroduces a file
interface or editor logic in core, direct Podman access in JailIDE, a
container-engine socket, or a floating build input.

## Acceptance criteria

- Final commits, every artifact checksum/version, the JailIDE compatible
  range, and all complete gates are recorded.
- Both repositories are independent: correct origins, no nested or sibling
  dependency, and gates that behave identically from standalone checkouts.
- jailbox releases first and JailIDE last against the exact tested jailbox
  version; each release goes only to its own remote and names the exact
  immutable dependencies tested.
- The reduced jailbox wrapper lacks editor-only packages, while the exact
  JailIDE setup contribution restores every supported editor gate without
  changing jailbox-owned SSH, egress, or runtime hardening.
- Release notes cover removed interfaces, migration, persistence, and
  destructive recovery.

## Non-goals

- New product behavior, automatic dependency installation, a dual-interface
  transition release, shared runtime utilities, or floating references.
