# 1.1. Explicit project initialization

## Goal

Add `jailbox init` to create a minimal default project configuration, and require
every launch or attach command to select an existing configuration file. jailbox
no longer launches a sandbox entirely from implicit defaults.

## Sequence

Order 1.1. Requires `01-protected-path-policy-plan.md`, because the generated
configuration uses `READONLY_PATHS`. It should land before the command-mode
plans beginning with `02-explicit-stop-plan.md`.

Decimal order labels are stable insertion points. Future work may be inserted
without renaming every later plan; for example, work between 1.1 and 2.0 can use
1.2.

## Command

```text
jailbox init
```

`init` creates `$PROJECT_DIR/jailbox.conf` with this complete content:

```conf
# Additional project paths mounted read-only inside the sandbox.
READONLY_PATHS=
```

The generated policy is minimal. The default in-project config is protected
automatically by `01-protected-path-policy-plan.md`, including when a later
launch selects another config, so it does not list itself.
Do not infer `.env`, Git files, workflow directories, or other ordinary project
paths. Users add those explicitly after reviewing their project; the exact
Containerfile used for a build is the other automatic trusted overlay.

`init` refuses to overwrite any existing path, including a regular file,
symlink, directory, device, FIFO, or socket. It requires no Podman, SSH tooling,
editor, or existing configuration. Reject `--config PATH init`: initialization
always targets the default project configuration, so accepting another path
would make the destination ambiguous.

## Publication

Write the complete template to a temporary regular file in `$PROJECT_DIR`, then
publish it without replacement by hard-linking it to `jailbox.conf`. Remove the
temporary file on every success and failure path.

If publication fails and `jailbox.conf` now exists, report that it already
exists and leave it untouched. If publication fails while the destination is
still absent, report the publication failure rather than describing it as a
creation race. Never use `mv -n`, whose no-clobber behavior is not portable
enough to define this boundary.

## Configuration requirement

A sandbox launch or attachment requires the default policy anchor and must
select a configuration:

- `$PROJECT_DIR/jailbox.conf` must always exist and pass regular-file,
  readability, and no-symlink checks;
- without `--config`, that default file is also the selected config and is
  parsed normally;
- with `--config PATH`, that selected file may be inside or outside the project,
  but it must exist, be a readable regular file, and have no symlink component
  in the supplied path. A caller selecting an external file through a symlink
  must pass its real path directly. The selected file is the only one parsed;
  the default remains an independently validated and protected anchor.

`--config PATH` does not bypass project initialization. Without a persistent
default path, a sandbox launched from an external config could create
`jailbox.conf` through the writable project mount, and a later bare launch would
trust policy authored inside the sandbox. Requiring the anchor to exist lets
jailbox mount it read-only on every launch and closes that next-launch policy
injection path.

At order 1.1, bare `jailbox` is the only command that requires configuration.
The predicate introduced here initially classifies only bare launch. The later
plans that add `up`, `exec`, and `shell` extend it when each command becomes
available; they own those commands' behavior and tests. If the default anchor
does not exist, bare launch fails before loading even an explicit `--config`
with an actionable message such as:

```text
Project is not initialized: jailbox.conf is required even with --config so the
sandbox cannot create policy for a later bare launch. Run 'jailbox init'.
```

An explicitly selected missing path retains the specific
`config path does not exist` error and must not suggest that `init` will create
the external target.

`init`, `doctor`, `ssh-config`, `--clean`, and `--uninstall` do not require
configuration merely to run. Commands that currently load an optional config
may continue doing so, but its absence is not an error. Later command plans must
classify their own commands explicitly rather than expanding this plan's tests
ahead of their implementation.

## Implementation

- Add `init` to `CLI_FLAGS_WITHOUT_VALUES` and `CLI_HELP` in
  `host/public-api.sh`, and update parsing, dispatch, the literal usage synopsis,
  and `tests/unit/public-api-diff.sh` expectations.
- Add `init_project_config` in `host/common.sh`. Keep its file creation focused
  there; it does not initialize Podman resource, SSH, editor, network, or mount
  state.
- Add a command predicate for whether configuration is required, initially
  matching bare launch only. Enforce it during config selection after argument
  parsing. For a matching command, validate the default anchor before selecting
  or loading another config. Do not make optional-config inspection and
  lifecycle commands fail when the default is absent.
- Update `check_readonly_mounts` (`host/validation.sh`) for the stronger invariant
  established here. A successfully finalized launch set now always contains the
  default anchor, so restore the existing
  "No read-only mounts were available to validate" branch as an internal
  regression warning. The legitimate empty-set behavior remains part of plan
  1.0 only and is no longer reachable through launch.
- Dispatch `init` before configuration selection and host preflight. Reject a
  supplied `--config` for this command before creating anything.
- Keep configuration as strict data. The generated file is parsed normally on
  the next launch and receives no privileged loading path.

Review `scripts/public-api-diff.sh`: adding `init` is a minor public-API change
before 1.0.

## Documentation

Update README onboarding to run `jailbox init` before the first launch. Document
the generated template, refusal to overwrite, external `--config` alternative,
and that bare launch requires the default anchor even when another config is
selected. Explain the security reason in user-facing language: the persistent
read-only anchor prevents a sandbox from planting policy for a later bare
launch. State that project-reachable config spellings reject every symlink
component and that directly selected external configs follow the same rule.

Reinforce the threat-model text introduced by
`01-protected-path-policy-plan.md`: an existing default config is protected even
when another config is selected, and any selected in-project config is protected
automatically. An external selected config is outside the project mount and
needs no overlay. Ordinary project paths remain writable unless listed, apart
from the exact used in-project Containerfile.

## Tests

- `init` creates exactly the complete template and a subsequent bare launch
  selects it.
- The generated `jailbox.conf` is protected automatically despite its empty
  `READONLY_PATHS`.
- `init` refuses every existing destination type without changing it.
- Concurrent `init` processes publish at most one complete file and leave no
  temporary files.
- A publication failure with no destination is reported as an error, not as a
  lost race.
- `init` needs no Podman, SSH tooling, editor, or existing configuration.
- `--config PATH init` is rejected before filesystem mutation.
- Bare launch fails with the explanatory `jailbox init` instruction whenever the
  default anchor is absent, including with an existing external `--config PATH`.
- With the default anchor present, an existing external `--config PATH` is the
  only parsed config and both files receive the appropriate protection; a
  missing selected path retains the path-specific error.
- Selected project-reachable and directly external configs with a leaf or
  intermediate symlink are rejected before parsing; supplying the external
  target's real path directly is accepted.
- External-config fixtures canonicalize their temporary directory
  unconditionally before passing `--config`; a separate macOS-capable assertion
  proves that a `/var` spelling with a symlinked prefix is rejected while its
  physical `/private/var` spelling is accepted. The project-root prefix
  exception remains covered independently.
- Every successful launch has a non-empty effective read-only set containing the
  default anchor. A direct empty-set validation probe increments `WARNINGS` as an
  internal regression signal, while ordinary launch never reaches that state.
- `doctor`, `ssh-config`, `--clean`, and `--uninstall` remain usable with no
  default config.
- `init` appears in usage, help, and the generated public-API diff.

Run `tests/run portable`. Also run `tests/run runtime` because the new
configuration precondition changes launch behavior.

## Non-goals

- Inferring project-specific protected paths.
- Creating an arbitrary `--config` destination.
- Automatically migrating or rewriting existing configuration.
- Automatically running `init` from launch.
