# 3.2. JailIDE repository split charter

## Goal

Split the user-facing project into independently installed products while
extracting their generic distribution mechanics into an independent maintainer
tool:

```text
JailIDE -> jailbox -> Podman
orchestrator --------> jailbox -> Podman

JailIDE build/release --\
                         > shell-release-toolkit (pinned build-time input)
jailbox build/release --/

JailIDE source/runtime --\
                         > jailutils (pinned Git submodule)
jailbox source/runtime --/
```

jailbox remains the generic machine-facing sandbox substrate; JailIDE owns the
human configuration and editor workflow. Their runtime dependency points only
toward jailbox. `shell-release-toolkit` is never installed as a shared runtime
library; consumers commit its deterministic self-contained outputs.

## Sequence

Implement the indexed plans in filename order. Version precedes digest because
the release version is hashed; digest precedes ownership-label removal because
it becomes the reuse gate; JailIDE exists and passes its gates before core
removes the surfaces it replaces.

## Product boundary

jailbox owns canonical configuration and validation, images, Podman lifecycle,
filesystem and egress policy, SSH generations and transport, deterministic
identity, machine status/connection data, generic caller-supplied wrapper setup,
and portable/runtime gates. SSH and generic attached-development prerequisites
stay core behavior. JailIDE supplies editor-specific wrapper setup through the
public caller mechanism and owns compatibility fixes to that contribution.
JailIDE owns `jailide.conf`, init, editor discovery/validation, profiles,
bootstrap destinations, launch/diagnostics, editor pins, and portable/editor
gates.

End-state jailbox has no config files, `init`, `--config`, `EDITOR`,
`JAILBOX_EDITOR`, editor launch/discovery, profiles, bootstrap composition,
`ssh-config`, or editor gate. Neither product owns worktrees, external
credentials, agent selection, scheduling, or Git integration.

`shell-release-toolkit` owns only manifest-driven shell-application packaging,
installer, SemVer/release-candidate, and reusable gate mechanics proven to have
identical contracts in both consumers. It owns no provider integration or
consumer release authority.
Each consumer owns its product manifest, public-API classifier, file inventory,
commands, gates, versions, release authority, and integration tests. Toolkit
adoption cannot permit either product to replace or uninstall the other.

`jailutils` owns only ecosystem-specific runtime mechanisms with
identical semantics in both products. Each source repository pins it as a Git
submodule without committing copied source; each release artifact packages its
own immutable copy. It initially owns the public Base64 record envelope, not
command schemas or decoded-value policy.

## Repository layout

This checkout remains jailbox. Plan 03.2.10 creates a clean locally excluded
`shell-release-toolkit/` history-filtered clone from the reviewed coordinated
03.2.01–03.2.09 jailbox commit, then adopts the toolkit in a new jailbox
commit. Plan 03.2.10.1 creates the locally excluded
`jailutils/` history-filtered clone and pins it in jailbox. The
clean locally excluded `jailide/` clone stays nested through 03.2.14; plan
03.2.11 fast-forwards it to the later coordinated 03.2.01–03.2.10.1 jailbox
commit, including both dependencies, before reduction. Plan 03.2.15 moves all
extracted repositories host-side to user-selected sibling paths, establishes
their remotes, removes their local excludes, and proves no product depends on
temporary nesting or an unpinned sibling checkout.

## Security invariants

- Container roots remain read-only, with capabilities dropped and
  `no-new-privileges`.
- No container-engine socket is mounted.
- Project runtime state remains outside the project.
- Core validates and read-only mounts known launch inputs; callers protect
  their own policy inputs.
- Egress mode has no direct route and HTTP(S) uses the allowlisting proxy.
- SSH uses strict host-key checking and project-scoped pinned state.
- Each new container generation gets fresh client/server credentials; resume
  preserves and validates that generation.

Persistent home content is sandbox-controlled state trusted across policy and
version changes. Server material is read-only and client secrets stay
host-only. Digest and structure validation prevent weakened resume. Guarantees
cover one lifecycle command at a time; locking remains backlog work.

## Acceptance criteria

- Each product exposes only its owned surface through the documented executable
  and environment boundary.
- All indexed plans and their gates pass in order.
- All four final repositories have independent documentation, gates, remotes,
  and commit identities. Toolkit, jailbox, and JailIDE have independent versions
  and releases; only jailbox and JailIDE install user-facing products or own
  runtime state.
- Jailbox and JailIDE consume one immutable published toolkit release through
  audited locks and generated self-contained files without a runtime dependency.
- Jailbox and JailIDE pin one common source commit without duplicated tracked
  source and package isolated copies into their self-contained artifacts.
- JailIDE's real editor gate detects remote-server runtime regressions, while
  jailbox owns and releases the prerequisite fix before compatibility is
  claimed.

## Non-goals

- Plugins, a private API, a separate protocol version, an installed or
  dynamically downloaded shared runtime library, or shared product policy.
- Automatic dependency installation or version matching.
- Moving SSH out of core or allowing JailIDE to call Podman.
- Automatic cleanup/replacement, persistent integrity monitoring, or lifecycle
  serialization.
