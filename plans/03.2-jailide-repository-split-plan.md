# 3.2. Extract JailIDE and make jailbox environment-only

## Goal

Split the project into two independently installed and released repositories:

```text
JailIDE -> jailbox -> Podman
orchestrator --------> jailbox -> Podman
```

`jailbox` remains the existing repository and becomes a generic, machine-facing
sandbox substrate. `JailIDE` becomes a new `jailide` repository containing
the human-facing configuration and VS Code/VSCodium workflow. The only
dependency direction is from JailIDE to jailbox.

## Sequence

This plan absorbs plan 4 rather than preceding it: the release order below
rewrites and lands the configuration digest as part of this work, and plans 5
through 8 follow the resulting core. It also replaces the configuration
interface proposed by `03.1-environment-config-overrides-plan.md`: rewrite plan
3.1 as an environment-only configuration plan, not as overrides over a file.
That rewrite must also drop 3.1's non-goal excluding per-item environment
variables, which was written when the environment was an override layer over a
file rather than the only configuration channel; the indexed array spelling
below replaces it.
Then revise plans 5 through 8 to use the resulting public interface. Do not edit
archived plans; they remain records of implemented behavior.

## Product boundary

### jailbox owns

- canonical sandbox configuration keys and validation;
- development-image selection, wrapper-image construction, and the runtime
  compatibility packages required by SSH-attached remote IDE servers;
- Podman containers, networks, mounts, volumes, proxy, and lifecycle;
- filesystem and egress policy;
- SSH setup, fresh credentials for each newly created development-container
  generation, credential preservation and validation during resume, pinned host
  keys, generated SSH config, readiness, `exec`, and `shell` transport;
- project identity, core runtime state, status, and connection information; and
- portable and runtime security gates.

SSH remains core behavior because editors, shells, commands, and future
orchestrators all use it.

For this split, keep the existing remote IDE-server runtime prerequisites in
`container/setup.sh`, including Alpine compatibility libraries, and describe
them as part of the generic SSH-attached development runtime rather than editor
selection or launch behavior. JailIDE's real editor gate owns detection of
compatibility regressions across supported VS Code and VSCodium versions. A
missing or changed runtime prerequisite is fixed in jailbox and requires a new
compatible jailbox release before JailIDE claims support. This deliberate
cross-repository coordination point remains until a public downstream wrapper-
setup extension is designed separately.

### Project resource identity

Preserve the existing naming convention: derive the project hash as the first
12 lowercase hexadecimal characters of the SHA-256 digest of the canonical
physical project-directory path, and use the existing sanitized project slug
where the resource format includes it. Generate every project-scoped container,
network, volume, SSH alias, and runtime-state path through the shared helpers in
`host/project-id.sh`. Equivalent relative, absolute, and symlinked spellings of
the same physical directory must produce identical names in every command.

The deterministic names establish project ownership. Any resource occupying an
exact derived name is treated as belonging to that project; do not add or check
a redundant project-path ownership label. The configuration-digest label
records policy compatibility, which the resource name does not encode. Public
API and regression checks must cover the naming inputs, format, and consistent
use by lifecycle and connection commands.

Resource names and labels are not authentication against the host user or any
process with access to that user's Podman service. Such a process can create an
exact derived name or forge any jailbox label. Names enforce one resource per
derived identity, while digest labels guard against accidental partial state,
configuration mismatch, and version skew. The sandbox receives no Podman or
Docker socket, so code confined to the sandbox cannot exercise that host-level
authority through the supported interface. State this boundary in the README
threat model.

Remove the `cksum` fallback from `jailbox_project_hash_for_path`; project
identity requires `sha256sum` or `shasum -a 256`, which the configuration
digest requires as well. The hash is then always hexadecimal, so remove the
decimal branch and its explanatory comment from
`jailbox_project_hash_port_offset` in `host/project-id.sh` rather than leaving
an unreachable path behind. Remove `jailbox_resource_owner`,
`jailbox_resource_ownership`, `resolve_owned_resources`, and all
`jailbox.project` label creation and inspection from `host/container-runtime.sh`
and `host/network.sh`; replace their callers with exact derived-name existence,
structure, and configuration-digest checks. Update the lifecycle unit tests,
runtime tests, and README claims accordingly.

The test cleanup helpers need a replacement designed rather than substituted.
`prune_stale_jailbox_resources` in `tests/e2e/editor-smoke.sh` enumerates
`label=jailbox.project` and prunes only resources whose label points into a
`/tmp/jailbox-editor-*` or `/tmp/jailbox-e2e-*` fixture, precisely so that a
developer's real sandboxes — including one this test may itself be running
inside — are never touched. It exists because a crashed run leaves resources
whose `mktemp` fixture directory is gone, so the names cannot be re-derived
afterwards.

Removing the label removes that protection, and a sweep over the shared
`jailbox-` name prefix must not replace it: every real project's resources
begin with that prefix too. Instead the harness must retain what it created.
Record each fixture's derived resource prefix in a ledger outside the fixture
directory, written before the launch that creates any resource so an
interrupted run is still recoverable, and prune only exact names under a
recorded prefix. Cleanup must never remove a resource it cannot tie to a
fixture the harness itself created; that invariant, not the mechanism, is what
this plan requires. It applies to both repositories' gates after the split,
and to project-scoped images as well as containers, networks, and volumes.

This preserves resource and runtime-state names produced by the existing
SHA-256 path and introduces no naming migration. The separate
configuration-digest migration still treats existing unlabeled resources as
incompatible and provides explicit cleanup and relaunch guidance.

### JailIDE owns

- the human-readable project configuration file and `init` workflow;
- editor selection, discovery, and Remote SSH extension validation;
- isolated editor profiles and settings;
- editor bootstrap egress destinations and compatibility guidance;
- editor launch and diagnostics; and
- editor version pins, compatibility matrix, and real editor gate.

Neither product owns worktrees, credentials, agent selection, scheduling, or
Git result integration. Those belong to a future orchestrator.

## Core configuration contract

jailbox accepts configuration only through `JAILBOX_CONFIG_*` environment
variables. These are the canonical public interface, not overrides. Remove core
support for project configuration files, `--config`, and `init`.

Each key declared in `host/public-api.sh` has one derived spelling, including:

```text
DEV_IMAGE          -> JAILBOX_CONFIG_DEV_IMAGE
DEV_CONTAINERFILE  -> JAILBOX_CONFIG_DEV_CONTAINERFILE
DEV_BUILD_CONTEXT  -> JAILBOX_CONFIG_DEV_BUILD_CONTEXT
DEV_TARGET_STAGE   -> JAILBOX_CONFIG_DEV_TARGET_STAGE
EGRESS_ALLOW       -> JAILBOX_CONFIG_EGRESS_ALLOW
READONLY_PATHS     -> JAILBOX_CONFIG_READONLY_PATHS
EPHEMERAL_HOME     -> JAILBOX_CONFIG_EPHEMERAL_HOME
```

Plans 7 and 8 add `JAILBOX_CONFIG_WRITABLE_PATHS` and
`JAILBOX_CONFIG_HIDDEN_PATHS` through the same declaration-driven mechanism.
Remove `EDITOR` from core and remove `JAILBOX_EDITOR` without an alias.

`EPHEMERAL_HOME` is a strict `true`/`false` scalar and defaults to `true`.
`true` makes the sandbox home part of the development-container generation and
removes it on `stop`; `false` preserves it across generations, policy changes,
and jailbox upgrades. Record the effective creation-time mode on the volume as
the lifecycle label `jailbox.ephemeral-home=true|false`, because `stop` remains
configuration-independent and must apply the policy under which the existing
volume was created.

A missing label is not an unknown mode. Every volume that exists before this
change was created by a release whose `stop` removed only containers and whose
`--clean` alone removed the home, which is exactly `EPHEMERAL_HOME=false`
behavior. An unlabeled volume therefore reads as `false` throughout: it is
legacy state with known semantics, not a fault. A label that is present but not
exactly `true` or `false` is the fault case — corrupted or forged metadata —
and is never guessed as ephemeral: preserve the volume, warn, and require
explicit cleanup or metadata resolution.

Callers pass final values for the keys they set. Scalars are direct: the
variable holds the value. An absent optional key receives core's documented
default, and a present empty scalar is the empty value. Core rejects every
unknown `JAILBOX_CONFIG_*` name and validates the complete effective
configuration before any image, credential, network, volume, or container
mutation.

Arrays use one variable per member rather than a separator. This replaces the
comma-separated representation inherited from the configuration file, which
could not express a member containing its own separator. Every byte except NUL
survives an environment value, and no path may contain NUL, so the indexed form
represents any legal path exactly:

```text
JAILBOX_CONFIG_READONLY_PATHS_0=src/main
JAILBOX_CONFIG_READONLY_PATHS_1=docs/api,v2
JAILBOX_CONFIG_READONLY_PATHS_2=vendor
```

The array grammar is:

- no `JAILBOX_CONFIG_<KEY>` variable and no indexed member present: the key is
  unset and takes core's documented default;
- a present, empty bare `JAILBOX_CONFIG_<KEY>` with no indexed member: the
  explicitly empty array;
- indexed members `JAILBOX_CONFIG_<KEY>_<N>`: the array in index order. Indices
  must start at `0` and be contiguous; a gap is an error rather than a silent
  truncation, and every member must be non-empty;
- a non-empty bare `JAILBOX_CONFIG_<KEY>`, or a bare name of any value combined
  with indexed members, is an error. No separator grammar remains to interpret
  the bare value, so it must never be guessed.

Accept an index only as `0` or a non-zero digit followed by digits, so `_01`,
`_+1`, and `_X` are rejected, and enforce an upper bound of 256 members per
array key. Derive accepted names from the declared array keys in
`host/public-api.sh` rather than pattern-matching the prefix loosely, so an
unknown key with an index suffix still fails as an unknown name.

There is no additive namespace, source marker, or configuration protocol
version. A trusted caller composes final values before invoking jailbox.
Configuration never contains credentials.

Configuration-consuming commands are:

```text
jailbox up
jailbox exec [--] CMD [ARG...]
jailbox shell
jailbox connection-info
```

They consume the same environment. `stop`, `status`, `doctor`, `config-schema`,
`--clean`, `--version`, `--help`, and `--uninstall` do not require it. Bare
`jailbox` is a missing-command usage error: it prints concise usage to stderr,
performs no mutation, and exits 2. `jailbox --help` prints help and exits 0.
Launch is explicit through `up`.

### Constrained `up` convergence

`jailbox up` means ensure that the exact declared sandbox is running. It is
idempotent, but it is not an automatic repair or replacement operation. After
validating the complete configuration and inspecting every required resource,
it behaves as follows:

- when every project resource is absent, create and start the sandbox;
- when all existing policy-bearing resources have a matching configuration
  digest, create any missing resources, apply the home volume's recorded
  lifecycle mode, start required containers in dependency order, and complete
  the normal readiness checks;
- when the complete matching sandbox is already running and healthy, succeed
  without changing it; and
- when any existing policy-bearing resource has a missing or mismatched digest,
  has an incompatible structure, or is otherwise unhealthy, fail without
  replacing, stopping, or removing anything.

Digest and structural validation of all existing resources occurs before any
mutation. Record the version-bound digest on every independently surviving
development container, proxy container, and network so a partial ephemeral set
remains verifiable when the development container is missing. A policy-bearing
resource with no digest is legacy and not automatically reusable.

The home volume is the deliberate digest exception. It has no immutable
security-relevant creation settings and does not receive or gate reuse on the
configuration digest; current security properties come from the container's
mounts and runtime options. On creation, label it with the effective
`EPHEMERAL_HOME` mode. A requested mode that differs from an existing valid
label refuses before mutation with directional recovery. An unlabeled volume
reads as `false`, so `up` accepts and preserves it when the requested mode is
`false`, and refuses when the requested mode is `true` under the
persistent-to-ephemeral rule below rather than as a separate legacy failure.
That keeps the ordinary upgrade non-destructive: existing sandboxes carry an
unlabeled volume, `jailide init` writes `EPHEMERAL_HOME=false`, and those
projects upgrade with `stop` then `up`. A caller that requests the core default
`true` against an existing home is asking for a genuine policy change that
deletes data written under the previous release, and takes the warned `--clean`
path deliberately.

Core never writes lifecycle metadata onto a volume it did not create, so an
accepted legacy volume stays unlabeled and continues to read as `false` on
every later invocation. A present but unparseable label refuses before mutation
with the same explicit cleanup guidance. To change an existing
ephemeral volume to persistent, run `jailbox stop` so its recorded policy
removes it, then launch with `EPHEMERAL_HOME=false`. To change an existing
persistent volume to ephemeral, run `jailbox --clean`, with an explicit warning
that this deletes the home and project runtime state, then launch with
`EPHEMERAL_HOME=true`.

In persistent mode, reuse the volume by its exact deterministic name across
generations, jailbox versions, and policy changes. In ephemeral mode, reuse it
only while its development-container generation survives; an orphaned
ephemeral volume blocks `up` until `stop` removes it. Jailbox may replace only
its own managed proxy blocks after connection and otherwise preserves persistent
home contents. Reconciliation may create a missing resource or start an
existing validated container, but never delete or replace a pre-existing
resource. If reconciliation fails, remove only resources created by that
invocation and preserve everything that predated it. Rollback covers host-side
generation material as well as Podman objects, under the SSH generation
contract below.

The digest includes the exact jailbox release version in addition to final
validated configuration and Containerfile identity. Any jailbox upgrade
therefore makes existing resources incompatible with automatic reuse, even when
the public configuration is unchanged. This conservative boundary prevents a
new release from resuming containers whose immutable Podman creation settings
were produced by older hardening rules.

Structural validation also covers the dependency graph and host-side SSH state.
Before resuming a development container, require its expected network and home
volume attachments, all required supporting resources, the generated SSH
configuration, matching client key pair, pinned host key, and container-side
SSH runtime material to be present and internally consistent. Validate file
ownership and restrictive modes without printing key or host-key contents. A
missing or inconsistent SSH artifact is not regenerated around a surviving
development container; fail before start.

A sandbox generation is the lifetime of one development-container object.
Creating a generation produces a fresh client key pair and server host key and
pins that host identity. A no-op or resume of the same container preserves and
validates those credentials; it is not a new generation. `jailbox stop` removes
the development container and ends its generation, so the next `up` creates and
pins fresh credentials. This gives an explicit operator-controlled rotation
boundary without turning resume into authentication-state repair.

Implement that boundary explicitly. Split host SSH setup into new-generation
creation and resume validation. New-generation creation atomically prepares the
client key pair, server host key pair, `authorized_keys`, pinned host entry, and
generated client configuration on the host before creating the development
container. Keep the client private key, pinned host state, and client
configuration outside every container mount. Mount only the server host key
pair and `authorized_keys` into the container as a read-only generation
directory. Put mutable daemon state such as `sshd.pid` in the container's `/run`
tmpfs.

A generation exists only once its container object does. When new-generation
creation fails, or the development container is not created successfully,
remove every SSH artifact that invocation created and leave no partial
generation behind; never alter or delete material that predated the invocation.

This read-only mount contract depends on `--userns=keep-id`: the host-created
files retain the effective managed-user ownership expected by OpenSSH
StrictModes inside the container without an entrypoint `chown` or `chmod`.
Preserve that mapping as part of the SSH transport contract. Any future user
namespace change must provide an equally strict ownership mapping and pass the
same runtime assertions before it can replace `keep-id`.

`container/entrypoint.sh` no longer creates, deletes, refreshes, or otherwise
mutates authentication material; it validates that the read-only files are
present and starts sshd with them. Resume validates the host-side client and
server pairs, pin, generated configuration, mount source, ownership, modes, and
regular non-symlinked file types before starting the container. Update
`container/setup.sh` to describe both key pairs as generated once per
development-container generation rather than once per launch. The sandbox can
read its server host private key because sshd must use it, but cannot use that
key to authenticate to the host; the client private key remains host-only.

Network reconciliation follows dependency order. A missing internal network
may be recreated only when neither the development container nor proxy
container survives. A surviving home volume does not prevent recreation: after
choosing the network's actual subnet, derive the live proxy URL, render fresh
host SSH session configuration, create the missing containers, and replace only
jailbox-managed proxy blocks in the home volume after SSH readiness. When the
network survives, derive the URL from its actual subnet and require surviving
containers to have the expected attachments before starting them. Never resume
a container against a recreated network or retain managed proxy state for a
different URL.

Every incompatible or unhealthy failure gives a non-mutating recovery path.
`jailbox stop` removes the development and proxy containers and all
project-scoped networks. It removes a valid `EPHEMERAL_HOME=true` volume and
preserves a valid `false` volume. An unlabeled volume is preserved as the
legacy `false` state it records, and an unparseable label preserves the volume
and warns. Images survive `stop` in every case, so a relaunch stays
fast. Direct the user to run `jailbox stop` and then `jailbox up` to replace
ephemeral policy-bearing resources and create fresh SSH credentials.

Reserve `jailbox --clean` for an explicitly requested full teardown: it removes
the containers, networks, home volume, project runtime state, and the three
project-scoped image names under the derived prefix: the built development
image (`PROJECT_DEV_IMAGE`), the wrapper image (`JAILBOX_IMAGE`), and the proxy
image (`PROXY_IMAGE`). It performs no provenance
check and cannot, since it receives no configuration and image ownership labels
are gone; it deletes those exact names whatever produced them, on the same
name-is-identity model as every other resource. An externally supplied
`DEV_IMAGE` whose name is not one of the three exact derived image names is
unaffected: the derived development-image name is used only when jailbox builds
from a Containerfile, and a configured `DEV_IMAGE` is referenced under the name
the caller gave it. A caller that deliberately gives an external image one of
this project's derived names loses it, which is the image case of the naming
collision boundary documented above. Every diagnostic that recommends
`--clean` must state that it permanently removes the sandbox home volume and
project runtime state.

Both commands act on exact derived names without ownership proof, which follows
directly from removing the `jailbox.project` label. `stop` and `--clean` remove
whatever occupies a derived name, including legacy resources carrying no digest
and resources whose digest or structure is invalid. That is deliberate: it is
what makes them the recovery path for incompatible state, which a digest check
could not provide. It is also the one place where a name collision destroys
data, so state this deletion boundary in the README beside the naming and
forgeability discussion. Neither recovery runs automatically.

## Version and compatibility

The jailbox release version is the sole version of its public API. Do not add
`JAILBOX_CONFIG_VERSION` or a separate API version.

Add stable, machine-readable version output:

```text
jailbox --version
jailbox 0.8.0
```

It requires no project or external dependency. Extend public API review to
cover environment keys, the configuration schema, machine-output schemas, and
command changes.

The version string must be readable from the installed tree, because
`--version` and the version-bound digest both consume it and neither may depend
on Git. Stamp it into the release tree at package time from the version
`scripts/build-tarball.sh` already validates against `vMAJOR.MINOR.PATCH`, so
the shipped copy carries the exact released version without adding a step to
the release flow. A source checkout has no stamped version and reports one
documented development version instead. That development version is a digest
input like any other, so a sandbox created from a checkout never satisfies the
digest of a released jailbox, and the reverse. The portable gate covers both
the stamped and unstamped spellings.

JailIDE declares a compatible jailbox range and checks `--version` before
mutation. Before jailbox 1.0, compatibility is bounded to a minor line, such as
`>=0.8.0,<0.9.0`; after 1.0, use the normal major-version boundary.

That range requires the pre-1.0 bump policy to treat the minor slot as the
breaking axis, which is what caret ranges already assume for `0.x` and what
SemVer leaves open by scoping its patch and minor rules to `x > 0`. Change the
policy accordingly: before 1.0, adding a public configuration key or CLI flag
is a patch bump, while removing or changing one is a minor bump; after 1.0 the
normal rules resume, where an addition is a minor bump that stays inside
JailIDE's major-version range. Without this, every newly declared core key
lands in a new minor line and falls outside the range that `config-schema`
discovery exists to make survivable. Update the policy comment in
`host/public-api.sh` and `suggest_bump` in `scripts/release.sh`, whose pre-1.0
branch currently collapses additions and removals into one minor bump.

The products otherwise have independent versions and release schedules.

## Machine interfaces

Add three read-only core commands.

`jailbox config-schema` emits the accepted core configuration keys directly
from their canonical declarations in `host/public-api.sh`. It requires no
project, configuration, Podman, or other external dependency. Output is in
declaration order with exactly one tab-separated record per key:

```text
DEV_IMAGE<TAB>scalar
DEV_CONTAINERFILE<TAB>scalar
DEV_BUILD_CONTEXT<TAB>scalar
DEV_TARGET_STAGE<TAB>scalar
EGRESS_ALLOW<TAB>array
READONLY_PATHS<TAB>array
EPHEMERAL_HOME<TAB>scalar
```

Plans 7 and 8 cause `WRITABLE_PATHS` and `HIDDEN_PATHS` to appear automatically
through the same declaration mechanism. The final core schema does not contain
`EDITOR`. Key names use the same validated uppercase identifier grammar as the
environment interface; the only types are `scalar` and `array`. A `scalar` key
is set through its bare `JAILBOX_CONFIG_<KEY>` spelling and an `array` key
through the indexed member spelling defined above, so the reported type tells a
consumer which form to compose. The command
prints no headings, values, defaults, colors, or diagnostics on stdout.
Consumers fail on malformed records, duplicate keys, invalid names, unknown
types, or a missing core key they specifically require for composition. The
jailbox release version governs this schema.

`jailbox status` derives project identity from the physical current directory
and prints one stable state on stdout:

```text
absent
running
stopped
```

Status examines exactly one inventory of deterministically named Podman
resources: the development container, the proxy container, the project
networks, and the home volume. That list is exhaustive and is part of the
stable output contract; a later plan that introduces a new resource kind does
not extend it without a deliberate schema change. It reports `running` when the
development container is running, `stopped` when it is not running but at least
one inventory resource exists, and `absent` only when none exists.

Project-scoped images are deliberately excluded even though they are
deterministically named. They are rebuildable build output rather than
lifecycle state, and `stop` preserves them so a relaunch stays fast. Counting
them would make `absent` unreachable for any project that has ever launched and
would permanently block `jailide init`. Host-side SSH and runtime state are
excluded for a different reason: `status` is a Podman-only lifecycle summary
and `doctor` owns host-state inspection.

`status` reports aggregate lifecycle state, not complete sandbox health or
configuration compatibility. A running development container may therefore
report `running` when its proxy is absent or stopped; `up` and
`connection-info` perform stricter structural, digest, and health checks.
Partial and unhealthy states produce actionable diagnostics on stderr without
changing the single state printed on stdout.

Diagnostics go to stderr. It requires Podman but no configuration. JailIDE
uses it to refuse initialization while resources occupy the project identity.

`jailbox doctor` remains the detailed, human-facing diagnostic command rather
than a second lifecycle-status interface. It requires no configuration and does
not mutate. It reports the one-word `status` result plus the presence and
runtime state of each derived Podman resource, missing or inconsistent digest
labels across policy-bearing resources, host SSH-state presence, permissions
and internal consistency, the live network subnet and required proxy state, and
the appropriate `stop`/`up` or `--clean`/`up` recovery sequence. Any
`--clean` recommendation warns that it deletes the sandbox home volume and
project runtime state. Without a supplied configuration it does not claim
whether a consistent recorded digest matches a hypothetical current policy.
Its output is for people and has no stable machine schema; automation uses
`status` and `connection-info`.

`jailbox connection-info` loads and validates the complete environment
configuration, computes the configuration digest defined by the rewritten plan
4, and uses a shared read-only attachment validator. That validator requires a
running, SSH-responsive development container, matching configuration-digest
labels on every required policy-bearing resource, a structurally valid home
volume, and, when egress filtering is active, a running required proxy. It never
creates, repairs, replaces, or removes resources.

Plans 5 and 6 reuse this validator for `exec` and `shell`; `connection-info`
does not depend on those commands being implemented first.

On success it emits fixed-order, tab-separated, Base64-encoded values:

```text
ssh_config<TAB>ENCODED_ABSOLUTE_PATH
ssh_host<TAB>ENCODED_HOST_ALIAS
remote_path<TAB>ENCODED_ABSOLUTE_PATH
project_id<TAB>ENCODED_PROJECT_ID
proxy_url<TAB>ENCODED_PROXY_URL_OR_EMPTY
```

Use unwrapped RFC 4648 Base64. Encoding and decoding must work on both GNU
coreutils and BSD/macOS `base64`, whose wrapping options differ; select the
available spelling once in a shared helper and cover both in the portable gate,
as the existing SHA-256 selection already does. Consumers ignore unknown
additional fields but fail on missing or duplicate required fields, invalid
Base64, or invalid names.
Stdout contains no headings, colors, or status text. Do not expose private-key
paths, known-host contents, container names, or raw configuration values.
`proxy_url` is required derived connection metadata, not a configuration value:
it is the live internal proxy URL when egress filtering is active, including a
URL derived from the network's actual collision-fallback subnet, and the empty
string otherwise. Do not expose the egress allowlist. Core continues to provide
`NO_PROXY` and `no_proxy` to remote sessions through the generated SSH
configuration; JailIDE does not duplicate that session policy.

The jailbox release version governs both schemas. Breaking changes require the
corresponding release bump and coordinated JailIDE compatibility update.

## JailIDE configuration and launch

The new executable is:

```text
jailide [--config PATH] [--editor code|codium]
jailide init
```

Its default configuration is `$PROJECT_DIR/jailide.conf`. The file belongs to
JailIDE even though most keys describe sandbox policy: JailIDE owns the
human format, while jailbox owns the meaning and final validation of exported
core values.

The file remains strict `KEY=value` data. It may contain keys reported by the
installed jailbox's `config-schema` plus the JailIDE-only `EDITOR`. `--config
PATH` selects one complete file. JailIDE does not maintain a static copy of the
core key list: it validates non-`EDITOR` names and scalar/array parsing against
the discovered schema, while jailbox remains the final authority and validates
everything again. Editor selection precedence is `--editor`, `JAILIDE_EDITOR`,
file `EDITOR`, then `codium` when available, then `code`.

Scalar keys appear at most once. Array keys repeat, one member per line, and
carry no separator:

```text
READONLY_PATHS=src/main
READONLY_PATHS=docs/api,v2
READONLY_PATHS=vendor
```

File order is member order and maps directly onto the indexed environment
spelling, so line one becomes `_0`. A single occurrence with an empty value is
the explicitly empty array; mixing an empty occurrence with non-empty ones is
an error, as is repeating a scalar key.

Because members are delimited by line boundaries, the file cannot express a
member containing a newline, and no parser can detect the difference: such a
path is indistinguishable from two adjacent members. Core's per-member
existence check makes the ordinary case fail closed, since neither half of a
split path exists, but a split that happens to name two real paths is applied
silently. That is a tightening for read-only and hidden arrays and a widening
for a future writable array, so plan 7 must confirm the behavior before
`WRITABLE_PATHS` ships. Document the limit in the JailIDE configuration
reference and direct anyone who needs such a path to compose indexed
environment variables directly, which have no equivalent limit.

`jailide init` creates the minimal default without overwriting any object. Its
template names core keys directly, so it validates every key it is about to
write against the discovered `config-schema` and fails with a clear
compatibility error rather than writing a file the installed jailbox would
reject. In addition to the ordinary minimal values, it writes
`EPHEMERAL_HOME=false` with a comment explaining that JailIDE intentionally
preserves editor servers, tools, shell configuration, and history across
generations, while also preserving sandbox-controlled state written under
earlier policy. It proceeds only when `jailbox status` prints exactly `absent`;
partial, stopped, and running resource sets all refuse without writing the
configuration file.

Bare `jailide` is the normal human launch command. Before launch, JailIDE:

1. resolves jailbox once and verifies its compatible `--version`;
2. loads and validates `config-schema` from that same executable;
3. parses and validates the selected file as strict data against that schema;
4. discovers the editor and validates its Remote SSH extension;
5. composes editor bootstrap hosts into the final egress array;
6. adds default and selected in-project configuration files to the final
   read-only paths;
7. exports every configured core key plus the composed egress and read-only
   values, using `JAILBOX_CONFIG_<KEY>` for scalars and contiguous
   `JAILBOX_CONFIG_<KEY>_<N>` members for arrays; and
8. invokes `jailbox up`, then `jailbox connection-info`, with the identical
   environment.

Composition of the egress and read-only arrays in steps 5 and 6 must be
deterministic, because array order is a digest input. Preserve file order,
append composed members in a fixed order after it, and drop later duplicates.
Two invocations with the same file and the same editor must produce identical
arrays; otherwise an unchanged project presents changed policy and `up`
refuses.

Because editor bootstrap hosts are part of that policy, selecting a different
editor for an existing sandbox changes the digest and `up` refuses rather than
replacing it. That is the constrained contract working as designed, not a
defect, but JailIDE's documentation must state that switching editors requires
`jailbox stop` and a fresh launch.

The constrained `up` contract makes this sequence valid for first launch,
reopening an already running sandbox, and resuming a complete stopped sandbox.
JailIDE treats any `up` failure as a real failure and does not parse its
diagnostics to decide whether attachment is safe.

JailIDE uses a non-empty `proxy_url` from `connection-info` for the editor's
`http.proxy` setting. It omits that setting when the field is empty. Remote
terminal proxy and bypass variables remain supplied by jailbox through SSH
session environment configuration.

JailIDE never sources jailbox files, calls Podman, derives resource names,
or reads jailbox state. Core validates all values again. An existing sandbox is
opened only when `connection-info` accepts the identical policy; JailIDE
never stops, replaces, repairs, or cleans it automatically. Its invocation of
`up` may resume existing containers only after jailbox validates the complete
resource set and matching policy, or complete a partial set whose existing
resources all carry the matching digest.

## Configuration anchoring

Core no longer reads project configuration, so it needs no config anchor or
selected-config digest record. A project-created file cannot affect core.

One automatic protection stays in core. The selected Containerfile is a launch
input core knows about, so core continues to add it to the effective read-only
paths and no caller configuration can remove it. Remove only the config-file
entries from `finalize_effective_readonly_paths` in
`host/container-runtime.sh`, along with `DEFAULT_CONFIG_PRESENT`,
`DEFAULT_CONFIG_INPUT`, and `SELECTED_CONFIG_INPUT`, and keep the
`SELECTED_DEV_CONTAINERFILE_INPUT` entry and its recheck immediately before
mount arguments are constructed.

JailIDE retains the anchor to protect the policy inputs of sandboxes it
launches. The default file must exist even with `--config`. Reject symlinks in
supplied path components. Protect the default and any selected in-project file
through core's read-only path policy. An external selected file is outside the
project mount.

JailIDE treats project files present at the start of an invocation as trusted
host input. It does not persist a trusted hash or Git revision, monitor the
checkout for changes made by other tools, or attempt to distinguish a
legitimate host edit from a write by a sandbox it did not launch. Files can be
changed by editors, Git operations, scripts, independently launched sandboxes,
and other host processes; policing all such writers is outside JailIDE's
containment boundary. The README threat model must state this limit directly
and must not imply that JailIDE provides general project-file integrity.

Every host caller has the same responsibility for its own policy inputs: if it
turns a project-tree file into `JAILBOX_CONFIG_*` values, it should include that
file in the final `JAILBOX_CONFIG_READONLY_PATHS` for every sandbox it launches.
This is a caller contract and guidance for future orchestrators, not something
core can infer or enforce for files it does not know about. A caller that omits
an input accepts that its sandbox can modify what the caller may trust on a
later invocation.

The configuration digest hashes the exact jailbox release version, final
validated core values, and the selected Containerfile identity. It does not
hash the JailIDE config path or raw file: within one jailbox release, equal
effective sandbox policy is equivalent to core. The anchor is a JailIDE
launch-safety rule, not core configuration identity.

## Repository, state, and installation

Keep the existing repository and history for jailbox. Create an MIT-licensed
`jailide` repository under the same owner, preserving relevant file history
without rewriting or force-pushing the jailbox repository.

```text
display name:       JailIDE
executable:         jailide
install directory: ~/.local/share/jailide/
state root:         ~/.local/state/jailide/
first release:      v0.1.0
```

Move profiles to `~/.local/state/jailide/profiles/<project-id>/`. Prefer
regenerating settings and leave legacy state untouched. Each uninstaller
removes only its own installed files and preserves state by default. Because
neither product deletes the other's leftovers, JailIDE's documentation must
name the legacy `~/.local/state/jailbox/editor-profiles/` path and give an
explicit manual removal instruction for users migrating from the combined
product.

The JailIDE installer verifies compatible jailbox but does not silently
install or upgrade it. Package metadata may declare the dependency later.

## Security invariants

The split and convergent lifecycle preserve these core guarantees:

- the development and proxy containers retain read-only root filesystems, all
  Linux capabilities dropped, and `no-new-privileges`;
- no Docker or Podman socket is mounted into the development container;
- project-scoped runtime state remains outside the project tree;
- the launch inputs core knows about — now the selected Containerfile, since
  core no longer reads a configuration file — are validated before launch,
  mounted read-only, and cannot be removed from policy by caller
  configuration. Protecting a caller's own policy inputs, including
  `jailide.conf`, is the caller contract described under configuration
  anchoring, not something core can enforce for files it never sees;
- egress-filtered sandboxes have no direct external route and use only the
  allowlisting proxy sidecar for outbound HTTP(S);
- SSH always uses strict host-key checking and project-scoped pinned state; and
- every newly created development-container generation receives fresh client
  and server credentials, while a no-op or resume preserves and validates the
  credentials of that same generation.

The sandbox home is writable, sandbox-controlled state. It is deleted at
`stop` by default. With `EPHEMERAL_HOME=false`, it survives generations,
configuration changes, and jailbox upgrades, including shell startup files,
executables, editor servers, and other content written under earlier policy.
Jailbox manages only its marked proxy blocks within that volume; `--clean` is
the only full reset. Persistent mode deliberately trades that cross-generation
trust for retained development state.

The sandbox can read its mounted server host private key because sshd needs it
to authenticate the sandbox to the client. It cannot write the generation key
directory, and the client private key and pinned host state are never mounted.
Possession of the server key does not authenticate the sandbox to the host.

Resume never weakens immutable container settings. The version-bound digest
prevents reuse across jailbox releases, and structural validation rejects
missing or inconsistent resources and SSH state before starting a stopped
container.

These guarantees hold for one lifecycle command at a time. Validation before
mutation is a check-then-act sequence against live Podman state, and JailIDE
runs `up` and `connection-info` as separate processes, so a concurrent
lifecycle command on the same project can invalidate a decision already made.
Serializing lifecycle operations per project is deliberately out of scope here
and remains the backlog's lifecycle-locking item; nothing in this plan should
be read as protecting against a second concurrent invocation.

## Acceptance criteria

- jailbox runs without an editor and accepts configuration only through its
  declared `JAILBOX_CONFIG_*` environment.
- Unknown or invalid configuration fails before mutation and no value is
  evaluated as shell code.
- Core contains no `EDITOR`, config parser, `init`, `--config`, editor
  selection, launch, profile, extension-management, bootstrap-host, or
  editor-test behavior. Generic runtime prerequisites used by SSH-attached
  remote IDE servers remain core-owned.
- Bare jailbox is a non-mutating usage error with status 2; `--help` succeeds
  and `up` is the explicit launch command.
- Core defaults `EPHEMERAL_HOME=true`; `jailide init` visibly writes
  `EPHEMERAL_HOME=false` with the persistence and cross-policy trust tradeoff.
  Volume lifecycle metadata, not invocation-time configuration, controls what
  configuration-independent `stop` removes.
- `up` creates an absent sandbox, reconciles a dependency-safe partial resource
  set only when every existing policy-bearing resource has the current
  version-bound digest, applies the home volume's recorded lifecycle mode
  independently of that digest, accepts an already healthy matching sandbox,
  and never replaces or cleans incompatible resources.
- Resume validates host SSH credentials, pinned host identity, generated SSH
  configuration, container-side SSH runtime state, and resource attachments
  before starting a surviving development container. Failures provide explicit
  `stop`/`up` or `--clean`/`up` recovery guidance.
- A failed new-generation creation leaves no partial generation: every SSH
  artifact that invocation created is removed and pre-existing material is
  untouched.
- `status` reports over its exhaustive documented inventory only. A project
  whose only remaining resources are preserved images reports `absent`. After
  a successful `stop`, a project whose home volume has valid
  `EPHEMERAL_HOME=true` metadata reports `absent`; a persistent home, an
  unlabeled legacy home, and one with an unparseable label all remain and
  report `stopped` because the home volume is inventory. After `--clean`,
  every one of them reports `absent`.
  `jailide init` proceeds in exactly the `absent` cases, so re-initializing a
  project with a preserved home requires `--clean` first.
- `--clean` removes the three derived project image names without checking
  provenance. An externally supplied `DEV_IMAGE` is untouched unless its name
  is one of those three exact derived names. `stop` and `--clean` remove
  resources occupying derived names regardless of digest validity or legacy
  status, and the README documents that deletion boundary.
- Machine-output Base64 encoding and decoding are proven on both GNU and
  BSD/macOS tooling by the portable gate.
- Core array keys use contiguous indexed `JAILBOX_CONFIG_<KEY>_<N>` members and
  accept any legal path, including members containing commas. Index gaps,
  malformed indices, non-empty bare array names, and bare-plus-indexed
  combinations each fail before mutation with a diagnostic naming the variable.
- An unknown key carrying an index suffix fails as an unknown name rather than
  matching the array pattern.
- `jailide.conf` array keys repeat one member per line in file order, mapping
  to `_0` upward; a lone empty occurrence is the empty array; mixed empty and
  non-empty occurrences, and repeated scalar keys, are errors.
- The JailIDE configuration reference documents that its line-delimited array
  form cannot express a member containing a newline, that such input is
  undetectable rather than rejected, and that the indexed environment interface
  has no such limit.
- Host-generated server authentication files are mounted read-only and satisfy
  StrictModes through `--userns=keep-id`; runtime tests reject incompatible
  ownership without weakening SSH permissions. Client private and pinned host
  state are never mounted.
- Repeated `up` and resume preserve one generation's SSH identities; `stop`
  followed by `up` creates a new generation and rotates both client and server
  credentials. Missing or altered SSH state blocks resume, and strict host-key
  checking is never relaxed.
- `stop` removes all containers and networks, removes a valid
  `EPHEMERAL_HOME=true` volume, preserves a valid `false` volume, preserves an
  unlabeled legacy volume as `false`, and preserves with a warning when the
  label is present but unparseable. `--clean` removes
  the home volume and project runtime state, and every recommendation of it
  warns about that loss.
- Changing an existing ephemeral home to persistent uses `stop` then `up`;
  changing an existing persistent home to ephemeral requires warned
  `--clean` then `up`.
- A missing network is recreated only when no development or proxy container
  survives. Every create or resume path derives the proxy URL from the live
  network and synchronizes generated SSH session state and managed downloader
  blocks before declaring readiness.
- `--version`, `config-schema`, `status`, and `connection-info` have stable
  tested output and do not expose secrets.
- `status` remains the one-word lifecycle interface; `doctor` provides detailed
  non-mutating resource, digest, SSH, network, proxy, and recovery diagnostics
  without claiming a current-policy match when no configuration was supplied.
- `config-schema` is generated from `host/public-api.sh`; within a compatible
  jailbox version range, JailIDE accepts newly declared core keys without
  carrying or releasing an updated static key list.
- `connection-info` reports the live proxy URL for an egress-filtered sandbox,
  including collision-fallback addressing, and a required empty `proxy_url`
  for an unfiltered sandbox; it does not expose the allowlist.
- JailIDE sets editor `http.proxy` exactly when `proxy_url` is non-empty, while
  jailbox remains the sole source of remote-session `NO_PROXY` and `no_proxy`.
- The exact jailbox release version, final validated environment values, and
  Containerfile identity determine the digest. Every independently surviving
  development container, proxy container, and network carries it; reuse and
  attach reject missing, inconsistent, or mismatched labels. A persistent-mode
  home volume is preserved across versions and policy changes without digest
  gating; its creation-time lifecycle mode is recorded separately and must
  match the requested configuration.
- JailIDE owns and protects `jailide.conf`, composes editor policy, and
  uses only the documented jailbox executable and environment interface. Its
  integrity guarantee covers the in-project policy files of sandboxes JailIDE
  launches, not changes made through other host tools or independently launched
  sandboxes.
- JailIDE reuses a sandbox only after core accepts identical effective policy;
  its only automatic mutation of existing lifecycle is asking `up` to resume or
  complete a dependency-safe partial sandbox after that validation.
- Repositories have independent versions, installers, state, releases,
  documentation, and gates.
- jailbox portable/runtime and JailIDE portable/editor gates pass against
  the declared compatible releases.
- Release notes document removed jailbox interfaces, including `ssh-config`,
  direct users to JailIDE, and explain the new `stop` network and conditional
  home-volume removal. They also state that upgrading jailbox changes the
  version-bound digest, so every existing sandbox requires `stop` then `up`;
  that this preserves an unlabeled legacy or persistent home and removes an
  ephemeral one; and that moving an existing home to ephemeral mode instead
  requires warned `--clean` and destroys it.
- `--version` reports the version stamped at package time in an installed
  copy and the documented development version in a source checkout, and both
  spellings are covered by the portable gate.
- The pre-1.0 bump policy in `host/public-api.sh` and `suggest_bump` in
  `scripts/release.sh` treat an added configuration key or CLI flag as a patch
  bump and a removed or changed one as a minor bump, so a jailbox release that
  only adds keys stays inside JailIDE's declared range.
- An unlabeled home volume reads as `EPHEMERAL_HOME=false` everywhere, so an
  existing sandbox upgrades non-destructively with `stop` then `up` under the
  `false` mode `jailide init` writes. Requesting `true` against that volume
  refuses before mutation as a persistent-to-ephemeral change and directs the
  user to warned `--clean`. A present but unparseable label refuses before
  mutation. Core never labels a volume it did not create.
- JailIDE composes the egress and read-only arrays deterministically, so
  repeated launches of an unchanged project produce an unchanged digest, and
  its documentation states that switching editors requires `stop` and a fresh
  launch.
- `jailide init` validates its template keys against the discovered
  `config-schema` before writing.

## Non-goals

- A plugin system or private cross-repository API.
- A second protocol version independent of the jailbox release.
- Automatic dependency installation or matching product versions.
- Worktrees, credentials, agent presets, scheduling, or Git integration.
- Moving SSH out of jailbox.
- Allowing JailIDE to call Podman or inspect core state directly.
- Automatic replacement, cleanup, or mutation of an incompatible existing
  resource.
- Persistent file-integrity monitoring or trusted-hash tracking for changes
  made outside JailIDE-launched sandboxes.
- Serializing concurrent lifecycle commands against the same project.
