# 3.2. JailIDE repository split charter

## Goal

Split the user-facing project into independently installed products:

```text
JailIDE (Go) ---------> jailbox (Bash) -> Podman
orchestrator ---------> jailbox (Bash) -> Podman
```

jailbox remains the generic machine-facing sandbox substrate, implemented in
Bash; JailIDE owns the human configuration and editor workflow and is a new
Go implementation. Their runtime dependency points only toward jailbox, and
the products communicate only through jailbox's installed executable and its
documented machine interfaces. `plans/repository-split-rationale.md` records
why the split exists, why JailIDE is Go, and why jailbox stays Bash.

## Sequence

Implement the indexed plans in filename order. Version precedes digest because
the release version is hashed; digest precedes ownership-label removal because
it becomes the reuse gate; JailIDE exists and passes its gates before core
removes the surfaces it replaces.

## Product boundary

jailbox owns canonical configuration and validation, images, Podman lifecycle,
filesystem and egress policy, SSH generations and transport, deterministic
identity, machine status/connection data, generic caller-supplied wrapper setup,
and portable/runtime gates. SSH and generic attached-development prerequisites
stay core behavior. JailIDE supplies editor-specific wrapper setup through the
public caller mechanism and owns compatibility fixes to that contribution.
JailIDE owns `jailide.toml`, init, editor discovery/validation, profiles,
bootstrap destinations, launch/diagnostics, editor pins, and unit/editor
gates.

End-state jailbox has no config files, `init`, `--config`, `EDITOR`,
`JAILBOX_EDITOR`, editor launch/discovery, profiles, bootstrap composition,
`ssh-config`, or editor gate. Neither product owns worktrees, external
credentials, agent selection, scheduling, or Git integration.

Each product owns its complete release tooling. jailbox keeps its existing
Bash packaging, installer, and release scripts; JailIDE uses standard Go
build and release tooling. There is no shared release toolkit, and neither
product's installer may replace or uninstall the other.

## Repository layout

This checkout remains jailbox. Plan 03.2.11 creates JailIDE as a fresh Go
repository at a user-selected path; it shares no history or source with
jailbox. If it is temporarily nested inside this checkout during development,
it is listed only in `.git/info/exclude`, never in tracked `.gitignore`, and
no build, test, or runtime path may depend on nesting or on a sibling
checkout. Plan 03.2.15 proves that independence before either product is
released.

## Security invariants

- Container roots remain read-only, with capabilities dropped and
  `no-new-privileges`.
- No container-engine socket is mounted.
- Project runtime state remains outside the project.
- Core validates and read-only mounts known launch inputs; callers protect
  their own policy inputs.
- Egress mode has no direct route and HTTP(S) uses the allowlisting proxy.
- SSH uses strict host-key checking and project-scoped pinned state.
- Each new container generation gets fresh client/server credentials; resume
  preserves and validates that generation.

Persistent home content is sandbox-controlled state trusted across policy and
version changes. Server material is read-only and client secrets stay
host-only. Digest and structure validation prevent weakened resume. Guarantees
cover one lifecycle command at a time; locking remains backlog work.

## Acceptance criteria

- Each product exposes only its owned surface through the documented executable
  and environment boundary.
- All indexed plans and their gates pass in order.
- Both final repositories have independent documentation, gates, remotes,
  commit identities, versions, and releases.
- JailIDE's real editor gate detects remote-server runtime regressions, while
  jailbox owns and releases the prerequisite fix before compatibility is
  claimed.

## Non-goals

- Plugins, a private API, a separate protocol version, an installed or
  dynamically downloaded shared runtime library, a shared source repository,
  a shared release toolkit, or shared product policy.
- Automatic dependency installation or version matching.
- Moving SSH out of core or allowing JailIDE to call Podman.
- Automatic cleanup/replacement, persistent integrity monitoring, or lifecycle
  serialization.
