# 3.2.15.1. Core organization and resource-contract verification

## Intent

### Goal and sequence

Make core understandable by command and resource, reuse production resource
detection in tests, and organize verification around detection, refusal, and
recovery contracts. Reduce repeated integration work without weakening the
security model or public behavior.

Read `03.2-machine-boundary-plan.md` first. Implement after
the accepted closure of `03.2.11.5-frontend-verification-plan.md` and its
frontend umbrella, archived with the local test evidence and its documented
limits. That acceptance is this plan's starting baseline; do not reopen frontend
completion or treat its evidence limits as additional passing results. This is
a separate core follow-up, not another frontend implementation step. Its own
final verification requirements below remain unchanged.

Implement before `03.2.16-consumer-verification-plan.md`. This plan owns the
core migration, its immediate installer/path integration, and the revised
verification strategy. The consumer plan receives the verified layout and
coverage inventory for its final installer completeness, consumer compatibility,
and durable-documentation review. Neither plan may defer ordinary regression
coverage to the other. The machine-boundary series remains one release unit;
no release occurs before its remaining plans and all four gates are complete.

### Behavior and boundaries

Preserve command names, configuration declarations, byte formats, exit-status
behavior, recovery guidance, and security invariants. This work does not make
invalid resources automatically disposable. In particular:

- Invalid SSH material continues to refuse unsafe reuse and require the
  existing recovery path; do not replace credentials beneath surviving
  containers automatically.
- Home retention and recovery precedence remain data-preserving. Corrupt
  retention metadata does not authorize deletion by `stop`; `--clean` retains
  its explicitly destructive meaning.
- Failed inspection is neither absence nor invalidity, and must not authorize
  dependent mutation. Rollback preserves dependencies needed by survivors.
- Read-only roots, capability restrictions, protected mounts, strict SSH
  identities, project-external runtime state, and proxy-only filtered egress
  remain enforced.
- Frontend modules invoke public core child processes. They do not import core
  detectors or inspect private state. Core checks remain outside the editor
  integration assertions.
- No lifecycle locking, concurrent mutation guarantee, or cross-command
  validation cache is introduced. Existing caller-serialization requirements
  remain applicable.

### Core ownership

Organize `src/host/core/` into these responsibility groups:

| Group | Responsibility |
|---|---|
| Commands | Public core command handlers and their orchestration |
| Resources | Detection, validation, and explicit operations for each resource |
| Configuration | Environment loading, configuration validation, fingerprints |
| Project | Project identity, resource naming, host-path validation |
| Checks | Host prerequisites and coordination of compatibility/attachment checks |

Keep module loading and initialization at the core entry boundary. Within a
resource module, detectors and mutations are separate functions but remain
together under the same owner. Coordinated checks call resource detectors;
they do not duplicate their detailed inspection logic. Resources do not call
public command handlers. Cross-resource recovery ordering and rollback belong
to command orchestration rather than hidden resource side effects.

Version has a command implementation under commands. Shared consumers obtain
the same version through a shared initialization/lookup facility, not by
calling the version command handler. Preserve commands that do not need a
version stamp or full runtime initialization; relocation must not introduce
eager validation or host dependencies on those paths.

Public command membership remains declared in `src/public-api.sh`; the directory
is not another declaration source. Preserve validated dispatch coverage for new
declarations, and keep frontend commands and installation/help behavior in
their existing layers.

### Production detection contracts

Tests exercise the same detection code used by production commands. Each
detector inspects without repair or cleanup, exposes a finite classification
with an actionable reason, and distinguishes failed observation from a known
state. The representation is internal; no new public state protocol is needed.

Sharing detectors must preserve each command's inspection scope. `status`
reports inventory independently of configuration compatibility and SSH health;
`stop` and `--clean` remain usable with missing or malformed configuration.
Do not make these paths require full resource health or attachment validation.
Retain regressions proving that unhealthy resources remain inspectable and
recoverable under each command's existing refusal and preservation rules.

Collapse concrete defects only when relevant commands have equivalent handling,
including refusal, preservation, diagnostics, and recovery. A single generic
invalid flag must not hide a distinction that changes safe handling.
Resource-local validity and relationships must both have explicit owners.
For example, valid key files may belong to the wrong container, and a valid
network may be an incorrect or newly recreated dependency.

Inventory these resource families and retain their distinct handling contracts:

| Family | Required distinctions to assess |
|---|---|
| Development and proxy containers | Absent, startable non-running, running; incompatible structure versus unresponsive service; unsupported engine states |
| Ordinary, internal, external networks | Absent, usable, incompatible; missing/wrong attachments, replacement identity, and unrelated members |
| Home volume | Absent, persistent, ephemeral, corrupt retention metadata; existing user data and ownership |
| SSH generation | Absent, valid, invalid; staged/legacy/orphaned material, container binding, and unsafe containing paths |
| Host runtime directory and generated files | Absent, usable, unsafe path/type/metadata; proxy configuration and allowlist consistency; unrelated retained content |
| Images and references | Absent/present project-owned images, selected image suitability, reference changes versus immutable container image identity |
| Project paths and mounts | Required source suitability, mount source and access, protected overlays, socket exposure |

Requested network/home modes and configuration compatibility are inputs or
relationships, not extra copies of the resources. Upstream outages, inspection
errors, mutation failures, and interruptions are environmental conditions or
operation outcomes. Do not disguise them as resources safe to discard.

### Verification strategy

Use individual resource states by default. Combinations require a named
interaction requirement, not an exhaustive Cartesian product. Automated
enumeration may expand explicit contracts, but must not derive expected behavior
from the production detector or silently skip unsupported declarations.

Maintain a reviewable mapping from current assertions to their final coverage:

1. **Detection and refusal:** construct each meaningful concrete defect, expect
   its independently specified classification, and verify the appropriate
   command refusal/guidance without unsafe mutation. Include malformed outputs,
   plausible output with failed producers, and conditional-call failures.
2. **Resource responses and recovery:** cover each behaviorally distinct state
   with applicable commands. Prove the prescribed recovery paths, home/data
   retention, survivor identity, and cleanup retryability. Equivalent defects
   share comprehensive recovery coverage instead of repeating the same sequence.
3. **Interactions:** retain focused evidence for recovery precedence, credential
   binding, container/network dependencies, filtered attachment readiness,
   unrelated resource preservation, and failed removal with surviving dependents.
   Use decision-level tests when they prove the contract; retain real-resource
   integration where the boundary requires it.
4. **Healthy integration:** prove creation, healthy reuse, resume, persistent and
   ephemeral stop/relaunch, complete cleanup/relaunch, and actual attachment.
   Reuse existing transport tests for argv, stdin, exit status, terminal behavior,
   proxy delivery, and refusal; do not repeat every transport assertion in every
   resource scenario.
5. **Interruption consequences:** establish the actual post-interruption state
   and independently verify preservation of data, unrelated resources, identities,
   and dependencies. Require recognition and appropriate recovery guidance for
   partial state. Detailed recovery and transport tests need not run at every
   interruption point when their obligations are mapped to coverage above.

Initially retain the existing discovery-driven interruption points and their
independent operation-role requirements. The current baseline has 327 points;
this is evidence, not a frozen required count. New mutation points continue to
enter discovery, and changes cannot silently lower coverage. Keep representative
interrupt-and-retry integration for creation, credential publication, home
initialization, stop, clean, and failed rollback. An unexplained partial state or
missing required transition is a test failure, not a new expected outcome.

Production classification may be reused to observe outcomes, but test expectations
come from fixture construction and explicit contracts. Independently check critical
effects, including preserved file contents and exact survivor identities. Prove
that a deliberately wrong classification, suppressed refusal, or omitted required
check makes the applicable regression fail. Shared code must not become its own
oracle.

This plan does not adopt a general graph-walking scheduler. Keep independently
owned fixtures and bounded, deterministic sequences. Any reuse must verify its
preconditions and preserve the coverage of distinct state/command transitions.
Do not assume `exec` or `shell` is incapable of changing user files: use controlled
probes and preserve the tests' isolation and cleanup obligations.

### Portability and performance

Catch the demonstrated macOS portability failures locally: avoid ambiguous
basic-regex extensions for assertions, use exact comparisons or explicit regex
syntax, and test logical versus physical paths using symlinked temporary roots.
Use existing portable test setup and focused regressions rather than adding a
new gate or silently adding GNU utilities as product prerequisites. Failures
identify the scenario, relevant exit status, and captured test diagnostics;
avoid indiscriminate tracing of credentials or user environment values.

Reuse the existing 50- and 150-case performance samples and timing artifacts.
Start with the 50-case sample, with worker count, host resource limits, image
preparation, and workload held fixed. Separate structural migration measurements
from coverage-strategy changes. Once a candidate improvement is established,
use a warm-up and repeated measured runs to assess the spread.

The samples exclude interruption sweeps. Measure the interruption changes using
bounded existing fault jobs or their per-phase timings as well; sample speed
alone cannot establish full-matrix improvement. Record coverage and work avoided
alongside elapsed time. Do not claim a target speedup or case count in advance.
Keep workers fixed while evaluating implementation efficiency; changing worker
count alone is not a resource-efficiency result.

### Acceptance criteria

- The core groups above have explicit owners; commands, resource operations,
  detailed detection, and coordinated checks do not maintain parallel policy.
  Public behavior and frontend isolation are unchanged.
- Shared detection preserves command-specific inspection scope: inventory does
  not require healthy attachment, and recovery does not require valid launch
  configuration. Regressions prove these distinctions without weakening the
  existing refusal and preservation contracts.
- Existing mixed modules are migrated and obsolete paths removed. Source,
  installed, packaging, installer, lint, syntax, boundary, and test-fixture
  consumers all use the resulting layout.
- A coverage mapping accounts for every previous load-bearing assertion before
  duplicate integration work is removed. Detector classifications, refusal and
  recovery contracts, named interactions, and healthy integration have independent
  expected outcomes and effective negative controls.
- Interruption discovery retains its required mutation-role coverage. Lightweight
  consequence checks preserve data/dependency guarantees and representative
  interrupt-and-retry tests demonstrate actual recovery.
- Deterministic coverage manifests detect missing scenarios, handlers, and fault
  contracts. Lifecycle membership still derives from the public declarations;
  no declaration silently loses test coverage.
- Benchmarks report comparable before/after workloads, timings, and limitations.
  Any changed sample membership starts a new baseline or is compared on the
  exact shared workload. A sample is never reported as a full matrix pass.
- Portable passes on Linux, Bash 4.4, and macOS; permission-sensitive tests pass
  under both `0022` and `0002`. Runtime, matrix, and both selected-editor CI jobs
  pass against the final implementation. Unavailable prerequisites remain open
  verification work, not passing evidence.
- `ARCHITECTURE.md`, `CONTRIBUTING.md`, and repository ownership instructions
  describe the implemented layout and test strategy. The final consumer plan
  receives the layout/coverage handoff. Archive this plan only after completion.

## Implementation detail

### Suggested layout and migration inventory

Use a command directory and resource directory, with the remaining concerns
grouped rather than accumulating in a catch-all helper module:

```text
src/host/core/
  entry.sh
  commands/       up, stop, clean, status, connection-info, exec, shell,
                  validate, ssh-config, config-schema, version
  resources/      container, home, network, proxy, ssh, images, runtime-files
  configuration/ load and digest
  project/       identity and paths
  checks/        host, compatibility, attachment
```

Names within those groups are guidance. Keep shared version lookup available
through initialization/configuration support while its printing handler lives
under commands; do not retain a duplicate root-level version implementation.

Migrate existing code rather than introduce replacement detectors alongside it:

- `src/host/core/common.sh`: distribute configuration loading, path validation,
  and project/resource identity to their owners.
- `src/host/core/container-runtime.sh`: separate home, container/mount and runtime
  file operations from `run_status`, `stop_jailbox`, `clean_jailbox`, launch
  tracking, and rollback orchestration. Preserve one operation-state owner.
- `src/host/core/network.sh`: separate network ownership from proxy container,
  configuration-file, and filtering behavior.
- `src/host/core/validation.sh`: move detailed SSH/proxy/session checks to the
  resource owners; retain shared attachment coordination under checks and move
  `run_connection_info` to its command owner.
- `src/host/core/config-digest.sh`: keep fingerprint production in configuration
  and coordinate cross-resource reuse decisions in compatibility checks.
- `src/host/core/dev-image.sh`, `ssh.sh`, `downloader-proxy.sh`, `exec.sh`,
  `preflight.sh`, `project-id.sh`, `schema.sh`, and `version.sh`: relocate or
  consolidate according to the agreed responsibilities. Extract handlers from
  mixed modules and `src/host/core/entry.sh` without changing call order.

Update the source annotations and loading paths in `src/jailbox`, the dispatch
integration in `src/host/cli.sh`, and `src/install.sh`'s `REQUIRED_PATHS` to the
complete new host-module inventory. Update direct source/copy references in
tests, `scripts/check-frontend-boundary.py` discovery as necessary, and existing
lint, syntax, package, and installer completeness checks. No obsolete-path shims
are needed solely for the unreleased migration. Follow the repository's `.new`
replacement procedure for protected files and verify a copied tree carrying
those replacements before handoff.

### Reuse the existing test machinery

Audit `tests/lib/lifecycle-matrix.sh`, `lifecycle-contracts.sh`,
`lifecycle-runtime.sh`, `lifecycle-runtime-faults.sh`, `lifecycle-jobs.sh`, and
`tests/integration/lifecycle-state.sh` before changing coverage. In particular,
`matrix_observe` currently repeats status, connection-info, exec, and shell
checks; `run_mutation_faults` invokes full observation before and after recovery.
Replace that repetition with the explicit coverage assignments in the intent,
not with unchecked success records or expectations inferred from the command.

Extend existing unit suites for detectors, observer effectiveness, matrix
contracts, fault discovery, cleanup ownership, and packaging. Preserve real
runtime/editor transport evidence in its owning gate. Update manifests and
progress reporting so the revised test counts describe actual work rather than
preserving the historical 493-case label.

`CONTRIBUTING.md` documents `--sample-50` and `--sample-150`, `sample-summary`,
`completed-cases`, `case-timings`, and `timings`. Preserve these comparison tools
and the existing four public gates. If resource-response selection changes the
sample implementation, retain deterministic selection and clearly document the
coverage change before collecting its new baseline.

Deliver the structural migration with behavior checks first, then introduce
detector-contract consolidation and test-workload reduction in reviewable steps.
Run `tests/run portable`, `tests/run runtime`, `tests/run matrix`, and
`tests/run editor` for the final integration; use the smaller comparisons during
optimization rather than repeatedly requesting full gates for initial profiling.
