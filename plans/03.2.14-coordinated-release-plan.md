# 3.2.14. Coordinated validation, repository move, and release

## Goal

Prove the final jailbox/JailIDE pair through the installation boundary, move
JailIDE out of the temporary nested checkout, establish safe remotes, and
release both products in dependency order.

## Sequence

Run after 03.2.13 and before continuing plans 5–8. This plan owns operational
cutover only; product behavior must already satisfy its owning plan.

## Coordinated identifiers and artifacts

Record in the handoff/release evidence:

- the full jailbox divergence commit imported by 03.2.10;
- the final jailbox candidate commit after 03.2.13;
- the final JailIDE candidate commit;
- the exact local package/prerelease artifact filename, checksum, and reported
  jailbox version installed for JailIDE testing; and
- JailIDE's declared compatible jailbox range.

Build the candidate with jailbox `scripts/build-tarball.sh`/release tooling,
install it into an isolated test prefix using the supported installer path, and
ensure JailIDE resolves that installed executable. Tests must not call the
jailbox worktree. Where a later core interface change required JailIDE source
adaptation, identify the explicit JailIDE commit; do not merge post-divergence
jailbox history.

## Pre-move gate sequence

Against the coordinated commit/artifact pair:

1. run complete jailbox `tests/run portable`;
2. run complete jailbox `tests/run runtime`;
3. run complete JailIDE `tests/run portable`;
4. run complete JailIDE `tests/run editor`; and
5. record skips only where the gate itself reports a supported platform skip,
   never as a passing complete gate.

This is the final rerun after core removal. Compare with the earlier
pre-removal run required by 03.2.13 so the evidence proves JailIDE replacements
worked before deletion and still work after it.

## Host-side repository move

The nested location cannot survive release. Ask the user for the sibling target
path because moving outside the confirmed workspace is a host-side action.
With both worktrees clean and gates recorded:

1. move the complete `jailide/` Git working copy to the selected sibling path,
   preserving its `.git` directory and permissions;
2. verify its HEAD and divergence record are unchanged;
3. add the standalone JailIDE repository as `origin` with fetch/push URLs
   supplied by the user;
4. retain `jailbox-upstream` with its existing fetch URL and disabled push
   URL, and prove a normal push cannot target jailbox;
5. remove exactly the `/jailide/` entry from jailbox `.git/info/exclude`;
   and
6. verify no tracked `.gitignore` in either product gained a nested-checkout
   rule.

Do not perform the move or remote mutation without the user's selected path and
repository URL. Do not push yet.

## Post-move independence proof

From each standalone checkout:

- confirm clean status, expected branch/HEAD, remotes, and no nested copy;
- rebuild packages/generated files and rerun all four complete gates using the
  same installed-artifact boundary;
- search jailbox and JailIDE source, tests, workflows, docs, installers, and
  packages for the old nested absolute/relative path;
- prove jailbox lint, unit discovery, packaging, and workflows do not inspect
  JailIDE, and JailIDE invokes only the installed jailbox executable; and
- compare gate outcomes and generated artifacts with the pre-move run.

Any location-dependent result blocks release and is fixed in the owning
repository, followed by the complete affected gate set.

## Remote and release safety

Before any explicitly authorized push/tag/release, display both repositories'
remotes and exact commits. jailbox pushes only to its existing jailbox origin;
JailIDE pushes only to its new origin. Never push JailIDE commits or tags to
`jailbox-upstream`.

Release the final environment-only jailbox version first using its existing
release procedure. Verify the published artifact checksum and `--version`,
install that exact artifact, and rerun the JailIDE compatible-version check and
complete gates if the published bytes differ from the prerelease artifact.
Then release JailIDE `v0.1.0` against that exact jailbox version.

No stable jailbox release supports both configuration interfaces. No transition
release or duplicate editor implementation is published.

## Release notes and documentation

jailbox notes:

- removed `jailbox.conf`, `init`, `--config`, editor interfaces, bare
  editor launch, profiles, and `ssh-config`;
- direct human editor users to JailIDE and environment callers to the canonical
  interface;
- explain expanded stop, default ephemeral deletion, persistent/unlabeled
  retention, malformed-label preservation, and clean data loss; and
- state that the version-bound digest makes every upgrade require stop/up,
  except changing persistent/legacy home to ephemeral requires warned clean/up.

JailIDE notes document v0.1.0 installation, compatible jailbox version, config
and init, editor matrix, profile root, proxy/bootstrap behavior, legacy profile
cleanup, and absence of automatic jailbox installation/migration.

Update cross-links to released repository URLs only after the standalone
repository exists.

## Security invariants

All product security invariants were verified through installed artifacts both
before and after relocation. Remote configuration prevents cross-repository
pushes. Destructive home cleanup remains explicit and warned. No release step
reintroduces a file interface, editor implementation in core, direct Podman
access in JailIDE, or a container-engine socket.

## Acceptance criteria

- Divergence, final commits, artifact checksum/version, compatible range, and
  all complete gate outcomes are recorded.
- The standalone move preserves JailIDE history/HEAD, establishes correct
  origin, retains fetch-only jailbox-upstream, and removes the local exclude.
- All four complete gates and package/generated checks behave identically
  before and after relocation.
- No runtime/build/test/document path depends on nesting or a jailbox worktree.
- jailbox releases first; JailIDE v0.1.0 names and passes against that exact
  published version; each release goes only to its own remote.
- Release notes cover every removed interface, migration boundary, persistence
  tradeoff, and destructive recovery.

## Non-goals

- New product behavior, shared utilities, automatic dependency installation,
  a dual-interface transition release, or wholesale post-divergence merging.
