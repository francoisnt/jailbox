# 3.2.11. JailIDE repository, installation, and gates

## Goal

Create JailIDE as an independent, MIT-licensed Go repository with its own
executable, installation and state roots, release machinery, documentation,
plans, and unit/editor gates.

## Sequence and reference point

Implement after jailbox plans 03.2.01–03.2.09 form one reviewed coordinated
commit. Record the exact jailbox commit, built artifact checksum, and reported
version that JailIDE development targets; JailIDE tests install and exercise
that artifact, never a jailbox source worktree. When a later jailbox interface
change requires adaptation, record the newly targeted artifact explicitly.

JailIDE is a fresh repository with no jailbox history. Create it at a
user-selected path as its own Git repository. If it is temporarily nested
inside the jailbox checkout during development, list it only in jailbox
`.git/info/exclude`, never in tracked `.gitignore`, and confirm jailbox
discovery, lint, packaging, and tests do not descend into it. No build, test,
or runtime path may depend on nesting.

## Implementation

JailIDE is one Go module built with a pinned Go toolchain version, producing
one statically linked `jailide` binary per supported target with
`CGO_ENABLED=0` and `-trimpath`. Prefer the standard library; keep any
third-party dependency minimal and reviewed, pinned by `go.mod` and
integrity-verified by `go.sum`. There is no committed `vendor/` tree.
Behavior that jailbox's editor and configuration modules provide today is
reimplemented in Go against the documented contracts in 03.2.12/03.2.13; no
shell source is ported or vendored.

The supported release targets are `linux/amd64`, `linux/arm64`,
`darwin/arm64`, and `darwin/amd64`, mirroring where jailbox runs. Minimum
supported OS versions are those of the pinned Go toolchain.

The editor-dependency setup script owned by 03.2.13 remains POSIX `sh`
because it runs inside arbitrary container base images. It is embedded in
the `jailide` binary with `go:embed` and materialized on demand as defined
in 03.2.13; it is a product runtime input passed to jailbox, not a
separately installed file.

## Public identity and installation

Set these public values:

```text
display name:       JailIDE
repository:         jailide
executable:         jailide
installed binary:   ~/.local/bin/jailide
state root:         ~/.local/state/jailide/
profile root:       ~/.local/state/jailide/profiles/<project-id>/
first release:      v0.1.0
license:            MIT
```

There is no separate install directory: product assets, including the editor
setup script, are embedded in the binary, so the installed footprint is the
one executable plus the state root JailIDE creates at runtime.

Release archives are named `jailide-vX.Y.Z-<goos>-<goarch>.tar.gz`, contain
the `jailide` binary and license/readme metadata, and are published with one
`SHA256SUMS` file. Installation is placing the binary at
`~/.local/bin/jailide`; the README documents the exact command, and
`go install` from the repository is a second supported channel. JailIDE
itself never writes to any binary location: update replaces the one
installed file atomically as the user's explicit action, and removing the
binary is the user's documented `rm`.

`jailide uninstall` removes only JailIDE's own state root and profiles,
after confirmation, then prints its running executable's resolved path with
the exact removal command for the user to finish with. Render that path as one
shell-safe argument so whitespace, quotes, glob characters, and other shell
metacharacters cannot alter the displayed command. It never deletes any binary,
so no ownership or marker mechanism is needed. Its help text states that it
removes JailIDE state, not sandboxes; sandbox lifecycle belongs to jailbox
`stop` and `--clean`. It never touches any jailbox path, and JailIDE must never
delete jailbox installation or state. Document manual removal of legacy
`~/.local/state/jailbox/editor-profiles/`; do not remove it automatically.

The public command surface is `jailide [--config PATH] [--editor
code|codium]`, `jailide init`, `jailide uninstall`, `--version`, and
`--help`. Version JailIDE with ordinary SemVer judgment under a documented
pre-1.0 policy; there is no generated API classifier.

## jailbox dependency boundary

Resolve one installed `jailbox` executable at invocation start and use that
exact path for `--version`, `config-schema`, `status`, `up`, and
`connection-info`. Declare a compatible jailbox version range in one JailIDE
version source, validate it before project/editor work, and give exact
install or upgrade guidance on absence or incompatibility. JailIDE never
installs or upgrades jailbox.

Tests must substitute a built package or prerelease installation, never
execute a jailbox source checkout. Add a fake-executable harness for
unit-gate contract tests.

## Gates and workflows

JailIDE has exactly:

```text
tests/run unit
tests/run editor
```

The unit gate wraps Go tooling: formatting and vet checks plus any adopted
linters, unit and contract tests for parser, init, composition, and the
jailbox client against the fake executable, and archive-layout, setup-script
materialization/verification, and uninstall scope checks proving only the
state root and profiles are removed, no binary or jailbox path is touched, and
the printed removal command safely represents adversarial executable paths as
one argument. It requires no
Podman, editor, or network beyond Go module resolution, which `go.sum` pins
and verifies; with a populated module cache it runs fully offline. Editor
prepares only supported positive wrapper images through the
installed jailbox artifact, then tests real pinned VS Code and VSCodium
Remote SSH, profiles/settings, proxy behavior, and launch.

PR CI runs the unit gate and the supported editor gate. Release/canary uses both;
scheduled CI additionally tests the latest compatible jailbox and its default
branch. There is no JailIDE runtime gate: jailbox owns editor-independent
container/security and negative-image cases.

## Documentation

Write README covering installation prerequisites, quick start, configuration,
editor precedence/matrix, profiles, bootstrap hosts, Remote SSH extension,
proxy behavior, compatible jailbox range, legacy cleanup, and
troubleshooting. Write `AGENTS.md`/`CONTRIBUTING.md` naming the two gates and
module ownership, add MIT `LICENSE`, and start a JailIDE-owned
active/backlog/archive plan series describing only remaining JailIDE work.

## Acceptance criteria

- The targeted jailbox commit, artifact checksum, and version are recorded
  before feature work, and every jailbox interaction uses one compatible
  installed executable through documented machine interfaces only.
- The repository contains only JailIDE behavior and infrastructure: no
  jailbox history, source, or shell modules, and no copy of jailbox release
  tooling.
- Installation, state, uninstall, versioning, documentation, plans, and
  workflows consistently use JailIDE identity, and installation cannot touch
  jailbox files.
- Unit and editor gates are complete and pass without reading any jailbox
  checkout.
- jailbox packaging and tests cannot descend into a nested JailIDE checkout.

## Non-goals

- Publishing, adding a JailIDE `origin`, or releasing before 03.2.15.
- Reimplementing Podman, SSH, resource identity, lifecycle, or runtime
  security.
- Porting or vendoring jailbox shell source, automatic jailbox installation,
  or a shared runtime library between the products.
