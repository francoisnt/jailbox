# 3.1.2. Resource-limit configuration keys

## Goal

Make the development container's hardcoded resource limits declared public
configuration before the digest exists, so the first digest version covers
them and no deployed sandbox is later invalidated just to add the keys.

## Sequence

Implement after `03.1-environment-only-configuration-plan.md` and before
`03.2.02-configuration-digest-plan.md`. No other plan depends on it.

## Public interface

Declare three scalar keys in `host/public-api.sh`, with literal defaults
equal to today's hardcoded `podman run` values so an absent key preserves
current behavior exactly:

```text
MEMORY_LIMIT  (default 4g)   -> --memory for the development container
CPU_LIMIT     (default 2)    -> --cpus
PIDS_LIMIT    (default 256)  -> --pids-limit
```

These are the first keys with non-empty `CONFIG_DEFAULTS` entries. The
default is the effective value, not a launch-time fallback for an empty
one, so an absent key and an explicitly spelled default produce identical
effective configuration — and identical digests once 03.2.02 lands.

Values are opaque data and Podman is the authority on their validity.
Each value is passed verbatim inside a single `podman run` argument
(`--memory=$MEMORY_LIMIT`, …), never evaluated, split, or interpreted by
jailbox. No key-specific grammar is checked; only the generic value rules
that already apply to every configuration value hold (the environment
model rejects control characters, the file adapter rejects whitespace and
shell metacharacters), which is also what keeps digest framing
unambiguous. A value Podman rejects — including a present-but-empty one,
which flows through as `--memory=` — fails at container start with
Podman's own diagnostic, after network/volume mutation, exactly as a
typo'd `DEV_IMAGE` fails at pull/run today. Under 03.2.02 such a failed
launch leaves resources labeled with the bad value's digest, so
correcting the value goes through the explicit lifecycle recovery
contract rather than a plain retry; this is the accepted cost of not
re-implementing Podman's grammars.

## Generic scalar assignment

Before declaring the keys, make scalar assignment declaration-driven:
replace the per-key case arms in `assign_config_scalar`,
`parse_config_scalar`, and `apply_config_defaults` with direct indirect
assignment (`printf -v "$key" '%s' "$value"`). This is safe because the
assigned names come only from the declared scalar key arrays (machine and
frontend), which `validate_public_api_declaration` already restricts to
the uppercase identifier grammar — never from user input. Array keys keep
`set_config_array`; only scalars are in scope.

With that in place, 03.1's automatic-coverage contract holds fully for
scalars: the declarations alone extend the environment spellings
(`JAILBOX_CONFIG_MEMORY_LIMIT`, …), the temporary file adapter, defaults,
schema, digest, and public-API comparison, with no key-specific code
anywhere in this plan. Plans 7 and 8 inherit the same property for their
future keys.

The limits apply to the development container only. The proxy sidecar's
resources remain core policy, not configuration.

A changed limit changes the digest under 03.2.02 and makes existing
resources incompatible; recovery is the explicit lifecycle contract, not
in-place adjustment of a running container.

## Tests and documentation

Unit tests cover absent keys producing byte-identical resource flags to
today, configured values landing verbatim in the constructed flags as
single argument values, and the declarations flowing into parser,
defaults, and public-API comparison without key-specific plumbing —
existing scalar behavior (including `EDITOR` on the frontend path) is
unchanged by the generic assignment. README documents the keys in the
configuration table, noting that Podman validates the values at container
start. Update the public-API fixture. Run `tests/run portable` and
`tests/run runtime`.

## Acceptance criteria

- Absent keys launch with exactly today's `--memory=4g --cpus=2
  --pids-limit=256`.
- A configured value reaches Podman verbatim as part of a single argument;
  jailbox adds no key-specific validation.
- Values Podman rejects fail at container start with Podman's diagnostic.
- The keys participate in schema, digest, and bump-policy coverage purely
  through their declaration once those mechanisms land.
- No per-key case arm exists for any scalar key: assignment, parsing, and
  defaults are driven by the declarations alone.

## Non-goals

- Key-specific value validation or re-implementing Podman's limit
  grammars.
- Canonicalizing equivalent spellings: `2` vs `2.0` or `4g` vs `4096m`
  are identical policy but different digests, accepted as a rare and
  low-consequence divergence.
- Proxy-container limits, verifying runtime enforcement, or resizing a
  running container.
