# 3.1.2. Resource-limit configuration keys

## Goal

Make the development container's hardcoded resource limits declared public
configuration before the digest exists, so the first digest version covers
them and no deployed sandbox is later invalidated just to add the keys.

## Sequence

Implement after `03.1-environment-only-configuration-plan.md` and before
`03.2.02-configuration-digest-plan.md`. No other plan depends on it.

## Public interface

Declare three scalar keys in `host/public-api.sh`, with defaults equal to
today's hardcoded `podman run` values so an absent key preserves current
behavior exactly:

```text
MEMORY_LIMIT  (default 4g)   -> --memory for the development container
CPU_LIMIT     (default 2)    -> --cpus
PIDS_LIMIT    (default 256)  -> --pids-limit
```

Validate before any image, credential, network, volume, or container
mutation, with a diagnostic naming the key. The grammar is a strict subset
of what Podman accepts:

- `MEMORY_LIMIT`: a nonzero decimal integer without leading zeros, with an
  optional single lowercase suffix `b`, `k`, `m`, or `g`.
- `CPU_LIMIT`: a nonzero decimal number — an integer without leading zeros,
  or an integer part (`0` allowed) followed by `.` and one to three digits
  with at least one nonzero digit overall.
- `PIDS_LIMIT`: a nonzero decimal integer without leading zeros.

Values are strict data passed as single `podman run` argument values; they
are never evaluated, split, or interpreted by jailbox beyond this grammar.
Under 03.1's automatic-coverage contract, the declarations alone extend the
environment spellings (`JAILBOX_CONFIG_MEMORY_LIMIT`, …), the temporary file
adapter, schema, digest, and public-API comparison; only the grammar
validators are key-specific code.

The limits apply to the development container only. The proxy sidecar's
resources remain core policy, not configuration.

A changed limit changes the digest under 03.2.02 and makes existing
resources incompatible; recovery is the explicit lifecycle contract, not
in-place adjustment of a running container.

## Tests and documentation

Unit tests cover absent keys producing byte-identical resource flags to
today, each accepted and rejected grammar form naming the key, and the
declarations flowing into parser, defaults, and public-API comparison
without key-specific plumbing. README documents the keys in the
configuration table. Update the public-API fixture. Run
`tests/run portable` and `tests/run runtime`.

## Acceptance criteria

- Absent keys launch with exactly today's `--memory=4g --cpus=2
  --pids-limit=256`.
- Every invalid value fails before mutation, naming the key.
- The keys participate in schema, digest, and bump-policy coverage purely
  through their declaration once those mechanisms land.

## Non-goals

- Proxy-container limits, unlimited or uppercase spellings, verifying
  runtime enforcement, or resizing a running container.
