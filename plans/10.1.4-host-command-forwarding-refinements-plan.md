# 10.1.4. Host command forwarding refinements

## Intent

Extend `10.1-host-command-forwarding-plan.md` with a sectioned policy format,
fixed argument insertion, per-section settings, transparent local fallback,
signal forwarding, a terminal indicator and policy-match logging.
Implement before
`10.2-host-git-forwarding-plan.md`, which uses these mechanisms for Git
integration.

### Policy format

The policy file consists of sections. This replaces the one-line rule format
of `10.1-host-command-forwarding-plan.md`; its matching, regex, escaping,
continuation and limit rules still apply unless changed here.

```text
# Protections for every forwarded git call.
[git]
# Ignore repository hooks and file watchers.
insert -c core.hooksPath=/dev/null \
       -c core.fsmonitor=false
# Use the host's SSH program.
insert -c core.sshCommand=ssh
allow status
allow commit -m "WIP {{.*}}"

[git log]
insert --oneline
allow {{[^-].*}}

[git push]
insert --no-verify
log all
fallback false
allow
allow origin {{main|dev}}

[git remote add]
insert --no-tags
allow upstream {{https://[a-z./-]+}}

[podman]
allow ps --format '{{.Names}}'
```

With `G` standing for the three `[git]` insertions
`-c core.hooksPath=/dev/null -c core.fsmonitor=false -c core.sshCommand=ssh`:

| Sandbox invocation | Host invocation |
| --- | --- |
| `git log main` | `git G log --oneline main` |
| `git commit -m "WIP parser"` | `git G commit -m "WIP parser"` |
| `git push` | `git G push --no-verify` |
| `git push origin main` | `git G push --no-verify origin main` |
| `git remote add upstream https://x.org/r` | `git G remote add --no-tags upstream https://x.org/r` |
| `podman ps --format '{{.Names}}'` | unchanged |

`"WIP {{.*}}"` is one argument combining literal text and a regex section,
and `'{{.Names}}'` is a literal argument.

- A header line `[COMMAND WORD...]` starts a section, which continues until
  the next header. `COMMAND` follows the existing executable-name grammar;
  optional `WORD`s are literal arguments, without regex sections, and make
  the section a subsection of any depth. Headers
  with the same command and words, however quoted, form one section: their
  `allow` lines combine and their `insert` arguments are concatenated in file
  order. Blank and comment lines may appear anywhere;
  any other line outside a section is invalid, as are policies in the
  one-line format.
- Every line in a section starts with a keyword:
  - `allow PATTERN...` permits one invocation whose arguments after the
    header words match the patterns. `allow` without patterns permits the
    header words alone. A section may contain any number of `allow` lines.
  - `insert ARG...` adds one or more literal arguments. A section may contain
    any number of `insert` lines; their arguments are concatenated in order.
  - `log none` (default), `log unmatched` or `log all` controls policy-match
    logging as described below. Logging is opt-in because arguments may
    contain credentials.
  - `fallback true` (default) or `fallback false` controls local fallback.

  A section may repeat `log` or `fallback` only with the same value;
  different values for one section, even across repeated headers, fail
  policy validation with both lines reported. Unknown keywords and
  invalid values fail policy validation. `insert`, `log` and `fallback` never
  grant permission. Create a wrapper and resolve the host executable only for
  commands with at least one `allow` rule across their sections. Sections
  without rules still participate in insertion inheritance and settings
  resolution.
- Single-quoted text is fully literal, as in a shell: it contains no regex
  sections, backslash is an ordinary character, and it cannot contain a
  single quote. `'{{.Names}}'` is the literal argument `{{.Names}}`. Regex
  sections and backslash escaping remain active inside double quotes.

### Argument insertion

- The final argument array is the command name, then, for the matched rule's
  section and each shorter header of the same command that its header words
  extend, from shortest to longest, the words that header adds to the next
  shorter one followed by its `insert` arguments, then the remaining original
  arguments. Each original argument appears once. There is no substitution
  or shell evaluation. With `[git]` inserting `A`, `[git push]` inserting
  `B` and `[git push origin]` inserting `C` and allowing `main`, `git push
  origin main` becomes `git A push B origin C main`. A section's insertions
  apply only to invocations permitted by a rule in that section or one of its
  subsections, never to an invocation merely starting with its header words.
  Rewording an invocation cannot avoid a section's insertions while still
  using that section's rules; it can only match a rule in another section,
  which applies that section's insertions instead.
- Match the original received invocation against all `allow` rules of its
  command. Inserted arguments do not affect matching or
  authorize any additional invocation. A request is ambiguous only when its
  matching rules would produce different final argument arrays or resolved
  settings; matching rules from the same section always agree. The order of
  rules and sections never affects matching or ambiguity; only the order of
  `insert` arguments within a section, including merged repeated headers,
  follows the file. Policy validation compares each rule's complete pattern,
  including its header words, and rejects two rules with the same complete pattern
  that would produce different final argument arrays or resolved settings.
- Only the host, using the validated policy snapshot, constructs the final
  argument array. Preserve every
  original argument and its order. Reject an
  invalid rule or an output exceeding the supported argument limits.

### Settings resolution

A matched request's `log` and `fallback` values come from the matched rule's
section. An unmatched request uses the longest header whose words begin its
arguments. Values that section does not set come from shorter headers its
words extend, then the defaults. These settings are conveniences, not
security controls: an invocation worded differently, such as with options
before a subcommand, may match another rule or resolve to a shorter header.
Settings are included in the snapshot.

### Local fallback

- Apply fallback to every forwarded command unless its resolved settings
  select `fallback false`. This supersedes the no-fallback rule in
  `10.1-host-command-forwarding-plan.md` for requests the host refuses, and
  its refusal of calls from outside the project.
- Calls from outside the project are not forwarded: the wrapper runs the
  local executable directly, without contacting the host, regardless of the
  fallback setting. For calls inside the project, the host makes every
  eligibility and fallback decision from its policy snapshot; the container
  holds no policy settings.
- An eligible invocation runs on the host. When the host refuses a request
  before starting a program because no rule matches or the working
  directory is inside a `HIDDEN_PATHS` directory, a local executable runs
  with the original arguments, directory, environment and untouched stdin.
  Resolve the local executable without selecting a forwarding wrapper again.
  If fallback is disabled for that command, report the refusal instead. If no
  local executable exists, report an error.
- A request that meets both a fallback reason and one of the results below
  reports that result: the host completes every applicable pre-execution
  check before allowing fallback.
- Report these results without local retry: an ambiguous match, an exceeded
  matching limit, an extended argument list exceeding the limits, a changed
  policy snapshot, a broken host project mapping
  (the host project is unavailable, or the working directory is missing,
  replaced or outside the host project when the host opens it), an
  unavailable host executable
  or one that fails to start, a transport or service failure, and a host
  program exit.
- Update the existing refusal tests to verify this behavior.

### Signal forwarding

After the host reports that the program has started, each SIGINT, SIGTERM or
SIGHUP the client receives is forwarded to the host program's process group,
and the client keeps streaming until the program exits, then exits with its
status, as a local program would. The host process relaying the request is
not ended by a forwarded signal, so it can still relay the program's
remaining output and exit status. Host programs that ignore or delay handling
a signal keep running. This supersedes the immediate client exit with an
unknown outcome in `10.1-host-command-forwarding-plan.md`. A signal before
the program has started, and a lost connection, still end the client with an
unknown outcome; host cancellation on disconnect, `stop`, `--clean` and
rollback is unchanged.

Preserve the distinction between a program exiting with a numeric status and
a program being terminated by a signal throughout the forwarding protocol.
The client reproduces the corresponding termination: it exits with the same
status or terminates itself with the same signal, so callers such as a Bash
loop interrupted by Ctrl-C react as they would to a local program.

### Terminal indicator

When both stdout and stderr are connected to a terminal, print `[HOST]` on
its own line to stderr after the host reports that the program has started
and before displaying any command output. Do this once per host invocation,
including commands that subsequently fail. Local execution, refused requests
and captured output, such as `x=$(git describe)`, receive no indicator.
Command stdout, stderr and exit status otherwise remain unchanged.

### Policy-match log

With `log unmatched`, record each request that reaches the host and has no
matching policy rule, including requests eligible for local fallback. With
`log all`, record every completed policy-match result. `log none` records
nothing. Record an ambiguous request when the resolved settings of any
matching rule's section would record that request had the rule matched
alone. Use one CSV row
per recorded attempt, with columns `timestamp`,
`cwd`, `command` and `match`: a UTC ISO 8601
timestamp, the project-relative working
directory, the original full command string with argument boundaries and
special characters unambiguously quoted or escaped, and the match result
(`matched`, `unmatched` or `ambiguous`). A match record does not establish
that the host program ran. Do not aggregate repeated requests or evaluate
logged text.

Keep the log in project-scoped host state, accessible only to the host user
and independent of the forwarding service's disposable state. It survives
later launches, stops and failed-launch rollbacks, which preserve its
records, and a retained log is never mistaken for orphaned service state;
`--clean` deletes it. Bound its size by discarding the oldest records.
Document its location.
Do not log stdin, output or environment variables; arguments themselves may
contain sensitive data. Logging is silent in the container. Concurrent
requests must not interleave records, and logging delays a request by at most
a brief bounded wait. A record that cannot be written within that wait, or
whose write fails, is skipped and must not change the authorization or
fallback decision.

## Implementation detail

Retain the matching patterns and section ancestry in the compiled rule.
Construct the final argument array separately from matching, after
authorization and before starting the host program.

Distinguish an ineligible invocation from a host execution failure in the
protocol so wrappers can choose local fallback without retrying a host action.
The ineligibility result carries whether fallback is allowed. The client
cannot tell when the program started from the existing refusal and exit
frames, so add a host message sent after the program starts and before any
output frame; the client prints the indicator when it arrives. Signal
forwarding needs a client-to-host message naming the signal. The current
exit frame carries one byte that cannot tell exit status 128+N from
termination by signal N, so it must carry that distinction. The host request
process currently leads the program's process group and treats these signals as
cancellation, so signalling the group as it stands would end the request
process too. Keep the program in the request process's group: the service's
forced shutdown kills that group, which is safe only while the request
process is alive. Have the request process catch forwarded signals rather
than set them to ignored, since an ignored signal stays ignored in the
program, and move the service's own cancellation request to a channel
forwarding never uses, such as the existing lifetime pipe.
