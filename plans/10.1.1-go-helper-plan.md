# 10.1.1. Go helper for host command forwarding

## Intent

The host command forwarding implementation for
`10.1-host-command-forwarding-plan.md` currently runs Python on the host and
installs Python 3 in every wrapper image. Replace that Python with Go programs
and remove the Python runtime dependency from both sides. 10.1 is
complete only when this plan is implemented; archive both plans together.

This plan also establishes the Go module, toolchain, build, packaging,
installation, and CI that later plans extend. `11.1-go-frontend-plan.md` adds
the frontend program, and later work moves core into its program, until both
layers are Go. This plan moves no frontend or core logic beyond the forwarding helper
and the container's argument decoding.

### Go programs

- Use one Go module rooted at `src/` that builds one program per role. This
  plan adds two: a container program under `src/container/` (forwarding client
  and `jailbox exec` argument decoding), and a core program under
  `src/host/core/` (the forwarding service and policy matcher, called by the
  Bash core). The core program grows as later work moves core to Go, until it
  replaces the Bash `jailcore`. `11.1-go-frontend-plan.md` adds the frontend
  program under `src/host/frontend/`.
- Programs share only common code, such as the forwarding protocol, the
  argument codec, and version stamping, through shared packages that import no
  role's code. The container program imports only its own and shared packages.
  The core program never imports frontend or container code. The frontend
  never imports core or container code and reaches core only through its
  public CLI.
- The subcommands added here are private: not on `PATH`, not declared in
  `src/public-api.sh`, not user-documented, and free to change in any release.
  Each program carries its release version and refuses to run when called by
  runtime files from a different version.
- Depend only on the Go standard library, plus `golang.org/x/sys` where the
  standard library lacks a required call. Build without cgo. Linux binaries
  are statically linked. macOS binaries use libraries supplied by the OS.

### Behavior

Port the host forwarding service and policy matcher, the container forwarding
client, and the container's `jailbox exec` argument decoding. External behavior
stays as currently implemented and specified by 10.1: protocol framing, the
argument frame limit and grammar shared with `jailbox exec`, exit statuses and
messages, policy snapshots and digests, executable location checks, hidden
directory identity checks, working-directory pinning, locking, retirement,
cancellation, and lifecycle integration. Core's Bash orchestration calls the Go
core program where it calls Python today; core otherwise stays Bash.
Forwarding refuses to start when the core program or the jailbox runtime files
it uses lie in the project tree or another container-writable location.

Each request runs in its own process, which validates and enters the working
directory and then starts the command; the service never changes its own
working directory. Tests cover concurrent requests from different directories.

The Go matcher preserves 10.1's byte-oriented POSIX rules. Each byte counts
as one character, character classes are ASCII-only, and a definition matches
the complete argument. `^` and `$` match only at the argument's ends. `.`,
negated bracket expressions, and `[[:space:]]` can match newline. Reject
bracket collating-symbol (`[.` `.]`) and equivalence-class (`[=` `=]`) forms.
Keep 10.1's matching time limit and end the request process when it expires.
The policy and pattern size limits remain. Enforce 10.1's combined limit on
nested counted repetitions. Tests cover acceptance at the limit, rejection
above it at policy load, embedded and trailing newlines, and non-UTF-8 bytes
in patterns and arguments.

Remove the Python runtime implementation and its dependency:

- `src/host/core/resources/forwarding/main.py`, `policy.py`, and `service.py`,
  and `select_forwarding_python` in `src/host/core/resources/forwarding.sh`.
- `src/container/runtime/lib/jailbox/forward_client.py`,
  `forward_protocol.py`, and `argv_codec.py`, and the Python invocations in
  `src/container/runtime/bin/jailbox-forward-client` and
  `src/container/runtime/bin/jailbox-exec-argv`.
- `python3` in every package list in `src/container/setup.sh`, and
  `check_runtime_python_syntax` in `scripts/lib/container-shells.sh` and its
  callers.
- The host and wrapper-image Python 3 requirements in the documentation.
- The parts of `tests/lib/forwarding-test.py` that import the removed
  modules, replaced by Go tests with equivalent coverage. Tests that drive the
  programs from outside may stay in Python. Python remains acceptable for
  repository tooling, tests, and test fixtures.

### Releases, installation, and checkout

- Releases contain one archive per platform for Linux and macOS on amd64 and
  arm64, named `jailbox-vX.Y.Z-OS-ARCH.tar.gz` with matching
  `jailbox-latest-OS-ARCH.tar.gz` copies. They replace `jailbox-vX.Y.Z.tar.gz`
  and `jailbox-latest.tar.gz`. `SHA256SUMS` covers every archive. Each archive
  contains the core program built for its platform and the container program
  built for Linux on the same architecture. Shared packages also compile for
  Windows as a check; isolate OS-specific operations so later Windows support
  can add implementations without restructuring.
- The installer stays Bash 3.2-compatible, selects the archive from the host
  OS and architecture, verifies its checksum as today, and fails clearly on an
  unsupported platform. To install a specific release, download that tag's
  `install.sh`. Each published installer defaults to the tag it shipped with
  and uses that release's archive layout. The installer can replace any
  installed version. Uninstall removes the programs. Users need no Go toolchain.
- The wrapper build takes the prepared Linux program as an input and installs
  it as an executable outside the normal container `PATH`. A dev image whose
  architecture differs from the host's fails clearly before the wrapper build;
  emulated architectures are unsupported.
- Developers build the checkout programs explicitly into an ignored location.
  Source installs and checkout commands use those prebuilt programs, and release
  installs use the programs bundled beside the CLI. A command that requires a
  missing or incompatible program fails with a clear diagnostic. Runtime
  commands run without Go. Installed core works independently of the frontend.
- One pinned Go version is used by CI, the root `Containerfile`, and release
  builds. Release builds stamp the release version; checkout builds use the
  `dev` version.

### Tests and CI

No new gate. Acceptance requires all five gates:

- `lint` adds Go formatting and static analysis. Go source discovery is
  automatic, like shell discovery.
- `portable` on Linux and macOS runs the Go tests, compiles every release
  target and the Windows check, and runs packaging and the install/update/uninstall
  lifecycle with the runner's platform archive.
- `runtime`, `matrix`, and `editor` build the current tree's programs in test
  setup and use the resulting binaries for CLI calls. A failed build fails
  test setup and never reuses earlier build output. The matrix preserves
  failure and interruption coverage for forwarding policy publication and
  transport startup through the private Go core program.
- Releases build and validate every platform archive and run the install test
  for each platform CI can run natively.
- `tests/run dev` adds the fast Go checks.

Cover both checkout and installed layouts, the version mismatch refusal, the
installer's platform selection and unsupported-platform failure, a saved
installer still selecting its own release after a newer one is published, and
the architecture mismatch failure.

### Documentation

Update `AGENTS.md` with the Go rules this plan creates: module, program, and
package placement by layer, import boundaries, the pinned toolchain, formatting and
analysis, test placement, and that runtime code no longer uses Python. Update
README, `ARCHITECTURE.md`, `CONTRIBUTING.md`, and the guides for per-platform
installation, the explicit checkout build step, and the removed Python

## Implementation detail

Share one build script under `scripts/` for explicit checkout builds, tests,
CI, and releases. It takes the target platform, output directory, and version. Build
with `CGO_ENABLED=0`, `-trimpath`, and the version set through `-ldflags`.
Use the local toolchain without automatic downloads (`GOTOOLCHAIN=local`) and
fail clearly when it is older than the module requires.

`scripts/build-tarball.sh` currently copies all of `src/` into one archive;
build per-platform stages instead, excluding Go sources and module files from
the bundle. Update `src/install.sh`, `scripts/validate-release.sh`,
`.github/workflows/release.yml`, `.github/workflows/test-gates.yml`,
`scripts/lint.sh`, and `tests/run` accordingly. Update `tests/portable/smoke.sh`
to verify the packaged Go programs in place of the forwarding Python files.

Update `src/container/Containerfile.wrapper` and `src/container/setup.sh` to
copy and install the prepared Linux executable. Preserve shell discovery in
`scripts/lib/container-shells.sh` when adding the native asset.

Migrate the Python-specific fault instrumentation in
`tests/lib/lifecycle-runtime.sh`, `tests/lib/lifecycle-fault.sh`, and
`tests/lib/lifecycle-contracts.sh` to intercept the private Go core executable
in the test fixture and trace the same operations.

For byte-exact matching, map each byte of the pattern and argument to the rune
with the same value. Anchor the grouped pattern and configure the regex engine
for 10.1's newline rules. The standard library's `syscall` package or
`golang.org/x/sys/unix` provides directory-relative opens without following
symlinks, `fchdir`, `flock`, sessions, and process-group signals.
